微信支付实战：接入准备、Native 下单、回调通知与退款全流程

2026年11月25日 · 约 13 分钟 · 4464 字 #微信支付#Java#Spring Boot#后端#支付实战#APIv3

这篇文章把微信支付实战课程的课堂笔记整理成一份可复盘的技术文档，覆盖从接入准备、安全基础、项目骨架，到 Native 下单、支付通知、退款、账单的完整链路。整体按“先概念、再骨架、最后接口流程”的顺序组织，方便以后重建环境或排查支付问题时查阅。

一、微信支付产品形态与接入准备

1.1 常见支付产品

产品形态 适用场景 特点
付款码支付 线下面对面收银 用户出示微信钱包付款码，商家扫码后完成支付
JSAPI 支付 公众号、线下、PC 网站 用户在微信内或扫码后输入金额完成支付
小程序支付 微信小程序内交易 在小程序平台内完成支付
Native 支付 PC 网站 商家展示支付二维码，用户用微信“扫一扫”付款，商家预先指定金额
APP 支付 移动端独立 APP 在 APP 应用内集成微信支付模块
刷脸支付 刷脸设备前 通过摄像头刷脸、识别身份后完成支付

1.2 接入前需要准备的资料

接入微信支付前，需要先在对应平台申请并妥善保存以下材料：

  • 商户号：在微信商户平台提交资料、签署协议后获取；
  • AppID：在微信公众平台注册服务号、完成认证后获取，再绑定商户号；
  • APIv2 密钥：APIv2 版本接口使用，在商户平台「账户中心 → 安全中心 → API 安全」设置；
  • APIv3 密钥：APIv3 版本接口使用，同样在 API 安全中设置；
  • 商户 API 证书：APIv3 接口普遍需要，APIv2 的退款、企业红包、企业付款等高级接口也需要；
  • 微信支付平台证书：可预先下载，也可通过编程方式获取，用于验签。

注意：所有 API 密钥和证书都属于敏感信息，必须妥善保管，防止泄露；公开博客、代码仓库中不要写入真实密钥、私钥或证书。

二、支付安全基础

理解微信支付的签名、验签与解密之前，先补齐几个密码学基础概念。

2.1 机密性相关概念

  • 明文：加密前的消息；
  • 密文：加密后的文本；
  • 密钥：掌握特殊“钥匙”的人才能解密文本，密钥本质是一个字符串，常用位（bit）度量长度；
  • 加密：实现机密性最常用的手段，按密钥使用方式可分为对称加密和非对称加密；
  • 解密：使用密钥还原明文；
  • 加密算法：加解密操作所使用的算法。算法本身通常是公开的，算法使用的密钥则必须保密。

2.2 对称加密与非对称加密

对称加密

  • 特点：只使用一个密钥，密钥必须保密，常见算法如 AES；
  • 优点：运算速度快；
  • 缺点：密钥需要在交换双方共享，一旦被窃取，消息会被破解，无法做到安全的密钥交换。

非对称加密

  • 特点：使用两个密钥——公钥可以任意分发，私钥必须保密，常见算法如 RSA；
  • 优点：黑客获取公钥无法破解密文，解决了密钥交换问题；
  • 缺点：运算速度非常慢。

混合加密：实际场景中通常把对称加密与非对称加密结合起来使用。

2.3 身份认证

  • 公钥加密、私钥解密：作用是加密信息；
  • 私钥加密、公钥解密：作用是身份认证。

2.4 摘要算法（Digest Algorithm）

摘要算法也就是散列函数、哈希函数（Hash Function），能把任意长度的数据“压缩”成固定长度、且独一无二的摘要字符串，相当于给数据生成了一个数字指纹。

作用：保证信息的完整性。

特性：

  • 不可逆：只有算法，没有密钥，只能加密不能解密；
  • 难题友好性：想要破解只能暴力枚举；
  • 发散性：原文哪怕只改动一点点，摘要就会发生剧烈变化；
  • 抗碰撞性：原文不同，计算出的摘要也要不同。

常见摘要算法：MD5、SHA1、SHA2（SHA224、SHA256、SHA384）。

2.5 数字签名与数字证书

数字签名：使用私钥对摘要加密生成签名，接收方用公钥对签名解密后进行验签，实现身份认证和不可否认。

数字证书：解决“公钥信任”问题，防止黑客伪造公钥。公钥不能直接分发，必须通过由 CA 颁发的数字证书来分发。HTTPS 握手时，浏览器会校验网站证书链、确认域名与证书一致，再与服务器交换加密信息。

2.6 微信支付中的两类证书

  • 商户证书：由商户申请，包含商户号、公司名称、公钥信息，在商户后台申请；
  • 平台证书：由微信支付负责申请，包含微信支付平台标识、公钥信息，商户用其中的公钥进行验签。

三、案例项目骨架

实战案例基于 Spring Boot 搭建，先把后端工程、接口文档、统一返回结构、数据库和持久层准备好。整体分层包结构大致为：controller（接口）、service / service.impl（业务）、mapper（持久层）、entity（实体）、enums（状态与接口地址枚举）、vo（返回对象）、config（配置）、util（工具）、task（定时任务）。

3.3 统一返回结果与 Lombok

引入 Lombok 简化实体类开发。定义统一结果类 R，包含状态码 code、消息 message、数据 data，并提供 ok()、error()、data() 链式方法；需要链式调用时在类上加 @Accessors(chain = true)：

@Data
@Accessors(chain = true) // 链式操作
public class R {
    private Integer code;
    private String message;
    private Map<String, Object> data = new HashMap<>();

    public static R ok() {
        R r = new R();
        r.setCode(0);
        r.setMessage("成功");
        return r;
    }

    public static R error() {
        R r = new R();
        r.setCode(-1);
        r.setMessage("失败");
        return r;
    }

    public R data(String key, Object value) {
        this.data.put(key, value);
        return this;
    }
}

四、APIv3 接入准备

4.1 读取支付参数

把支付相关配置（商户号、AppID、商户私钥路径、APIv3 密钥、通知域名等）放到 wxpay.properties，通过配置类 WxPayConfig 读取为 Bean。项目中可引入 spring-boot-configuration-processor（optional 标记为 true），让配置文件与代码参数之间自动提示、定位。

可在测试 Controller 中读取商户号验证参数是否注入成功：

@Api(tags = "测试控制器")
@RestController
@RequestMapping("/api/test")
public class TestController {

    @Resource
    private WxPayConfig wxPayConfig;

    @GetMapping("/get-wx-pay-config")
    public R getWxPayConfig() {
        String mchId = wxPayConfig.getMchId();
        return R.ok().data("mchId", mchId);
    }
}

4.2 加载商户私钥

商户私钥文件（apiclient_key.pem）复制到项目目录，使用 SDK 提供的 PemUtil.loadPrivateKey 加载为 PrivateKey：

public PrivateKey getPrivateKey(String filename) {
    try {
        return PemUtil.loadPrivateKey(new FileInputStream(filename));
    } catch (FileNotFoundException e) {
        throw new RuntimeException("私钥文件不存在", e);
    }
}

4.3 引入 SDK 与 JSON 处理

APIv3 官方 SDK 封装了请求签名生成、应答签名验证与平台证书自动更新，引入 wechatpay-apache-httpclient；接口与通知报文使用 JSON，引入 Gson：

</dependency>
<dependency>

4.4 获取签名验证器与 HttpClient

证书与密钥在各环节的使用关系（M 代表商户私钥/公钥，W 代表微信支付公钥/私钥）：

签名验证器：平台证书封装了微信的公钥，用于验签；使用 ScheduledUpdateCertificatesVerifier 可以定时更新平台证书，无需手动传入证书。

@Bean
public ScheduledUpdateCertificatesVerifier getVerifier() {
    PrivateKey privateKey = getPrivateKey(privateKeyPath);
    // 私钥签名对象（签名）
    PrivateKeySigner privateKeySigner = new PrivateKeySigner(mchSerialNo, privateKey);
    // 身份认证对象（验签）
    WechatPay2Credentials credentials = new WechatPay2Credentials(mchId, privateKeySigner);

    return new ScheduledUpdateCertificatesVerifier(
            credentials,
            apiV3Key.getBytes(StandardCharsets.UTF_8));
}

HttpClient 对象：是建立远程连接的基础，通过 SDK 的 Builder 构造，构造出的 HttpClient 会自动处理签名、验签并更新证书：

@Bean
public CloseableHttpClient getWxPayClient(ScheduledUpdateCertificatesVerifier verifier) {
    PrivateKey privateKey = getPrivateKey(privateKeyPath);

    WechatPayHttpClientBuilder builder = WechatPayHttpClientBuilder.create()
            .withMerchant(mchId, mchSerialNo, privateKey)
            .withValidator(new WechatPay2Validator(verifier));

    return builder.build();
}

五、Native 下单

5.1 支付流程

Native 扫码支付的整体时序：

  1. 商户后台生成订单；
  2. 商户调用统一下单 API；
  3. 微信支付系统预支付交易；
  4. 微信返回支付二维码链接 code_url；
  5. 商户把二维码展示给用户，用户打开微信扫一扫；
  6. 微信校验链接有效性，用户确认支付、输入密码；
  7. 微信验证授权并完成交易；
  8. 微信异步回调商户支付结果；
  9. 商户根据回调或主动查单确认订单状态，再进行后续发货等操作。

5.2 接口分层

  • WxPayController：暴露 /api/wx-pay 相关接口；
  • WxPayService 与 WxPayServiceImpl：封装下单业务逻辑。

Controller 接收商品 ID，调用 Service 返回二维码链接和订单号：

@ApiOperation("调用统一下单 API，生成支付二维码")
@PostMapping("/native/{productId}")
public R nativePay(@PathVariable Long productId) throws Exception {
    log.info("发起支付请求");
    Map<String, Object> map = wxPayService.nativePay(productId);
    return R.ok().setData(map);
}

5.3 下单 Service 逻辑

Service 层处理要点：

  1. 订单防重：先按商品 ID 查询是否存在未支付订单，存在则直接复用已有订单和已保存的二维码，避免重复下单；
  2. 生成订单：填充标题、商品 ID、金额、未支付状态后入库；
  3. 组装请求体：appid、mchid、description、out_trade_no、notify_url、amount（total 总金额、currency 币种 CNY）；
  4. 把参数序列化为 JSON，以 application/json 发送 POST 请求；
  5. 解析响应得到 code_url，把二维码链接回填到订单；
  6. 返回二维码链接和订单号给前端。

下单请求体字段示例：

Gson gson = new Gson();
Map<String, Object> paramsMap = new HashMap<>();
paramsMap.put("appid", wxPayConfig.getAppid());
paramsMap.put("mchid", wxPayConfig.getMchId());
paramsMap.put("description", orderInfo.getTitle());
paramsMap.put("out_trade_no", orderInfo.getOrderNo());
paramsMap.put("notify_url",
        wxPayConfig.getNotifyDomain().concat(WxNotifyType.NATIVE_NOTIFY.getType()));

Map<String, Object> amountMap = new HashMap<>();
amountMap.put("total", orderInfo.getTotalFee());
amountMap.put("currency", "CNY");
paramsMap.put("amount", amountMap);

金额注意：微信支付金额单位为分，入参、落库与后续金额一致性校验都要保持单位一致。

六、支付通知（异步回调）

6.1 内网穿透

本地开发时，微信服务器无法直接访问本机服务，需要用内网穿透工具（如 ngrok）把本地端口暴露为公网地址：

ngrok http 8090

启动后得到的公网地址填入支付配置的通知域名；每次重启 ngrok 地址变化后，都需要同步修改通知配置。

6.2 通知应答规则

  • 用户支付完成后，微信会把支付结果和用户信息发送给商户，商户需要接收处理并返回应答；
  • 应答不符合规范或超时，微信会判定通知失败，并按策略重试（频率大致为 15s、15s、30s、3m、10m、20m、30m……总计约 24h），但不保证通知最终一定成功；
  • 成功应答必须为 200 或 204，否则视为失败应答；商户收到通知后应在 5 秒内返回应答报文，否则微信会重复发送通知。

6.3 验签、解密与订单处理

回调处理的核心步骤：

  1. 读取通知报文：把请求体读取为字符串；
  2. 验签：参考 SDK 源码中的 WechatPay2Validator 封装通知验签工具类 WechatPay2ValidatorForRequest，用 verifier、请求体与请求 ID 校验请求签名，验签失败返回 500 与错误应答；
  3. 解密报文：通知中的 resource 使用 AES-256-GCM 加密，取出 ciphertext（密文）、nonce（随机串）、associated_data（附加数据），用 APIv3 密钥通过 AesUtil.decryptToString 解密得到明文 JSON；
  4. 处理订单：解析明文得到 out_trade_no，更新订单状态为支付成功，并记录支付日志；
  5. 成功应答：返回 200 与 {"code": "SUCCESS", "message": "成功"}。

6.4 支付日志记录

支付日志实体留存订单号、微信支付单号 transaction_id、交易类型 trade_type、交易状态 trade_state、支付金额 payer_total，并把完整通知原文存入 content 字段，便于事后对账排查。

6.5 重复通知与并发控制

微信可能把同一通知多次发送给商户，商户系统必须正确处理重复通知。官方对回调处理的注意事项如下：

  • 幂等性：处理前先查询业务数据状态，若订单已经是已支付状态，直接返回成功，不再重复处理；
  • 并发控制：在更新订单状态、处理订单之前，使用数据锁进行并发控制，避免函数重入造成数据混乱。示例使用 ReentrantLock 的 tryLock：
private final ReentrantLock lock = new ReentrantLock();

// 在业务数据状态检查和处理之前加锁
if (lock.tryLock()) {
    try {
        // 处理重复通知：已处理则直接返回
        String orderStatus = orderInfoService.getOrderStatus(orderNo);
        if (!OrderStatus.NOTPAY.getType().equals(orderStatus)) {
            return;
        }
        // 更新订单状态、记录支付日志
    } finally {
        lock.unlock(); // 必须主动释放锁
    }
}

七、订单查询、取消与超时关单

7.1 查询本地订单状态

后端提供查询本地订单状态的接口（如 GET /query-order-status/{orderNo}）：订单已支付返回成功，否则返回“支付中”。前端在二维码页面用定时器定时轮询订单状态（示例每 3 秒一次），支付成功后清除定时器，延迟跳转成功页。

7.2 用户取消订单

用户主动取消订单时：

  1. 调用微信支付的关单接口（请求体携带商户号 mchid）；
  2. 更新商户端订单状态为已取消（OrderStatus.CANCEL）。

7.3 主动查单核实

商户后台未收到异步通知时，应主动调用微信查单接口同步订单状态。查单为 GET 请求，URL 拼接订单号与商户号，返回结果中的 trade_state 用于判断：

  • SUCCESS：核实已支付，补更新本地订单状态为成功，并记录支付日志；
  • NOTPAY：核实仍未支付，调用关单接口关闭订单，并把本地订单状态置为已关闭（CLOSED）。

7.4 定时处理超时未支付订单

Spring 提供 Spring Task 实现任务调度：启动类加 @EnableScheduling，任务方法上用 @Scheduled(cron = ...) 定义执行周期。

定时任务逻辑：

  1. 周期性（示例每 30 秒）扫描创建超过指定时长（示例 5 分钟）、且仍未支付的订单；
  2. 按订单号调用查单接口核实状态；
  3. 已支付：补更新本地订单状态为成功，并记录支付日志；
  4. 未支付：调用关单接口关闭订单，并把本地订单状态置为已关闭。

查询超时订单的条件：用 Instant.now().minus(Duration.ofMinutes(minutes)) 得到时间下界，按 order_status = 未支付 且 create_time <= 下界时间 过滤。

八、退款与退款核实

8.1 申请退款

退款流程：

  1. 根据订单号查询订单信息；
  2. 创建本地退款单（订单号、退款单号、原订单金额、退款金额、退款原因）；
  3. 组装退款请求参数（out_trade_no、out_refund_no、reason、notify_url、amount 中的 refund 退款金额、total 原订单金额、currency 币种）调用退款 API；
  4. 更新订单为退款处理中（OrderStatus.REFUND_PROCESSING），并更新退款单状态。退款业务建议加事务（@Transactional(rollbackFor = Exception.class)），异常时回滚。

8.2 查询退款与定时核实

  • 提供按退款单号查询退款状态的接口；
  • 定时任务扫描申请超过指定时长、仍处于退款中（WxRefundStatus.PROCESSING）的退款单，主动调用微信退款查询接口核实；
  • 核实退款成功（SUCCESS）：更新订单为退款成功（REFUND_SUCCESS），并更新退款单；
  • 核实退款异常（ABNORMAL）：更新订单为退款异常（REFUND_ABNORMAL），并更新退款单。

8.3 退款结果通知

微信退款状态改变后会向商户推送退款结果通知。处理方式与支付通知一致：先验签，再 AES-GCM 解密报文，更新对应订单与退款单状态；同样需要保证幂等，必要时加锁。

九、账单下载

微信支付提供交易账单（tradebill）和资金账单（fundflowbill）两类：

  1. 调用申请账单接口，传入账单日期 bill_date 与类型，获取 download_url；
  2. 下载账单使用无签名客户端请求该地址，拿到账单文件内容。

十、APIv2 与 APIv3 对比

V2 和 V3 是基于两套接口标准设计的接口，目前大部分接口已升级到 V3。主要差异：

对比项 V3 V2
参数格式 JSON XML
提交方式 POST、GET、PUT、PATCH、DELETE POST
回调加密 AES-256-GCM 加密 无需加密
敏感信息加密 RSA 加密 RSA 加密
编码方式 UTF-8 UTF-8
签名方式 非对称密钥 SHA256-RSA MD5 或 HMAC-SHA256

10.1 V2 统一下单要点

V2 仍以 XML 作为报文格式，流程为：组装参数（appid、mch_id、nonce_str 随机串、body、out_trade_no、total_fee、spbill_create_ip、notify_url、trade_type=NATIVE）→ 用商户 APIv2 密钥生成带签名的 XML → 以 HTTPS POST 发送到统一下单接口 → 把 XML 响应转为 Map 做通信/业务错误判断 → 取出 code_url 保存并返回二维码。

10.2 V2 回调要点

V2 回调先通过 WXPayUtil.isSignatureValid 验签，再解析 XML；除判断通信与业务成功外，还要校验回调金额与商户侧订单金额一致；通过后再加锁、按幂等规则更新订单状态并记录支付日志，最终返回 XML 格式的成功应答。

十一、关键要点小结

  • 安全职责分清：商户私钥用于签名，平台证书公钥用于验签；公钥加密用于加密信息，私钥加密用于身份认证。
  • 回调必须幂等：微信会重复推送通知，处理前先查订单状态，已处理直接返回成功。
  • 并发要加锁：状态更新与日志记录前后用锁控制，避免重入导致数据错乱。
  • 金额单位与一致性：金额一律以分为单位；回调时要校验返回金额与本地订单金额一致，防止金额篡改。
  • 主动查单兜底：异步通知可能丢失或超时，定时任务要主动查单核实，完成补单或关单；退款同样需要定时核实退款状态。
  • 密钥与证书不落地：商户号、密钥、私钥、证书属于敏感信息，不能提交到公开仓库或写进博客正文。
