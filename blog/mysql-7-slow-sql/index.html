慢 SQL 优化实战：定位排查、EXPLAIN 诊断、索引失效与 SQL 改写

2026年11月28日 · 约 6 分钟 · 1885 字 #MySQL#数据库#慢SQL#性能优化#索引#MyBatis

这一篇从排查到根治梳理慢 SQL 优化：先定位真凶，再用 EXPLAIN 照X光，然后从索引、SQL 写法、代码层、表结构与架构逐层优化。SQL、配置与命令为通用示例。

一、多慢才算慢

慢是相对的，取决于业务场景：

  • 用户操作类接口：超过 200ms，用户就能感受到卡顿；
  • 后台报表查询：超过 5 秒，可以考虑优化；
  • 批量数据处理：超过 30 秒，可能影响其他业务。

MySQL 默认把超过 10 秒的 SQL 记入慢查询日志，实际项目中通常把阈值调到 1~2 秒。

慢 SQL 不是绝对的”慢”，而是”不符合业务预期的慢”。统计报表跑 30 秒可能正常，但登录接口查用户表超过 200ms 就该优化。

二、抓住真凶：定位慢 SQL

2.1 慢查询日志：监控摄像头

-- 确认是否开启
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启（开发/测试环境建议常开）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;

拿到日志后用 mysqldumpslow 汇总分析：

# 按查询时间排序，显示前 10 条
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按出现次数排序
mysqldumpslow -s c -t 10 /var/log/mysql/slow.log

输出示例：

Count: 327  Time=5.23s (1710s)  Lock=0.00s (0s)  Rows=50000.0 (16350000)
SELECT * FROM orders WHERE status='PENDING' ORDER BY create_time DESC

327 次执行、平均 5.23 秒、扫描 1635 万行——必须优化。

生产环境不要长期开启慢查询日志，会产生大量磁盘 IO；建议只在问题排查时短暂开启，或使用采样记录。

2.2 当场抓现行

SHOW FULL PROCESSLIST;

重点关注 Time 值很大、State 为 Sending data、Creating sort index、Copying to tmp table 的连接。

2.3 Java 开发者排障工具

工具 用途 一句话
Druid 连接池 SQL 监控面板 阿里出品，内置 Web 监控，慢 SQL 一览无余
Arthas 在线诊断 不重启应用，直接 trace 方法级 SQL 耗时
pt-query-digest 慢日志分析 Percona 出品，生成详细分析报告

三、EXPLAIN：给 SQL 照X光

抓到慢 SQL 后，EXPLAIN 是诊断核心武器：

EXPLAIN SELECT * FROM orders WHERE user_id = 10086;

重点关注三列：

列名 含义 为什么重要
type 访问类型 决定查询方式，从优到劣
rows 预估扫描行数 越大越慢
Extra 额外信息 是否用了临时表、文件排序

3.1 type 访问类型（从快到慢）

type 值 说明 示例
const 主键或唯一索引查一条 WHERE id = 1
eq_ref JOIN 时唯一匹配 JOIN ON 主键
ref 非唯一索引查多行 WHERE name = '张三'
range 索引范围扫描 WHERE id > 10
ALL 全表扫描 没走索引，性能灾难

让 type 至少达到 range，最好 ref 及以上；看到 ALL 立刻警惕——除非表很小，否则就是定时炸弹。

3.2 Extra 列：藏着的关键信息

Extra 信息 含义 好坏
Using index 覆盖索引，不需回表 优秀
Using index condition 索引下推 良好
Using temporary 用了临时表 需要优化
Using filesort 文件排序 需要优化

Using temporary 和 Using filesort 是慢 SQL 的头号元凶，看到就要打起精神。

四、索引：慢 SQL 的第一解药

4.1 索引大白话

索引就像书的目录：查”第 5 章”翻目录找页码直接跳过去，而不是从第 1 页逐页翻。

4.2 联合索引与最左前缀原则

建了联合索引 idx_a_b_c (a, b, c)：

-- 能走索引
SELECT * FROM t WHERE a = 1;                    -- ✅
SELECT * FROM t WHERE a = 1 AND b = 2;          -- ✅
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3; -- ✅

-- 不能走索引
SELECT * FROM t WHERE b = 2; -- ❌ 不满足最左前缀
SELECT * FROM t WHERE c = 3; -- ❌ 不满足最左前缀

联合索引像多层楼梯：必须从第一级台阶（最左列）开始走，不能直接从中间爬。

建索引口诀：区分度高的放前面，查询频率高的放前面，= 条件在 >/< 条件前面。

4.3 索引失效的六大经典场景

明明建了索引却不走，问题通常出在 SQL 写法上：

序号 场景 错误示例 正确写法
1 对索引列做函数操作 WHERE DATE(create_time) = '2026-01-01' WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02'
2 隐式类型转换 WHERE phone = 13800138000（phone 是 varchar） WHERE phone = '13800138000'
3 LIKE 以 % 开头 WHERE name LIKE '%张三' 避免左模糊，或改用 ES
4 OR 连接非索引列 WHERE a = 1 OR b = 2（b 无索引） 给 b 加索引，或拆成 UNION
5 联合索引不满足最左前缀 WHERE b = 1 AND c = 2（索引是 (a,b,c)） 调整 WHERE 条件顺序
6 范围查询右边列失效 WHERE a=1 AND b>10 AND c=3（索引 (a,b,c)） c 的条件放应用层过滤

隐式类型转换最容易在生产暴雷：自测用数字传进去一看走索引；上线后用户填了奇怪字符串，MySQL 悄悄做类型转换，索引直接失效。

五、SQL 改写技巧：好 SQL 是改出来的

5.1 告别 SELECT *

-- 低效：无法用覆盖索引，网络传输浪费
SELECT * FROM orders WHERE user_id = 10086;

-- 优雅：只取需要的列
SELECT id, order_no, amount, status FROM orders WHERE user_id = 10086;

一天 100 万次请求，每次多传 1KB，一天就是 1GB 额外流量。

5.2 深分页优化

-- 经典慢 SQL：先取 100020 条，再丢弃前 100000 条
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 游标分页：直接用上一页最后一条的 id
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;

5.3 避免在 WHERE 里做函数运算

-- 错误：索引列套函数
WHERE DATE(create_time) = '2026-07-23'
WHERE LEFT(name, 3) = 'abc'

-- 正确：把函数移到等号右边
WHERE create_time >= '2026-07-23' AND create_time < '2026-07-24'
WHERE name LIKE 'abc%'

阿里巴巴开发手册强制规范：严禁在 WHERE 条件中对索引列使用函数或运算。

5.4 IN vs EXISTS vs JOIN

简单记忆：内表大用 EXISTS，内表小用 IN；大部分情况下 JOIN 比子查询快，因为优化器对 JOIN 的优化手段更多。

-- 子查询（差）
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE vip_level = 3);

-- JOIN（好）
SELECT o.*
FROM orders o
INNER JOIN users u ON o.user_id = u.id
WHERE u.vip_level = 3;

六、Java/MyBatis 视角：代码层面的慢 SQL

6.1 MyBatis 三大元凶

元凶一：N+1 查询

<!-- 每条 order 都会触发一次额外查询；100 条订单 = 1 + 100 = 101 次查询 -->
<collection property="items"
            select="com.example.dao.OrderItemMapper.selectByOrderId"
            column="id" />

解决方案：改用 JOIN 一次查出，或用 MyBatis-Plus 的批量填充。

元凶二：foreach 拼接超大 IN 列表

ids 有几千个元素时，SQL 解析本身就耗时巨大。建议分批查询，每批不超过 500 个。

元凶三：动态 SQL 的意外索引失效

<if test="keyword != null and keyword != ''">
  AND name LIKE CONCAT('%', #{keyword}, '%') <!-- 左模糊，索引失效！ -->
</if>

6.2 Druid + Arthas：排障黄金搭档

spring:
  datasource:
    druid:
      stat-view-servlet:
        enabled: true
        url-pattern: /druid/*
      filter:
        stat:
          enabled: true
          slow-sql-millis: 1000 # 超过 1 秒的 SQL 标记为慢 SQL

启动后访问 http://localhost:8080/druid/sql.html，实时查看 SQL 执行次数、平均耗时、最大耗时。

# Arthas 在线追踪，不重启应用
trace com.example.dao.OrderMapper selectByUserId '#cost > 100'

SQL 日志发现问题、Druid 持续追踪、Arthas 精准定位——三件套搭配，慢 SQL 无所遁形。

七、实战案例：三个经典优化全过程

案例一：分页查询 8 秒 → 15 毫秒

-- 原始 SQL：type=ALL，rows=200 万
SELECT * FROM order_detail
WHERE status = 'PAID'
ORDER BY create_time DESC
LIMIT 500000, 20;

-- 优化：建索引 + 游标分页
ALTER TABLE order_detail ADD INDEX idx_status_time (status, create_time);
SELECT * FROM order_detail
WHERE status = 'PAID' AND id > 500123
ORDER BY id LIMIT 20;

效果：8 秒 → 15 毫秒，提升约 500 倍。

案例二：JOIN 查询 3 秒 → 30 毫秒

诊断：orders.create_time 未建索引，三表关联产生大量中间结果，Extra = Using temporary; Using filesort。

ALTER TABLE orders ADD INDEX idx_create_time (create_time);
ALTER TABLE order_items ADD INDEX idx_order_id (order_id);

效果：3 秒 → 30 毫秒。

案例三：统计 SQL 30 秒 → 200 毫秒

-- 原始 SQL：DATE(create_time) 对索引列做了函数操作
SELECT DATE(create_time) AS dt, COUNT(*), SUM(amount)
FROM orders
WHERE create_time > '2025-01-01'
GROUP BY DATE(create_time);

-- 优化：加计算列 + 索引
ALTER TABLE orders ADD COLUMN order_date DATE
  GENERATED ALWAYS AS (DATE(create_time)) STORED;
ALTER TABLE orders ADD INDEX idx_order_date_amount (order_date, amount);

SELECT order_date, COUNT(*), SUM(amount)
FROM orders
WHERE order_date > '2025-01-01'
GROUP BY order_date;

效果：30 秒 → 200 毫秒。

数据量特别大（几千万行以上）时，可考虑建汇总表：每天凌晨定时任务把前一天数据汇总好，业务查询直接查汇总表，毫秒级响应。

八、优化思维框架

按投入产出比排序的优化优先级：

  1. 加索引 / 修正索引（ROI 最高，5 分钟可能提升 100 倍）；
  2. 改写 SQL（避免 SELECT *、优化分页、修正左模糊）；
  3. 优化表结构（选对字段类型、适当冗余）；
  4. 调整数据库参数（buffer pool、连接数）；
  5. 架构层面兜底（读写分离、分库分表、引入缓存）。

九、慢 SQL 排查清单

步骤 做什么 用什么工具
1 确认有没有慢 SQL 慢查询日志 / Druid 监控 / SHOW PROCESSLIST
2 分析执行计划 EXPLAIN / EXPLAIN ANALYZE
3 检查索引使用情况 EXPLAIN 的 type、key、Extra 列
4 判断是否索引失效 对照六大索引失效场景逐一排查
5 检查 SQL 写法 SELECT * / 深分页 / 子查询 / 函数运算
6 检查 Java 层面 MyBatis 日志 / Arthas trace / Druid 监控
7 检查表结构与参数 字段类型 / 冗余设计 / buffer_pool_size
8 验证优化效果 再次 EXPLAIN + 实际执行计时

十、小结

慢 SQL 优化的核心是一套”排查肌肉记忆”：先用日志和监控定位，再用 EXPLAIN 判断执行计划，先榨干索引与 SQL 写法，最后才动表结构、参数和架构。

三句最关键的认知：

  1. 先定位再动手：慢查询日志、PROCESSLIST、Druid、Arthas 各管一段，避免凭感觉改 SQL；
  2. 索引是第一解药，但最容易失效：遵守最左前缀，避开函数运算、隐式转换、左模糊、OR 非索引列与范围右边列；
  3. 改写 SQL 收益高：去掉 SELECT *、深分页游标化、JOIN 替代子查询，能用覆盖索引就不回表。

备注：本篇为个人学习整理，内容基于公开学习资料归纳；阈值、分批大小与汇总表策略需结合实际业务量和压测结果调整。
