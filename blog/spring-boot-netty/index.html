一、技术选型与版本基线

1.1 版本矩阵

组件 选型 说明
JDK 17 Spring Boot 3.x 基线
Spring Boot 3.5.16 3.5 系列版本
Netty 4.2.21.Final 4.2 稳定维护版本（Stable / Recommended）
协议 TCP + 自定义长度帧 4 字节大端序长度字段 + UTF-8 消息体
I/O 模型 NIO Netty 4.2 推荐的 MultiThreadIoEventLoopGroup + NioIoHandler
构建工具 Maven 3.6.3+ 通过 netty-bom 统一管理 Netty 模块版本

1.2 为什么选 Netty 4.2 而不是 4.1

Netty 官方已将 4.2 列为 Stable / Recommended，并宣布 4.1 将于 2027-07-01 结束维护。新项目优先选 4.2；现有组件被 4.1 锁定时，升级前必须先检查依赖树和兼容性。注意：4.1 和 4.2 不能同时出现在同一个运行时 classpath 中。

1.3 Netty 是什么、与 Spring Boot 怎么分工

Netty 是基于 Java NIO 的异步事件驱动网络应用框架，封装了底层 Socket、Selector、线程调度、缓冲区、编解码和连接管理等细节。常见场景：TCP 长连接服务（设备接入、游戏网关、即时通信、服务端推送）、物联网平台、自定义二进制协议、代理网关与高并发客户端。

组件 主要职责
Spring Boot 启动应用、加载配置、管理 Bean、提供依赖注入与关闭回调
Netty 监听 TCP 端口、接收连接、处理读写事件、编解码和维护 Channel
Spring MVC（可选） 提供 HTTP 管理接口，如健康检查、统计信息
业务服务层 执行业务校验、数据库访问、缓存读写和消息投递

一个关键认知：本项目的 TCP 端口和 HTTP 端口相互独立——Netty TCP 监听 9000，Spring MVC HTTP 监听 8080。引入 spring-boot-starter-web 不代表 Netty TCP 服务运行在 Tomcat 上，两者是同一 JVM 里两个互不相干的网络服务。

2.2 application.yml 与配置属性

netty:
  server:
    host: 0.0.0.0          # 监听所有 IPv4 网卡
    port: 9000
    backlog: 1024

参数说明：host 控制监听网卡（0.0.0.0 表示所有 IPv4 网卡）；port 是 TCP 监听端口；backlog 是待处理连接队列提示值；max-frame-length 限制单帧最大字节数；reader-idle-seconds 是读空闲超时秒数。

三、设计 TCP 消息协议

3.1 为什么需要自定义消息边界

TCP 是面向连接的字节流协议，不保留应用层一次 write 对应一次 read 的消息边界。一次业务消息可能被拆成多次接收；多次业务消息也可能合并在一次接收中——这就是粘包和拆包。应用层必须自行定义消息边界。

3.2 帧格式

字段 长度 说明
Length 4 字节 大端序整数，表示后续消息体字节数，不含长度字段本身
Body 0 至 N 字节 UTF-8 编码的业务消息体

一个高频出错点：长度单位是字节，不是 Java String.length() 的字符数。中文字符通常占用多个 UTF-8 字节，必须由编码后的字节长度计算帧长度，这也是中文乱码和截断问题的根源。

3.3 常见消息边界方案对比

方案 示例 优缺点
固定长度 每帧固定 128 字节 解析简单，但可能浪费带宽
分隔符 消息以换行符结束 文本协议易读，但要处理转义和分隔符注入
长度字段 4 字节长度 + 消息体 边界明确，适合二进制/文本消息，需限制最大帧长
自定义协议头 魔数+版本+类型+长度+内容+校验 扩展能力强，但协议设计和维护复杂

四、编解码与业务处理器

4.1 ChannelInitializer

ChannelInitializer 在每条客户端连接建立时，为该连接配置独立的 ChannelPipeline：

public class TcpChannelInitializer extends ChannelInitializer<SocketChannel> {

    @Override
    protected void initChannel(SocketChannel ch) {
        ChannelPipeline pipeline = ch.pipeline();
        // 入站：按长度字段切帧，参数 (maxFrameLength, lengthFieldOffset,
        // lengthFieldLength, lengthAdjustment, initialBytesToStrip)
        pipeline.addLast(new LengthFieldBasedFrameDecoder(1048576, 0, 4, 0, 4));
        // 出站：自动在消息前补 4 字节长度
        pipeline.addLast(new LengthFieldPrepender(4));
        pipeline.addLast(new TcpMessageHandler());
    }
}

两个参数细节：

  1. LengthFieldBasedFrameDecoder(maxFrameLength, lengthFieldOffset, lengthFieldLength, lengthAdjustment, initialBytesToStrip)：本例传 (1MiB, 0, 4, 0, 4)——长度字段在帧首、占 4 字节、长度值不含头本身、解码后剥掉 4 字节长度头。maxFrameLength 包含长度字段本身，因此消息体最大可用长度为 1 MiB - 4 字节；
  2. 出站用 LengthFieldPrepender(4) 自动补长度，客户端和服务端参数必须完全一致。

4.2 业务 Handler

@Sharable
@Slf4j
public class TcpMessageHandler extends SimpleChannelInboundHandler<String> {

    @Override
    protected void channelRead0(ChannelHandlerContext ctx, String msg) {
        if ("PING".equals(msg)) {
            ctx.writeAndFlush("PONG");
        } else {
            ctx.writeAndFlush("ECHO: " + msg);
        }
    }

    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
        if (evt instanceof IdleStateEvent event) {
            if (event.state() == IdleState.READER_IDLE) {
                log.info("读空闲，关闭连接：{}", ctx.channel().remoteAddress());
                ctx.close();
            }
        }
    }
}

三个设计说明：

  1. @Sharable 的前提：Handler 是 Spring 单例，被所有客户端 Channel 复用，只有 Handler 不保存连接级可变状态时才能这样用；若需要保存每连接状态，应为每条 Channel 创建独立实例，或把状态放进 Channel Attribute；
  2. userEventTriggered 处理空闲事件：IdleStateHandler 只负责「发事件」，关不关连接是业务 Handler 的决定。60 秒没收到任何数据就判定对端失效，主动关闭；
  3. 真实业务扩展点：在 channelRead0 里解析命令、设备编号、消息类型和业务载荷，再调用 Service 层；PING/PONG 只是心跳的最小实现。

五、将 Netty 服务端交给 Spring Boot 管理

5.1 为什么要管理 Netty 生命周期

Netty 会创建 EventLoop 线程组和监听 Channel。如果只在 main 方法里随意启动，Spring 容器关闭时可能留下非守护线程或未关闭的端口。正确做法是把 Netty 的启动、停止与 Spring ApplicationContext 生命周期关联——这正是 SmartLifecycle 的用途：容器启动完成阶段自动调用 start()，应用关闭时调用 stop()。

5.2 NettyTcpServer 实现

Netty 4.2 API 变化：NioEventLoopGroup 在 4.2 中已标记弃用，推荐 MultiThreadIoEventLoopGroup + NioIoHandler.newFactory()。网上大量 4.1 教程的写法在 4.2 下能编译但会有弃用警告，新代码应按本例编写。

@Slf4j
@Component
@RequiredArgsConstructor
public class NettyTcpServer implements SmartLifecycle {

    private final NettyServerProperties properties;
    private EventLoopGroup bossGroup;
    private EventLoopGroup workerGroup;
    private Channel serverChannel;

    @Override
    public void start() {
        bossGroup = new MultiThreadIoEventLoopGroup(1, NioIoHandler.newFactory());
        workerGroup = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());

        ServerBootstrap bootstrap = new ServerBootstrap()
                .group(bossGroup, workerGroup)
                .channel(NioServerSocketChannel.class)
                .childHandler(new TcpChannelInitializer());

        serverChannel = bootstrap.bind(properties.getHost(), properties.getPort()).sync().channel();
        log.info("Netty TCP 服务端启动：{}:{}", properties.getHost(), properties.getPort());
    }

    @Override
    public void stop() {
        if (serverChannel != null) {
            serverChannel.close();
        }
        if (bossGroup != null) {
            bossGroup.shutdownGracefully();
        }
        if (workerGroup != null) {
            workerGroup.shutdownGracefully();
        }
    }

    @Override
    public boolean isRunning() {
        return serverChannel != null && serverChannel.isActive();
    }
}

启动类无需任何额外注解。可选地再加一个 HTTP 管理接口，返回服务运行状态，与 TCP 业务端口相互独立。

6.2 粘包场景验证

粘包测试用原生 Socket 把「第一条」「第二条」两帧拼在一次 write 中发出——这正是 TCP 字节流的真实行为。LengthFieldBasedFrameDecoder 依长度字段正确切出两条消息并依次响应，是协议设计正确性的最直接证据。应用停止后 8080/9000 端口均释放，无残留 Netty 线程，即 SmartLifecycle 生效。

七、Netty 核心线程模型

7.1 Boss 与 Worker

线程组 职责 本教程配置
Boss Group 监听服务端端口、接收新连接，并将连接注册到 Worker 1 个 I/O 线程
Worker Group 处理已建立连接上的读写事件及 Pipeline 回调 使用 Netty 默认线程数

Channel 注册到某个 EventLoop 后，通常由该 EventLoop 串行执行这个 Channel 的 I/O 事件和任务，避免同一 Channel 的多线程并发访问——这是 Netty 高性能且大部分 Handler 无需加锁的基础。

7.2 不能在 Handler 中执行阻塞操作

如果在 I/O 线程里直接执行慢 SQL、同步 HTTP 调用或 Thread.sleep，会阻塞同一 EventLoop 上的所有 Channel，造成整体吞吐下降。阻塞任务应迁移到有界业务线程池：配置合理的核心线程数、最大线程数、有界队列和拒绝策略；若异步传递的是 ByteBuf 等引用计数对象，必须正确 retain/release（本例传 String 不涉及）。

八、粘包与拆包

类型 说明
粘包 多个完整业务报文连续到达，底层一次读取可能同时包含多个报文
拆包 一个完整业务报文被底层拆成多次读取
半包 当前读取只包含一帧的一部分，需等待后续字节

TCP 提供可靠、有序的字节流，但不承诺应用层消息边界。操作系统缓冲、网络分段、发送时机都会影响一次 read 获取的字节数。粘包/拆包不是 TCP 故障，而是应用层协议必须处理的问题。Netty 对应解码器：

解码器 适用协议
FixedLengthFrameDecoder 每条报文长度固定
DelimiterBasedFrameDecoder 按换行符、特殊分隔符等切帧
LineBasedFrameDecoder 按行结束符切分文本
LengthFieldBasedFrameDecoder 报文头含长度字段，适用范围最广

必须同时约定：长度字段的字节数、偏移量、长度值覆盖范围（是否含报头）、字节序。客户端和服务端协议必须完全一致，任何一项对不上都会表现为「连上了但没响应」或「消息被截断」。

九、心跳检测与连接管理

TCP 连接可能因网络中断、设备断电、NAT 超时变成「僵尸连接」，仅靠连接建立时的成功状态无法保证连接长期可用。IdleStateHandler 三个参数：

参数 含义 示例
readerIdleTime 指定时间内没有读到数据 60 秒无入站数据触发 READER_IDLE
writerIdleTime 指定时间内没有写出数据 可用于检测是否需要发送心跳
allIdleTime 指定时间内没有读写数据 双向无活动时触发 ALL_IDLE

设备接入平台的实际心跳管理流程：

  1. 连接建立时，记录 Channel、设备 ID、客户端地址和连接时间；
  2. 收到登录/注册报文后，将设备身份与 Channel 关联；
  3. 收到心跳报文时，更新最近活跃时间和在线状态；
  4. 连接关闭时，移除 Channel 映射并更新设备离线状态；
  5. 同一设备重复连接时，按业务规则处理旧连接（踢旧或多连接共存）。

注意：不要仅以 TCP Channel 存活作为设备业务在线的唯一依据，应用层心跳、设备身份认证和最近活跃时间才是物联网业务的在线判定标准。

十、常见问题排查

问题 可能原因 排查思路
启动报 Address already in use 9000 端口被占用 netstat -ano | findstr :9000 查进程；改 netty.server.port
客户端连接被拒绝 服务未启动、监听地址错误、防火墙拦截 检查启动日志、监听地址、系统防火墙和安全组
连上但没有响应 帧格式不正确、Handler 未加入 Pipeline 核对长度字段、字节序、Pipeline 顺序

十一、Netty 4.1 与 4.2 版本注意

对比项 Netty 4.1 Netty 4.2
官方状态 2027-07-01 EOL Stable / Recommended
事件循环创建 NioEventLoopGroup（已弃用） MultiThreadIoEventLoopGroup + NioIoHandler.newFactory()
TLS 主机名校验 旧默认不自动开启 客户端默认启用，需显式理解配置行为
内存分配器 默认 pooled 默认 adaptive

迁移建议：先将系统升级到最新 4.1 修复版本并消除已知问题，再检查所有依赖统一使用 4.2，重点验证客户端 TLS 主机名校验和内存分配器行为变化。4.1 和 4.2 不应同时出现在同一个 classpath。 本项目直接按 4.2 编写，使用新的 EventLoopGroup API；旧项目用 4.1 时，事件循环创建方式需按对应版本调整。

十二、小结

本项目完成了 Spring Boot 3.x 整合 Netty 的完整闭环：TCP 服务端随容器启停（SmartLifecycle）、长度帧协议解决粘包拆包（LengthFieldBasedFrameDecoder / LengthFieldPrepender）、心跳检测清理失效连接（IdleStateHandler）、HTTP 管理接口独立于 TCP 业务端口。三个最值得记住的点：

  1. TCP 是字节流，消息边界是应用层自己定的——长度字段协议 + 两端参数完全一致，是「连上没响应」问题的解药；
  2. Netty 生命周期必须交给 Spring 管理——否则关闭应用时留下非守护线程和占用端口；
  3. 4.1 与 4.2 不共存——netty-bom 统一版本，依赖树定期检查。
