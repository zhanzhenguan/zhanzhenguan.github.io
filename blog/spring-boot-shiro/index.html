这篇是 Spring Boot 系列第十四部分，用 Shiro 搭建一套登录认证与权限控制体系。Shiro 是轻量级 Java 安全框架，认证、授权、会话管理、加密一体。技术栈：Spring Boot 3.5.16、Shiro 2.2.1、Java 17、MyBatis 3.0.5、MySQL 8.0。代码为通用示例，连接信息与密码用占位符。

一、最大的坑：Spring Boot 3 的 Jakarta 适配

Spring Boot 3 基线从 Java EE 换成 Jakarta EE，所有 javax.servlet.* 包名变成 jakarta.servlet.*。Shiro 又是重度依赖 Servlet API 的框架，由此引出本次整合最隐蔽的三个坑：

  • 坑一：Shiro 1.x 在 Spring Boot 3 下完全跑不起来。 1.x 只支持 javax.servlet，启动直接报 ClassNotFoundException: javax.servlet.Filter，必须用 Shiro 2.x；
  • 坑二：Shiro 2.x 的主包默认还是 javax 版本。 2.x 虽支持 Jakarta，但以 jakarta classifier（分类器）的形式另外发布；直接引入不带 classifier 的 2.x 依赖，等于还是引了 javax 版本，报错和 1.x 一模一样；
  • 坑三：Maven classifier 不会随传递依赖传导。 即使给 shiro-spring-boot-web-starter 加了 <classifier>jakarta</classifier>，它传递依赖进来的 shiro-spring、shiro-web 仍然是 javax 版本，照样启动失败。

正确姿势：整条 Shiro 依赖链全部显式声明 jakarta classifier，并把 javax 版传递依赖逐个排除。

另外一个小坑：Shiro starter 自带 spring-boot-starter-log4j2，与 Spring Boot 默认的 logback 冲突，要一并排除。

四、数据库与密码加密方案

user 表不存明文密码。设计取舍：数据库一旦泄露，明文密码全裸奔；这里采用 Shiro 标准加密方案——MD5 加密 1024 次后的密文，配合 HashedCredentialsMatcher，用户提交明文后由 Shiro 自动加密比对，数据库里永远只有密文。

通用 DDL：

CREATE TABLE user (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(64) NOT NULL UNIQUE,
    password VARCHAR(128) NOT NULL,
    nickname VARCHAR(64)
);

密文用 new Md5Hash("明文", null, 1024).toHex() 真实生成，不要手抄来路不明的密文；换密码先跑一行代码生成新密文。示例账号 mumu / mhxy1218。

5.2 全局异常处理

访问没有权限的接口时，把 Shiro 抛出的授权异常转成统一的 403 JSON 响应，前端拿到的不再是报错页：

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UnauthorizedException.class)
    public JsonResult handleUnauthorized(UnauthorizedException e) {
        return JsonResult.fail(403, "没有权限访问该接口");
    }

    @ExceptionHandler(AuthenticationException.class)
    public JsonResult handleAuthentication(AuthenticationException e) {
        return JsonResult.fail(401, "用户名或密码错误");
    }
}

注意：perms 过滤器的权限校验发生在 Filter 层，抛出的 UnauthorizedException 根本到不了 @RestControllerAdvice，全局异常处理器拦不住。这部分要靠 ShiroConfig 里的 unauthorizedUrl 兜底（见第八节）。

七、UsernameRealm

Realm 是 Shiro 连接业务数据的桥梁：认证时从数据库加载用户，授权时提供权限列表。

两个关键点：

  1. HashedCredentialsMatcher 在构造器中配置，告诉 Shiro 数据库存的是 MD5 加密 1024 次的密文；登录时 Shiro 自动把提交的明文按同样规则加密，再与数据库密文比对，业务代码完全不碰加密逻辑；
  2. SimpleAuthenticationInfo 的第三个参数是 Realm 名称，用 getName() 获取。
@Slf4j
public class UsernameRealm extends AuthorizingRealm {

    private final UserMapper userMapper;

    public UsernameRealm(UserMapper userMapper) {
        this.userMapper = userMapper;
        setCredentialsMatcher(new HashedCredentialsMatcher("MD5", 1024, null));
    }

    /** 授权：提供当前用户的权限列表 */
    @Override
    protected AuthorizationInfo doGetAuthorizationInfo(PrincipalCollection principals) {
        String username = (String) principals.getPrimaryPrincipal();
        SimpleAuthorizationInfo info = new SimpleAuthorizationInfo();
        // 实际项目按用户名查库装配权限标识
        List<String> permissions = userMapper.selectPermsByUsername(username);
        info.addStringPermissions(permissions);
        return info;
    }

    /** 认证：按用户名查库并返回封装信息 */
    @Override
    protected AuthenticationInfo doGetAuthenticationInfo(AuthenticationToken token)
            throws AuthenticationException {
        String username = (String) token.getPrincipal();
        User user = userMapper.selectByUsername(username);
        if (user == null) {
            throw new UnknownAccountException("用户不存在");
        }
        // 第三参数传 Realm 名称 getName()
        return new SimpleAuthenticationInfo(user.getUsername(), user.getPassword(), getName());
    }
}

八、Shiro 配置类

8.1 两个必须注意的点

  • Bean 方法名必须叫 shiroFilterFactoryBean。 Shiro 自动配置类按这个名字查找过滤器工厂 Bean；若像老教程一样命名为 shiroFilter，启动直接报「required a bean named ‘shiroFilterFactoryBean’」，报错信息很难和方法名联想到一起；
  • 配置 setUnauthorizedUrl("/user/unauthorized")。 如第五节所述，perms 权限异常在 Filter 层抛出，全局异常处理器拦不住；配置 unauthorizedUrl 后，无权限访问统一跳转到返回 JSON 的接口，前端响应格式一致。

8.2 配置代码

@Configuration
@RequiredArgsConstructor
public class ShiroConfig {

    private final UserMapper userMapper;

    @Bean
    public SecurityManager securityManager() {
        DefaultWebSecurityManager manager = new DefaultWebSecurityManager();
        manager.setRealm(new UsernameRealm(userMapper));
        return manager;
    }

    /** Bean 名必须是 shiroFilterFactoryBean */
    @Bean
    public ShiroFilterFactoryBean shiroFilterFactoryBean(SecurityManager securityManager) {
        ShiroFilterFactoryBean factory = new ShiroFilterFactoryBean();
        factory.setSecurityManager(securityManager);

        // 未登录访问受保护资源跳转登录页
        factory.setLoginUrl("/login.html");
        // 无权限访问跳转统一 JSON 接口
        factory.setUnauthorizedUrl("/user/unauthorized");

        Map<String, String> chain = new LinkedHashMap<>();
        chain.put("/login.html", "anon");
        chain.put("/js/**", "anon");
        chain.put("/user/login", "anon");
        chain.put("/user/unauthorized", "anon");
        // 接口级权限绑定
        chain.put("/user/delete", "perms[user:delete]");
        chain.put("/user/update", "perms[user:update]");
        // 其余请求需要认证
        chain.put("/**", "authc");
        factory.setFilterChainDefinitionMap(chain);
        return factory;
    }
}

过滤器说明：anon 匿名放行；authc 需要登录；perms[xxx] 需要对应权限标识。

九、登录认证流程

登录 DTO：

public record UserLoginDTO(String username, String password) {}

完整认证链路：

  1. 前端提交用户名密码 → UserController.login() 接收并校验参数；
  2. UserServiceImpl.login() 构造 UsernamePasswordToken，调用 subject.login(token) 发起认证；
  3. Shiro 找到 UsernameRealm，执行 doGetAuthenticationInfo() 按用户名查数据库；
  4. 用户不存在或账号锁定 → 抛异常，全局异常处理器返回 403/401；用户存在 → HashedCredentialsMatcher 把提交的明文 MD5 加密 1024 次后与数据库密文比对；
  5. 密码错误 → IncorrectCredentialsException，转成「用户名或密码错误」；比对通过 → 认证成功，Shiro 自动创建 Session 并种下 Cookie。
@Service
@RequiredArgsConstructor
public class UserServiceImpl implements UserService {

    @Override
    public void login(UserLoginDTO dto) {
        Subject subject = SecurityUtils.getSubject();
        UsernamePasswordToken token =
                new UsernamePasswordToken(dto.username(), dto.password());
        try {
            subject.login(token);
        } catch (IncorrectCredentialsException | UnknownAccountException e) {
            throw new AuthenticationException("用户名或密码错误", e);
        }
    }
}

十、授权实现与测试

授权代码在前面已就位：UsernameRealm 的 doGetAuthorizationInfo() 给当前用户分配 user:delete、user:update 两个权限；ShiroConfig 过滤器链把 /user/delete、/user/update 分别绑定到这两个权限。串联起来：登录后点击按钮 → 请求到达 perms 过滤器 → Shiro 调用 doGetAuthorizationInfo() 查权限 → 有权限放行，无权限跳转 unauthorizedUrl。

实测场景：

  • 正常访问：登录后点击「删除」「修改」按钮，分别返回成功；
  • 访问失败：把 Realm 中 user:update 权限注释掉重启再登录，点「修改」返回统一 403 JSON，「删除」仍正常——权限粒度精确到单个接口；测完记得把注释放回；
  • 未登录直接调接口：不带 Session 请求 /user/delete，302 跳转登录页，不泄露任何数据。

十一、踩坑汇总

# 坑 解决
1 版本与 classifier 必须 2.x + jakarta classifier，且整条依赖链（web-starter、spring、web）都显式声明并排除 javax 版传递依赖
2 日志冲突 starter 自带 log4j2，排除掉，统一用 logback
3 Bean 命名 过滤器工厂 Bean 必须命名为 shiroFilterFactoryBean，否则启动报找不到该 Bean
4 perms 异常拦截 权限异常发生在 Filter 层，@RestControllerAdvice 拦不到，要配 unauthorizedUrl 指向统一 JSON 接口

十二、小结

  • Spring Boot 3 整合 Shiro 的工作量几乎全在依赖适配：1.x 不能用，2.x 必须整条链挂 jakarta classifier 并排除 javax 传递依赖；
  • 认证由 Realm 完成：doGetAuthenticationInfo() 查库封装身份，HashedCredentialsMatcher 负责 MD5 1024 次加密比对，业务代码不碰加密；
  • 授权在 doGetAuthorizationInfo() 装配权限标识，perms 过滤器按标识放行；
  • 过滤器链按 anon / authc / perms 分层拦截，未登录跳登录页，无权限走 unauthorizedUrl；
  • 这套「页面 + Session 会话」方案适合传统 Web 应用；前后端分离 + Token 鉴权场景需要再扩展无状态认证方案。
