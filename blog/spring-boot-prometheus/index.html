一、目标：一套完整的指标监控闭环

很多项目的监控止步于「引入了 actuator 依赖」，以为这就是接入了 Prometheus。实际差一步关键动作：把指标以 Prometheus 认识的格式暴露出来，并让 Prometheus 来抓。

完成后会得到：

  • 一个业务流量与监控端点分离的 Spring Boot 应用（业务 8080 / 管理 8081）；
  • JVM、HTTP 请求、进程存活等自动指标，加上订单数、下单耗时、活跃任务数三个自定义业务指标；
  • Prometheus 每 15 秒抓取一次应用指标并写入本地时序数据库；
  • Grafana 连接 Prometheus，用 PromQL 查询并展示图表。

二、版本基线

组件 版本 为什么
JDK 17 LTS，Spring Boot 3.x 的最低要求线
Spring Boot 3.5.16 3.5.x 线最终 OSS 版本，Web + Actuator 由 parent 统一管版本
micrometer-registry-prometheus 由 Boot BOM 托管 不要手写版本号，Boot 3.5.16 锁定 Micrometer 1.15 系
Prometheus 3.16.0 本机运行，/api/v1/status/buildinfo 实测确认
Grafana 13.3.1 本机运行，/api/health 实测确认

一个容易忽视的事实：Actuator ≠ 监控接入。Actuator 只提供端点壳子；Micrometer 负责记录指标；micrometer-registry-prometheus 负责把指标翻译成 Prometheus 文本格式。三者缺一，/actuator/prometheus 就不会出现或没有内容。

三、创建工程与依赖

依赖只有三个：web、actuator、prometheus registry，都不写版本号，交给 parent：

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-registry-prometheus</artifactId>
    </dependency>
</dependencies>

四、核心配置：业务端口与管理端口分离

4.1 application.yml

server:
  port: 8080

management:
  server:
    port: 8081
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  endpoint:
    health:
      show-details: never
  metrics:
    tags:
      application: prometheus-demo
  observations:
    http:
      server:
        percentiles-histogram: true

info:
  app:
    name: prometheus-demo
    version: 1.0.0

4.2 关键配置逐项说明

配置项 作用 本机实测效果
management.server.port: 8081 管理端点独立端口 8080 上访问 /actuator/health 返回 404，端口隔离生效
exposure.include 只暴露这 4 个端点 8081 上访问 /actuator/env 返回 404
metrics.tags.application 全局公共标签 所有指标带 application="prometheus-demo"
percentiles-histogram.http.server.requests HTTP 请求直方图 出现 http_server_requests_seconds_bucket 序列
show-details: never 健康详情不展示 health 只返回总体状态

端口分离是生产标配：业务口对外服务，管理口只对监控网络开放。如果两个口共用 8080，就得在安全策略上对业务流量和抓取流量做区分，麻烦且容易出漏洞。

4.3 坑：info 端点默认为空

第一轮验证发现 /actuator/info 返回 {}，info.app.* 配置一个都没出来。根因：Boot 3.5 里 env 型 info 贡献者的条件注解是 @ConditionalOnEnabledInfoContributor(value = "env", fallback = DISABLE)——默认关闭，和 build/git 贡献者的默认开启不一样。

解法是显式打开：

management:
  info:
    env:
      enabled: true

加上之后 info 端点立刻返回 {"app":{"name":"prometheus-demo","version":"1.0.0",...}}。很多「配置了 info 不生效」的问题都卡在这一处。

五、自定义业务指标：Counter / Timer / Gauge

5.1 三类指标怎么选

类型 语义 本项目用法
Counter 只增不减的累计值 订单创建总数（重启归零是正常的，Prometheus 用 rate() 处理）
Timer 次数 + 耗时分布 下单接口的业务耗时，含直方图桶，可算 P95
Gauge 某一时刻的瞬时值 当前活跃任务数

选型铁律：Counter 不要拿来表示「当前数量」（它不能减）；Gauge 不要拿来统计事件次数（重启会丢历史）；Timer 想算分位数就必须开直方图。

5.2 指标埋点实现

@RestController
@RequestMapping("/api/demo")
@RequiredArgsConstructor
public class DemoController {

    private final MeterRegistry meterRegistry;
    private final AtomicInteger activeTasks = new AtomicInteger();

    @PostMapping("/orders")
    public OrderResponse createOrder() {
        // Timer 包住业务方法，记录业务耗时；接口总耗时另有 http_server_requests 自动指标
        Timer.Sample sample = Timer.start(meterRegistry);
        try {
            OrderResponse response = orderRepository.save();
            meterRegistry.counter("demo.orders.created").increment(); // 成功后才递增
            return response;
        } finally {
            sample.stop(Timer.builder("demo.orders.create.duration")
                    .publishPercentileHistogram().register(meterRegistry));
        }
    }

    @PostMapping("/tasks/finish")
    public void finishTask() {
        activeTasks.updateAndGet(current -> Math.max(0, current - 1)); // 下限保护，不为负
    }

    @GetMapping("/tasks")
    public Map<String, Object> activeTasks() {
        Gauge.builder("demo.tasks.active", activeTasks, AtomicInteger::get)
                .register(meterRegistry);
        return Map.of("active", activeTasks.get());
    }
}

几个值得注意的细节：

  • Counter 在业务成功后递增，失败路径不计数，这样「订单创建成功率」才有正确的分母口径；
  • Gauge 的被观测对象用字段强引用持有。Gauge 持有的是弱引用，如果被观测对象被 GC，Gauge 会变成 NaN——这是官方文档明说、又极容易被忽略的坑；
  • 任务数用 updateAndGet 做下限保护，连续 finish 不会出现负数。

5.3 指标命名转换（实测）

Micrometer 用点号风格注册指标，Prometheus Registry 输出时会做命名规范化。注册名 ≠ 输出名，这是新手写 PromQL 时最常见的翻车点。

Micrometer 注册名 Prometheus 实际输出序列 说明
demo.orders.created demo_orders_total Counter 加 _total 后缀；.created 段被收敛
demo.orders.create.duration demo_orders_create_duration_seconds_count / _sum / _bucket / _max Timer 转成秒单位的直方图族
demo.tasks.active demo_tasks_active Gauge 直译
http.server.requests http_server_requests_seconds_* 自动 HTTP 指标同样转秒

注意 demo.orders.created 的输出是 demo_orders_total，而不是直觉拼出来的 demo_orders_created_total——.created 这一段在命名规范化中被吃掉了。写面板查询前，先到 /actuator/prometheus 里看实际序列名，这一步能省掉后面所有「为什么查不到数据」的排查。

六、启动项目并本地验证

6.1 验证指标端点

第三个命令必须带 Accept: text/plain——prometheus 端点产出纯文本，用纯 JSON 的 Accept 去请求会得到 406：

curl -H "Accept: text/plain" http://localhost:8081/actuator/prometheus

返回的文本里应能看到 JVM、HTTP 与业务指标样本。触发一次下单后，回到该端点能看到三个业务指标的真实样本。

七、Prometheus 接入：追加抓取任务

7.1 确认本机服务形态

status/config 返回的配置里只有 Prometheus 自抓取一个 job——这就是要追加任务的原因。/-/reload 返回 403 说明这个实例没开 --web.enable-lifecycle，改配置没法热生效，只能走重启。

7.2 追加 scrape 任务

先备份，再改，改完校验语法。在 scrape_configs: 下追加：

scrape_configs:
  - job_name: spring-boot
    metrics_path: /actuator/prometheus
    static_configs:
      - targets:
          - localhost:8081
        labels:
          application: prometheus-demo

三个关键点：

  • metrics_path 必须是 /actuator/prometheus，写成 /metrics 会 404；
  • targets 里的地址是从 Prometheus 进程的视角出发的——本机 Windows 进程抓本机应用用 localhost:8081；如果 Prometheus 在 Docker 里跑，要换成 host.docker.internal:8081；
  • labels 是给这组目标追加的静态标签，application 标签可以和应用侧 metrics.tags 注入的标签互相印证。

7.3 让配置生效：热重载还是重启

方式 条件 命令
热重载 启动时带 --web.enable-lifecycle curl -X POST http://localhost:9090/-/reload
重启进程 无条件 停掉进程后按原命令重新启动

重启后日志出现 TSDB started、Loading configuration file、Server is ready to receive web requests. 三行即成功。历史时序数据保留（TSDB 是本地目录，不受进程重启影响）。

如果生产上经常需要增删抓取目标，建议启动 Prometheus 时加上 --web.enable-lifecycle，改完配置一条 reload 请求生效；但这个管理接口必须限制访问来源，不能暴露公网。更彻底的做法是用 file_sd 文件服务发现或对接注册中心（Consul/Nacos/Kubernetes），抓取目标列表与 Prometheus 配置解耦。

7.4 验证 Targets 与指标入库

关注 activeTargets 里 job="spring-boot" 这一项：health 应为 up，scrapeUrl 应为 http://localhost:8081/actuator/prometheus；也可以在浏览器看 http://localhost:9090/targets，DOWN 时点开会看到具体错误信息。

注意 rate() 类查询需要窗口内至少两个样本点——刚接入时等 30 秒以上再查，第一次查不到数据不一定是配置错了。

八、PromQL 常用查询

目标 PromQL
目标存活 up{job="spring-boot"}
JVM 堆内存 jvm_memory_used_bytes{area="heap",job="spring-boot"}
进程 CPU process_cpu_usage{job="spring-boot"}
下单速率 sum(rate(demo_orders_total[2m]))
HTTP 请求速率 sum(rate(http_server_requests_seconds_count{job="spring-boot"}[2m]))
按 URI/状态码的请求速率 sum by (uri, status) (rate(http_server_requests_seconds_count[2m]))
平均请求耗时 sum(rate(http_server_requests_seconds_sum[2m])) / sum(rate(http_server_requests_seconds_count[2m]))
下单 P95 耗时 histogram_quantile(0.95, sum by (le) (rate(demo_orders_create_duration_seconds_bucket[2m])))
当前活跃任务数 demo_tasks_active

histogram_quantile(0.95, ...) 返回约 0.125 秒左右，和下单模拟耗时（30~120ms）的分布吻合——直方图链路是准的。分位数查询依赖 _bucket 序列，查不到就回头检查 percentiles-histogram 配置和 Timer 的 publishPercentileHistogram()。

九、Grafana 接入与面板

9.1 添加数据源

  1. 浏览器打开 http://localhost:3000 并登录；
  2. 左侧菜单 Connections → Data sources → Add data source，选 Prometheus；
  3. URL 填 http://localhost:9090——注意这个地址是从 Grafana 进程视角出发的。本机 Grafana 和 Prometheus 都是 Windows 进程，localhost 正确；如果两者都在 Docker Compose 网络里，要填服务名 http://prometheus:9090；
  4. 点 Save & test，出现绿色 “Successfully queried the Prometheus API” 即通。

9.2 面板实配

新建 Dashboard，逐个添加 Visualization 面板，查询用第八章的 PromQL。实测保存的五个面板：

面板 查询 图表类型 实测效果
服务状态 up{job="spring-boot"} Time series（也可用 Stat，阈值 1 绿 / 0 红） 序列稳定在 1
活跃任务数 demo_tasks_active Gauge 显示与接口返回一致
下单速率 sum(rate(demo_orders_total[2m])) Time series 压测时段出现明显尖峰
下单 P95 耗时 histogram_quantile(0.95, sum by (le) (rate(demo_orders_create_duration_seconds_bucket[2m]))) Time series 与 PromQL 实测吻合
JVM 堆内存 sum(jvm_memory_used_bytes{area="heap",job="spring-boot"}) Time series 典型 GC 锯齿

两个实操细节：

  • 面板查询切到代码模式粘贴 PromQL，点「运行查询」确认预览有数据后再返回；每加完一个面板都要点一次仪表板顶部的保存——只保存面板不保存仪表板，刷新后面板会丢；
  • 新面板默认 Time series；Gauge 类瞬时值在可视化选择器里切换，Grafana 会根据查询结果在右侧给出建议类型。

9.3 面板没数据的排查顺序

  1. Prometheus 的 /targets 页面确认应用 UP；
  2. Prometheus 的 Graph 页面直接跑同一条 PromQL；
  3. 都有数据再检查 Grafana：数据源 URL、面板查询、右上角时间范围（默认 15m 有时太短）。

十、告警规则：目标宕机告警

Prometheus 可以按 PromQL 周期性评估告警规则。给「应用抓取失败」配一条最基础的规则——springboot-alerts.yml：

groups:
  - name: springboot
    rules:
      - alert: TargetDown
        expr: up{job="spring-boot"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Spring Boot 应用抓取失败"

在 prometheus.yml 顶层加载规则文件，然后重载/重启生效。for: 1m 的含义是条件要持续满足一分钟才触发，避免抓取抖动造成的误报。规则触发后可以在 http://localhost:9090/alerts 页面看到 firing 状态。

要发邮件、企业微信、钉钉通知，还需要再接 Alertmanager（或改用 Grafana Alerting）——告警规则本身只产生状态，不发通知。

十一、生产环境上线清单

  1. 管理端口隔离：8081 只对监控网络开放（防火墙/安全组/NetworkPolicy），不要映射公网；
  2. 端点最小暴露：保持 include: health,info,prometheus,metrics 这类白名单，禁止 include: "*"——env/configprops 会泄露配置与内部结构；
  3. 带认证的抓取：引入 Spring Security 后 actuator 会被拦截，给 Prometheus 配专用只读账号（Prometheus 侧用 basic_auth + 密码文件），不要为了抓取成功关掉安全机制；
  4. 标签基数控制：禁止把 userId、orderId、完整 URL、requestId 做标签。每个不同的标签组合都是一条独立时间序列，高基数会同时打爆内存、磁盘和查询；URL 用路由模板（/api/demo/orders 而不是带参数的完整路径）；
  5. 数据保留规划：本机默认 15 天，按实例数 × 序列数 × 保留天数估算磁盘；大规模场景考虑远程存储或联邦；
  6. Grafana 固定版本：生产不用 latest 镜像，密码走密钥管理，不进 Git。

十二、常见问题排查

现象 根因 解法
/actuator/prometheus 404 缺 micrometer-registry-prometheus 依赖；或端点未暴露 补依赖；检查 exposure.include 含 prometheus
端点 406 请求 Accept 是纯 JSON 加 Accept: text/plain
Target DOWN 且 connection refused 应用没起 / 端口错 / 网络不通 先在 Prometheus 所在机器 curl 目标 URL
Target DOWN 且 404 metrics_path 写错 必须是 /actuator/prometheus
/actuator/info 返回 {} Boot 3.5 env 贡献者默认关闭 management.info.env.enabled: true
集成测试里 prometheus 端点 404 Spring Boot Test 默认关可观测性 测试类加 @AutoConfigureObservability
PromQL 查不到 demo_orders_created_total 注册名 ≠ 输出名 实际序列是 demo_orders_total，先看端点输出
rate() 查不到数据 窗口内样本点不足 等 30 秒以上（至少两轮抓取）再查
P95 查询为空 没有直方图桶 确认 percentiles-histogram 配置与 Timer 的 publishPercentileHistogram()
Gauge 变 NaN 被观测对象被 GC 用字段强引用持有 AtomicInteger 等对象
Grafana Save & test 失败 数据源地址视角错误 本机进程用 localhost；容器间用服务名
改了 prometheus.yml 不生效 未启 lifecycle API 热重载（--web.enable-lifecycle + reload）或重启进程

十三、小结

Spring Boot 整合 Prometheus 的完整链路只有四步：

  1. 依赖：web + actuator + micrometer-registry-prometheus，版本交给 Boot BOM；
  2. 暴露：管理端口独立（8081），白名单暴露 prometheus 端点，注入 application 公共标签；
  3. 抓取：prometheus.yml 加一个 job 指向 localhost:8081/actuator/prometheus，让配置生效；
  4. 消费：PromQL 查询、Grafana 面板、告警规则。

三个最值得记住的实战点：

  1. 注册名不等于输出序列名：demo.orders.created → demo_orders_total，写查询前先看端点实际输出；
  2. Boot 3.5 的 info 端点默认空：management.info.env.enabled: true；
  3. 改抓取配置要想清楚生效方式：lifecycle API 没开就只能重启，生产上建议 file_sd 或服务发现解耦。

监控的价值不在「接上了」，而在出问题时有数据可查：下单速率掉了、P95 涨了、堆内存爬坡了——这些都从这套链路里来。
