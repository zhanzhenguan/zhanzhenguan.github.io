一、跨域问题的原因

浏览器出于安全考虑，会受到同源策略（Same-Origin Policy）的限制。当请求的 协议、域名、端口 任意一项不同时，就属于跨域请求。

地址 是否跨域 原因
http://localhost:8080 → http://localhost:8080 否 完全相同
http://localhost:8080 → http://localhost:8081 是 端口不同
http://localhost:8080 → https://localhost:8080 是 协议不同
http://localhost:8080 → http://127.0.0.1:8080 是 主机名不同
http://localhost:8080 → http://www.example.com 是 域名不同

跨域限制主要由浏览器执行，并不是服务器之间不能互相请求。当后端没有返回浏览器认可的 CORS（Cross-Origin Resource Sharing，跨源资源共享）响应头时，浏览器可能阻止前端 JavaScript 读取响应。

注意：跨域并不意味着请求一定没有到达服务器。部分请求可能已经被服务器处理，只是浏览器不允许前端读取响应。

二、方法一：使用 @CrossOrigin 注解（局部配置）

适合只允许某个 Controller 或接口跨域的情况。

2.1 Controller 级别

@RestController
@RequestMapping("/api/users")
@CrossOrigin(origins = "http://localhost:3000")
public class UserController {
    // ...
}

此配置允许来自 http://localhost:3000 的请求访问该 Controller。也可以标在单个方法上做方法级别配置。

2.2 常用属性

属性 说明
origins 允许访问的来源，例如 http://localhost:3000
methods 允许的 HTTP 方法
allowedHeaders 允许前端请求携带的请求头
exposedHeaders 允许前端 JavaScript 读取的响应头
allowCredentials 是否允许携带 Cookie 等凭证
maxAge 预检请求结果缓存时间，单位秒 
@CrossOrigin(
        origins = "http://localhost:3000",
        methods = {RequestMethod.GET, RequestMethod.POST},
        allowedHeaders = "*",
        exposedHeaders = "Authorization",
        allowCredentials = "true",
        maxAge = 3600)

如果需要携带 Cookie，必须指定明确的来源，不能使用 origins = "*"。

三、方法二：使用 WebMvcConfigurer 全局配置（推荐常见 MVC 项目）

适合统一配置整个 Spring MVC 应用的跨域规则。

@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOrigins("http://localhost:3000", "http://localhost:5173")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .exposedHeaders("Authorization")
                .allowCredentials(true)
                .maxAge(3600);
    }
}

配置说明：

  • addMapping("/**")：配置所有接口路径；
  • allowedOrigins(...)：指定允许的前端来源；
  • allowedMethods(...)：指定允许的请求方法；
  • allowedHeaders("*")：允许请求携带的请求头；
  • exposedHeaders(...)：让前端能够读取指定响应头，例如 Authorization；
  • allowCredentials(true)：允许浏览器请求携带凭证；
  • maxAge(3600)：浏览器缓存预检结果 3600 秒。

生产环境建议配置明确的域名，不要无条件允许所有来源。

四、方法三：使用 Spring Security 配置跨域（Spring Boot 3.x）

如果项目集成了 Spring Security，建议通过 Spring Security 的 CORS 支持配置，并确保 CORS 在认证授权处理之前生效。

4.1 配置 CORS 来源

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("http://localhost:3000"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("*"));
    config.setAllowCredentials(true);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

4.2 Security 配置启用 CORS

Spring Boot 3.x 通常使用 Spring Security 6.x，采用 SecurityFilterChain 配置方式：

@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated());
    return http.build();
}

http.cors() 会使用容器中提供的 CorsConfigurationSource 等 CORS 配置。

注意：跨域配置与认证授权是不同问题。CORS 配置正确后，接口仍可能返回 401 或 403，这通常是认证、授权或 CSRF 相关问题，不应直接认定为跨域配置失败。旧版 Spring Security（例如 5.x）的 WebSecurityConfigurerAdapter 在较新版本中已被弃用并移除，建议使用 SecurityFilterChain。

五、方法四：使用 Filter 手动设置跨域响应头

适用于需要在 Servlet Filter 层处理跨域的场景。但普通 Spring MVC 项目通常优先采用 WebMvcConfigurer 或 Spring Security 的 CORS 支持，避免重复配置。

@Component
public class CorsFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        HttpServletResponse response = (HttpServletResponse) res;

        String origin = request.getHeader("Origin");
        if (isAllowedOrigin(origin)) {
            response.setHeader("Access-Control-Allow-Origin", origin);
            response.setHeader("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS");
            response.setHeader("Access-Control-Allow-Headers", "*");
            response.setHeader("Access-Control-Allow-Credentials", "true");
        }
        chain.doFilter(req, res);
    }

    private boolean isAllowedOrigin(String origin) {
        // 白名单匹配，不要直接回显任意 Origin
        return origin != null && (origin.equals("http://localhost:3000"));
    }
}

Filter 注意事项：

  1. 允许来源应通过白名单判断，不能直接把任意 Origin 回显给客户端；
  2. 如果允许凭证，不能将 Access-Control-Allow-Origin 设置为 *；
  3. 不要同时在 Filter、MVC、Security、Nginx 中重复添加冲突的 CORS 响应头；
  4. Spring Boot 3.x 使用 jakarta.servlet；Spring Boot 2.x 通常使用 javax.servlet，代码包名需要对应版本调整；
  5. 如果 Filter 在 Spring Security 之后执行，预检请求可能先被认证机制拒绝，需要调整 CORS 处理顺序或使用 Security 原生 CORS 配置。

六、预检请求（OPTIONS）

浏览器对部分跨域请求会先发送 OPTIONS 请求，询问服务器是否允许后续请求。常见触发情况：

  • 使用 PUT、DELETE 等非简单请求方法；
  • 请求携带 Authorization 等自定义请求头；
  • 使用 Content-Type: application/json 等不属于简单请求允许范围的内容类型。

预检请求通常会携带：Origin、Access-Control-Request-Method、Access-Control-Request-Headers。服务器应返回符合要求的 CORS 响应头；如果预检请求失败，浏览器通常不会继续发送实际请求。

七、Cookie 与跨域请求

如果前后端跨域且需要使用 Cookie，需要前后端共同配置。

7.1 后端

后端允许凭证：Access-Control-Allow-Credentials: true，且 Access-Control-Allow-Origin 返回明确来源，不能为 *。

7.2 前端（Fetch）

fetch("/api/users", {
  credentials: "include"
})

7.3 前端（Axios）

axios.get("/api/users", { withCredentials: true })

注意事项：

  • Access-Control-Allow-Origin 不能为 *，必须返回明确来源；
  • Access-Control-Allow-Credentials 必须为 true；
  • Cookie 的 SameSite、Secure、域名和路径属性也可能影响是否发送；
  • 跨站 Cookie 通常需要 SameSite=None; Secure，而 Secure 一般要求 HTTPS；
  • CORS 允许访问不等于 Cookie 一定会发送，Cookie 策略仍然独立生效。

八、生产环境 Nginx 配置

如果请求经过 Nginx，Nginx 也可能处理或覆盖 CORS 响应头。应先确定由后端还是 Nginx 统一处理，避免双方重复添加响应头。

说明：

  • always：让指定响应头在更多响应状态下也添加，便于处理错误响应；
  • 如果需要支持多个来源，应使用经过校验的白名单映射，不能将任意来源直接回显；
  • Nginx 配置语法及 if 的使用需结合实际配置结构验证；
  • 如果后端已经配置 CORS，建议不要再由 Nginx 重复设置相同响应头。

九、跨域问题排查步骤

9.1 检查浏览器控制台

打开浏览器开发者工具（F12），查看 Console 和 Network：请求的实际 URL、协议、域名、端口是否正确；是否出现 CORS 错误；是否存在 OPTIONS 预检请求；OPTIONS 返回状态码和响应头是否符合预期；实际请求是否发出，以及返回 401、403、404、500 等状态码。

9.2 检查响应头

响应头 作用
Access-Control-Allow-Origin 允许的请求来源
Access-Control-Allow-Methods 允许的请求方法
Access-Control-Allow-Headers 允许的请求头
Access-Control-Allow-Credentials 是否允许凭证
Access-Control-Expose-Headers 前端可读取的响应头
Access-Control-Max-Age 预检结果缓存时间

9.3 使用 curl 模拟请求

普通跨域请求与模拟预检请求都可以用 curl 复现。curl 不会像浏览器一样执行 CORS 限制，但可以帮助检查服务器是否返回正确响应头：

# 模拟预检请求
curl -i -X OPTIONS http://localhost:8080/api/users \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET"

9.4 检查中间件与代理

如果部署链路为「前端 → Nginx / 网关 → 后端」，需要逐层检查：Nginx 是否添加、覆盖或移除 CORS 响应头；API 网关是否有统一跨域策略；Spring Security 是否在 CORS 处理前拒绝 OPTIONS 请求；是否有多个组件重复添加 Access-Control-Allow-Origin，导致响应头重复或值不合法；错误响应（例如 401、403、500）是否缺少 CORS 响应头。

9.5 检查前端请求配置

如果使用 Cookie：Fetch 是否配置 credentials: "include"；Axios 是否配置 withCredentials: true；Cookie 是否因 SameSite、Secure、域名或路径限制而未发送。如果使用 JWT：前端是否在请求头中携带 Authorization；后端 allowedHeaders 是否允许 Authorization；是否正确处理 OPTIONS 预检请求。

十、常见错误及解决方案

问题 可能原因 解决方案
No 'Access-Control-Allow-Origin' header 服务端没有返回允许来源响应头 检查 CORS 配置是否生效
允许 Cookie 却使用 * 浏览器不允许凭证模式下使用通配来源 配置具体 Origin
OPTIONS 返回 401/403 Security、网关或 Filter 拦截预检请求 确保 CORS 先处理，并正确允许 OPTIONS
请求头 Authorization 被拒绝 未允许该请求头 在 allowedHeaders 中允许
前端读取不到响应中的自定义头 未暴露响应头 配置 exposedHeaders
配置了跨域但仍报错 Nginx、网关、Security 等层存在冲突 按请求链路逐层排查
Cookie 没有发送 前端凭证配置或 Cookie 属性不符合要求 检查 credentials、SameSite、Secure 等
响应头出现多个 Access-Control-Allow-Origin 多层重复配置 统一由一个层级负责 CORS

十一、安全注意事项

  1. 生产环境不要无条件使用 allowedOrigins("*")，只允许可信前端来源。
  2. 如果启用 allowCredentials(true)，必须使用明确的来源，不能使用通配符来源。
  3. CORS 不是身份认证和授权机制，不能替代登录验证、权限控制。
  4. CORS 不能防止所有 CSRF 攻击。使用 Cookie 认证时，仍应根据业务安全要求配置 CSRF 防护。
  5. allowedHeaders("*")、允许所有方法等宽松设置，应根据项目实际需求收敛。
  6. 如果允许动态 Origin，必须先进行严格白名单匹配，不能直接信任请求中的 Origin。
  7. 生产环境尽量使用 HTTPS。

十二、推荐配置方案

项目情况 推荐方式
少量接口跨域 @CrossOrigin
普通 Spring MVC 项目 WebMvcConfigurer 全局配置
Spring Security 项目 CorsConfigurationSource + http.cors()
需要特殊 Servlet 处理 自定义 Filter（避免重复配置）
由网关统一管理 在 API 网关统一配置 CORS
Nginx 直接代理前后端 可由 Nginx 统一处理，但需避免后端重复添加

建议：一个项目尽量由一个明确的层级统一负责 CORS。先确认请求链路，再配置对应层级；不要同时在 Controller、MVC、Filter、Security、Nginx 中随意叠加跨域配置。

十三、小结

跨域问题本质是浏览器同源策略，不是服务端不通；排查先分清「请求没到」「响应头不对」「被认证拦截」「Cookie 没发」四类情况。三个最容易复盘的点：

  1. 配置层级单一负责：MVC 项目优先 WebMvcConfigurer，Security 项目用 CorsConfigurationSource，避免多层叠加出重复响应头；
  2. 凭证与通配符互斥：允许 Cookie / 凭证时，来源必须明确，不能用 *；
  3. 预检先放行：OPTIONS 被 401/403 拦截时，先检查 CORS 处理顺序与 Security 过滤链，不要当成跨域配置本身写错。
