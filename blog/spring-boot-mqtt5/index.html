一、版本基线

组件 版本 说明
JDK 17 Spring Boot 3.x 最低要求
Spring Boot 3.5.16 3.5 系列维护版本，依赖统一交给 BOM
Spring Integration 6.5.10 随 Boot 3.5.16 引入，spring-integration-mqtt 不用手写版本
Eclipse Paho MQTT v5 Client 1.2.5 必须显式声明，它是 Spring Integration 的可选依赖
Eclipse Mosquitto 2.1.4 本机 MQTT Broker，监听 1883
Maven 3.9.3 3.6.3+ 均可

两条版本原则：

  1. Spring Integration 的版本交给 Spring Boot 管。Boot 3.5.16 的依赖清单锁定的就是 6.5.10，自己在 pom 里写版本号反而容易和 BOM 混搭出不兼容组合。
  2. MQTT v5 客户端一定显式引入。spring-integration-mqtt 只把 Paho v5 当可选依赖，不会自动传递；漏了它，编译期就会报「MQTT v5 类找不到」。

二、MQTT 核心概念速览

2.1 发布/订阅模型

MQTT 是为弱网、低带宽、嵌入式设备设计的轻量消息协议。它不像 HTTP 那样「请求一次、响应一次」，而是所有客户端都连到 Broker，通过 Topic（主题） 解耦：发布者把消息发给某个 Topic，订阅者提前订阅感兴趣的 Topic，双方不需要知道对方的地址。

对比项 HTTP MQTT
通信模型 请求 / 响应 发布 / 订阅
双方耦合 调用方要知道对方地址 双方只认 Broker 与 Topic
连接开销 每次请求可新建连接 长连接 + 心跳保持
典型场景 Web API、页面交互 设备遥测、实时下发、物联网

2.2 Topic 与通配符

Topic 是斜杠分隔的层级字符串，大小写敏感，例如 demo/device/001/telemetry。订阅时可以用通配符，发布时必须是精确主题：

符号 含义 示例 匹配
+ 单层 demo/device/+/telemetry demo/device/001/telemetry
# 多层（须在末尾） demo/device/# demo/device/001/telemetry、demo/device/a/b

本项目订阅 demo/device/+/telemetry，用一层通配覆盖所有设备；发布接口里专门做了校验，Topic 含 + 或 # 直接拒绝。

2.3 QoS 三个等级

QoS 语义 代价 适用
0 至多一次，发完不管 最低 高频遥测、允许丢点
1 至少一次，可能重复 中等 通用业务消息
2 恰好一次 四次握手，最重 计费、关键指令

本项目默认 qos=1。QoS 1 不保证不重复，去重必须在业务层用 messageId 做。

2.4 保留消息与遗嘱消息

  • 保留消息（Retained）：Broker 为每个 Topic 保存最近一条 retained 消息，新订阅者一上线就能立刻拿到最新状态，不用等设备下次上报。
  • 遗嘱消息（LWT）：客户端连接时预先登记一条「遗言」，当它异常断开（网络断、进程被杀）时由 Broker 代发；正常 DISCONNECT 不触发。

两者配合就是最轻量的在线状态方案：本项目登记遗嘱 demo/server/status = offline，订阅成功后主动发一条 retained 的 online。

2.5 MQTT 5 相比 3.1.1 的增强

常用增强有：原因码与更清晰的错误反馈、会话过期间隔（Session Expiry）、共享订阅 $share、消息过期、用户属性、Topic 别名等。Spring Integration 对 v5 提供了独立的 Mqttv5ClientManager 与 Mqttv5Paho* 适配器，不要把 v3 的转换器套到 v5 适配器上。

三、准备 Broker：Mosquitto 2.1.4

3.1 Docker Compose 方案

有 Docker 的机器最省事，broker/docker-compose.yml：

services:
  mosquitto:
    image: eclipse-mosquitto:2.1.4
    container_name: mosquitto
    ports:
      - "1883:1883"
    volumes:
      - ./mosquitto.conf:/mosquitto/config/mosquitto.conf
      - mosquitto-data:/mosquitto/data
      - mosquitto-log:/mosquitto/log
    restart: unless-stopped

volumes:
  mosquitto-data:
  mosquitto-log:

对应 broker/mosquitto.conf（容器用，开持久化）：

listener 1883
allow_anonymous true
persistence true
persistence_location /mosquitto/data/
log_dest stdout

3.2 本机命令行方案

本机没有 Docker 时，可用官方 Windows 版程序文件命令行启动，不需要注册 Windows 服务，效果与容器一致。broker/mosquitto-windows.conf 同样配置 listener 1883、allow_anonymous true、log_dest stdout。

allow_anonymous true 仅限本机隔离学习环境，切勿把这样的 Broker 暴露到公网。

3.3 踩坑：log_dest 没有 console

第一次启动时 Broker 秒退，退出码 3。Mosquitto 的 log_dest 合法取值只有 stdout / stderr / syslog / topic / file <path> / none，没有 console。改成 log_dest stdout 后正常启动。这是配置文件解析阶段的错误，不会有任何网络连接日志，容易被误判成「端口不通」。

3.4 命令行往返自检

Broker 起来后先别急着写 Java，用 mosquitto_pub / mosquitto_sub 做一次往返自检，确认 Broker 本身没问题：

# 终端 A：订阅
mosquitto_sub -t "demo/selftest"

# 终端 B：发一条保留消息
mosquitto_pub -t "demo/selftest" -m "hello" -r

# 测完清掉保留消息
mosquitto_pub -t "demo/selftest" -n -r

-r 是发一条保留消息，mosquitto_sub 一订阅就立刻收到，一次命令就能验证发布、订阅、保留三条链路；-n 表示空消息，用于清掉该 Topic 的 retained 消息。

五、配置 MQTT 客户端参数

5.1 application.yml

mqtt:
  broker: tcp://127.0.0.1:1883
  client-id: demo-app-001
  username: ${MQTT_USERNAME:}
  password: ${MQTT_PASSWORD:}
  topic-telemetry: demo/device/+/telemetry
  topic-status: demo/server/status
  qos: 1
  clean-start: true
  max-reconnect-delay: 30

logging:
  charset:
    console: UTF-8

三个细节：

  1. 凭据用环境变量占位，本机匿名时为空，将来开启 Broker 认证不必改代码。
  2. Client ID 必须全局唯一。MQTT Broker 限制同一个 Client ID 只能有一个活动连接，两个进程用同一个 ID 会互相踢下线。
  3. logging.charset.console: UTF-8 是实测后补的。Windows 中文环境下 Logback 控制台编码跟随系统代码页，日志里的中文会变成乱码；显式指定 UTF-8 后 IDEA 里正常，CMD 下配合 chcp 65001 即可。

5.2 MqttProperties

用 record 做构造器绑定，不用手写 getter/setter：

@ConfigurationProperties(prefix = "mqtt")
public record MqttProperties(
        String broker,
        String clientId,
        String username,
        String password,
        String topicTelemetry,
        String topicStatus,
        @Min(0) @Max(2) int qos,
        boolean cleanStart,
        int maxReconnectDelay) {
}

配置类上加 @EnableConfigurationProperties(MqttProperties.class) 即可启用，QoS 直接在绑定阶段被约束在 0~2。

六、用 Spring Integration 接入 MQTT 5

6.1 先想清楚连接怎么管

最容易踩的坑是「入站适配器一个连接、出站适配器另一个连接，两个都用同一个 Client ID」。Broker 会把先连上的踢掉，于是日志里出现反复掉线重连。

正确做法是让所有通道适配器共享一个 ClientManager 管理的连接：入站负责订阅、出站负责发布，底层是同一个 MQTT 客户端会话。

6.2 MqttConfig：共享连接 + 遗嘱 + 自动重连

@Configuration
@EnableConfigurationProperties(MqttProperties.class)
@RequiredArgsConstructor
public class MqttConfig {

    private final MqttProperties props;

    @Bean
    public Mqttv5ClientManager mqttClientManager() {
        MqttConnectionOptions options = new MqttConnectionOptions();
        options.setServerURIs(new String[]{props.broker()});
        options.setClientId(props.clientId());
        options.setAutomaticReconnect(true);
        options.setMaxReconnectDelay(props.maxReconnectDelay());
        options.setCleanStart(props.cleanStart());
        if (props.username() != null && !props.username().isBlank()) {
            options.setUserName(props.username());
            options.setPassword(props.password().toCharArray());
        }
        // 遗嘱消息：异常断开时代发 offline
        MqttMessage will = new MqttMessage("offline".getBytes(StandardCharsets.UTF_8));
        will.setQos(props.qos());
        options.setWill(props.topicStatus(), will);
        return new Mqttv5ClientManager(options);
    }
}

automaticReconnect 交给 Paho 按退避策略重连，maxReconnectDelay 限制最大等待。cleanStart=true 表示每次从干净会话开始，适合演示；生产要保留离线消息得改成固定 Client ID + cleanStart=false + Session Expiry + Broker 持久化。

6.3 入站订阅 IntegrationFlow

@Bean
public IntegrationFlow mqttInboundFlow(Mqttv5ClientManager manager,
                                       TelemetryService telemetryService) {
    Mqttv5PahoMessageDrivenChannelAdapter adapter =
            new Mqttv5PahoMessageDrivenChannelAdapter(manager, props.topicTelemetry());
    adapter.setPayloadType(byte[].class);
    adapter.setManualAcks(false);

    return IntegrationFlow.from(adapter)
            .handle(message -> telemetryService.consume((byte[]) message.getPayload()))
            .get();
}

payloadType 设成 byte[]，把解码和 JSON 解析留给业务层，适配层不绑死数据格式。setManualAcks(false) 是协议层自动确认；关键业务如需「处理成功才确认」，再开手动 ACK。

6.4 出站发布 IntegrationFlow

@Bean
public MessageChannel mqttOutboundChannel() {
    return new DirectChannel();
}

@Bean
public IntegrationFlow mqttOutboundFlow(Mqttv5ClientManager manager) {
    Mqttv5PahoMessageHandler handler = new Mqttv5PahoMessageHandler(manager);
    return IntegrationFlow.from("mqttOutboundChannel")
            .handle(handler)
            .get();
}

业务代码只往 mqttOutboundChannel 丢消息，Topic / QoS / Retained 放在消息头里，适配器负责真正发到 Broker。

6.5 核心类职责一览

组件 职责
MqttProperties 绑定 Broker 地址、Client ID、Topic、QoS、连接参数
Mqttv5ClientManager 管理共享的 MQTT 5 客户端连接
Mqttv5PahoMessageDrivenChannelAdapter 订阅 Topic，把入站报文转成 Spring Message
Mqttv5PahoMessageHandler 把 Spring Message 发布到 MQTT Topic
IntegrationFlow 组织消息从入站通道到业务处理器、从出站通道到适配器的流转

七、实现消息消费与发布

7.1 消费服务

重点是非法消息不能打断订阅链路：设备可能发纯文本、发半个 JSON，解析失败只告警返回，不能让异常一路抛回适配器。

@Service
@Slf4j
@RequiredArgsConstructor
public class TelemetryService {

    private final ObjectMapper objectMapper;

    public void consume(byte[] payload) {
        String body = new String(payload, StandardCharsets.UTF_8);
        try {
            JsonNode node = objectMapper.readTree(body);
            log.info("收到设备遥测：{}", node);
        } catch (Exception e) {
            log.warn("非法消息已跳过：{}", body, e);
        }
    }
}

7.2 发布请求 DTO

public record PublishRequest(
        @NotBlank String topic,
        @NotBlank String payload,
        @Min(0) @Max(2) Integer qos,
        boolean retained) {
}

7.3 发布服务与注入歧义

@Qualifier 不是可选项。Spring Integration 启动时会自动注册 errorChannel、nullChannel 等多个 MessageChannel Bean，只按类型注入 MessageChannel 存在歧义风险；按名称精确指定才稳。

@Service
@RequiredArgsConstructor
public class CommandPublishService {

    @Qualifier("mqttOutboundChannel")
    private final MessageChannel outboundChannel;

    public void publish(PublishRequest req) {
        Message<byte[]> message = MessageBuilder
                .withPayload(req.payload().getBytes(StandardCharsets.UTF_8))
                .setHeader(MqttHeaders.TOPIC, req.topic())
                .setHeader(MqttHeaders.QOS, req.qos() == null ? 1 : req.qos())
                .setHeader(MqttHeaders.RETAINED, req.retained())
                .build();
        outboundChannel.send(message);
    }
}

7.4 REST 接口

@RestController
@RequestMapping("/api/mqtt")
@RequiredArgsConstructor
public class MqttController {

    private final CommandPublishService publishService;

    @PostMapping("/publish")
    public Map<String, Object> publish(@Valid @RequestBody PublishRequest req) {
        publishService.publish(req);
        return Map.of("success", true, "topic", req.topic(),
                "qos", req.qos() == null ? 1 : req.qos(), "retained", req.retained());
    }
}

success=true 只代表消息已提交到出站通道并由 Broker 确认，不代表设备已经执行。要业务级确认，得让设备处理后往 response/ack 主题回执，并跟踪 requestId。

7.5 实测缺陷：非法 Topic 返回 500

第一轮参数测试：qos=3 正确返回 400，但 topic=demo/+/bad 返回了 HTTP 500。原因是 IllegalArgumentException 被 Servlet 容器当成未处理异常，直接落到 Boot 默认错误页。请求参数写错，不该报服务端内部错误，补一个全局异常处理器：

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, Object>> badRequest(IllegalArgumentException e) {
        return ResponseEntity.badRequest()
                .body(Map.of("success", false, "message", e.getMessage()));
    }
}

修复后同样请求返回 400 与错误信息。发布接口的 Topic 校验：含 + 或 # 时抛 IllegalArgumentException，由上述处理器统一映射。

7.6 连接事件与在线状态

事件回调跑在 Paho 的回调线程上，同步发布可能阻塞回调线程，所以丢到独立线程；发布失败只告警，不影响主流程。这样 online（订阅成功主动发）和 offline（遗嘱）就形成闭环。

八、启动与端到端实测

8.1 构建与启动

顺序固定：先 Broker，再应用。看到订阅成功那一行日志，才说明连接、订阅、ClientManager 全链路通了。

8.2 设备上报遥测

用 mosquitto_pub 模拟设备上报 demo/device/001/telemetry，应用日志应解析出设备编号与指标；非法 JSON 只告警跳过，不影响后续消息。

8.3 REST 下发指令

先开一个订阅窗口 mosquitto_sub -t "demo/device/001/command"，再调发布接口。实测接口返回 {"success":true,"retained":false,"qos":1,"topic":"demo/device/001/command"}，订阅窗口收到对应指令。

8.4 保留消息与遗嘱消息实测

先订阅状态主题，能立刻拿到 retained 的 online；然后强制杀掉应用进程（模拟异常掉线，而不是正常关闭），再查同一个主题，offline 由 Broker 代发——应用进程已经不在了，这正是 LWT 的价值。重启应用后再查，会重新变回 online。这一步很多教程只讲配置不验证，建议自己动手确认一次。

8.5 参数校验实测

请求 实测结果
qos: 3 HTTP 400，qos 最大为 2
topic: "demo/+/bad" HTTP 400，发布 Topic 不能包含通配符 + 或 #
空 payload HTTP 400，payload 不能为空

九、踩坑汇总

现象 根因 处理
Broker 退出码 3，Invalid 'log_dest' value (console) 该配置项无 console 取值 改为 log_dest stdout
编译报 MQTT v5 类找不到 Paho v5 是可选依赖，未显式引入 pom 加 org.eclipse.paho.mqttv5.client:1.2.5
入站/出站反复掉线 两个适配器各自建连且 Client ID 相同 用 Mqttv5ClientManager 共享连接

非法参数返回 HTTP 500 IllegalArgumentException 未被识别为参数错误 加 @RestControllerAdvice 映射为 400
Windows 控制台日志中文乱码 Logback 控制台编码跟随系统代码页 配 logging.charset.console: UTF-8，CMD 用 chcp 65001
订阅不到消息 Topic 层级、大小写、通配符不匹配 核对订阅日志与订阅成功事件
QoS 1 收到重复消息 协议至少一次投递 + 业务重复消费 消息带 messageId，消费端幂等

十、QoS、会话与可靠性怎么选

10.1 QoS 选择

高频温度/位置遥测用 0 或 1，允许少量丢失；通用业务消息用 1 并做幂等；计费、关键指令才上 2。QoS 越高，握手次数和 Broker 状态开销越大，别一律拉满。

10.2 Clean Start 与会话

本项目 cleanStart=true，每次连接从干净会话开始，断线期间的订阅与消息不保留。生产若要离线消息，需要：固定 Client ID + cleanStart=false + 合理的 Session Expiry + Broker 开启持久化。三者缺一，重连后照样丢消息。

10.3 QoS 1 不等于不重复

PUBLISH 与 PUBACK 之间任何一环丢包，发送方都会重发，接收方就可能收到两次。协议层只能保证「至少一次」，业务层必须用 messageId + 唯一索引 / 去重表实现幂等，这是消费端设计而不是 Broker 配置能解决的。

十一、生产化建议

11.1 认证、ACL 与 TLS

关闭 allow_anonymous，用 mosquitto_passwd 建账号、配 ACL，按租户/产品/设备限制发布与订阅权限；外网一律上 TLS（8883），校验证书链与 SAN。凭据走环境变量或密钥管理，绝不写进代码仓库。

11.2 可观测性与多实例

监控连接数、消息吞吐、消费延迟、重连次数、设备在线率；连接事件回调已可监听订阅成功与连接失败，可扩展成告警。多实例部署时每个实例用唯一 Client ID，需要负载均衡消费时用 MQTT 5 的共享订阅 $share，避免多实例重复消费同一条消息。

11.3 MQTT 与其他中间件分工

技术 适合承担的职责
MQTT 设备、网关与服务之间的轻量级实时消息接入
Kafka / RocketMQ 平台内部事件流、业务解耦、高吞吐数据管道
Redis 在线状态缓存、短期去重、限流
MySQL 设备档案、业务配置、告警记录
时序数据库 温度、压力、位置等周期性指标的历史存储

常见架构是：设备通过 MQTT 上报到 Broker → Spring Boot 接入服务消费校验 → 业务事件投递 Kafka / 写库。MQTT 解决设备侧接入，内部消息平台解决系统间异步解耦，两者不是替代关系。

十二、小结

这套工程把 MQTT 接入最核心的五件事落到了可运行的代码里：共享连接、订阅入站、发布出站、状态感知、参数与异常治理。真正花时间的不是写 IntegrationFlow，而是把 Broker 起对、把 Client ID 与连接管对、把实测暴露的 500 和乱码修掉。三个最容易复盘的点：

  1. Paho v5 必须显式依赖，漏了编译期就报 v5 类找不到；
  2. 入站出站共享一个 ClientManager，否则同 Client ID 互相踢下线、反复重连；
  3. QoS 1 只保证至少一次，重复消费靠业务层 messageId 幂等解决。
