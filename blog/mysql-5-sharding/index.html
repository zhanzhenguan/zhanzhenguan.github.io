数据库分库分表策略全解：垂直/水平拆分、四种分片策略、落地姿势与连环坑

2026年11月28日 · 约 7 分钟 · 2384 字 #MySQL#数据库#分库分表#分片策略#ShardingSphere#后端

这一篇专门啃分库分表这块硬骨头：先讲单表为什么扛不住，再拆”怎么分、按什么规则分、代码怎么落地、分完还有哪些坑”。SQL、配置与代码为通用示例。

一、为什么需要分库分表

1.1 一张表的”中年危机”

数据库表像一家小餐馆：刚开张时几十个客人，一个服务员加一本菜单就够；客人多了，菜单翻烂、服务员忙不过来。对应到数据库是三个核心瓶颈：

瓶颈类型 表现 类比
数据量太大 一张表几千万行，B+ 树高度增加，查询变慢 菜单太厚，翻页都费劲
并发太高 上千请求同时打到一个库，连接池被打满 排队的人太多，服务员崩溃
磁盘/内存不够 单库数据数百 GB，备份恢复都成问题 餐馆太小，食材堆到门口

1.2 线上痛悟时刻

COUNT(*) 在 100 万行表上只要 0.1 秒，在 5000 万行表上可能要 30 秒以上；ALTER TABLE 加字段还会锁住表，所有写入阻塞。

核心认知：单表不是越大越好，数据量超过一定阈值（通常 500 万 ~ 2000 万行，视硬件和业务而定），性能会出现断崖式下跌。

二、分库分表到底”分”什么：两把刀

2.1 第一把刀：垂直切（按业务/列）

垂直切是把一张”宽表”按列拆成多张”窄表”：

原表（user）：id, name, password, avatar, bio, balance, vip_level, login_count
  ↓ 垂直拆分
user_base   （id, name, password）            ← 常用基础信息
user_profile（id, avatar, bio）               ← 不常用详情
user_account（id, balance, vip_level, login_count） ← 账户相关

适用场景：表字段太多（几十上百列）；有些列很大（TEXT、BLOB）拖慢整表扫描；业务上能明显按模块划分。

垂直分库则是把不同业务的表放到不同数据库实例上：

用户服务 → user_db    ← 独立数据库实例
订单服务 → order_db   ← 独立数据库实例
商品服务 → product_db ← 独立数据库实例

这是微服务架构下最常见的做法：每个服务有自己的库，互不干扰。

2.2 第二把刀：水平切（按数据行）

水平切是把一张表的行按某种规则分散到多张结构相同的表里：

原表（order）：5000 万行
  ↓ 水平拆分
order_0：0 ~ 1000 万行
order_1：1000 万 ~ 2000 万行
order_2：2000 万 ~ 3000 万行
order_3：3000 万 ~ 4000 万行
order_4：4000 万 ~ 5000 万行

适用场景：单表数据量太大查询变慢；单库数据量撑爆磁盘。

一句话判断：垂直切解决”表太宽”，水平切解决”表太长”。

三、水平分片的四种策略

数据怎么落到不同的表，直接决定后续查询能不能高效。

3.1 策略一：按范围分片（Range）

按某个字段的区间范围来分：

-- 按时间范围：每年一张表
order_2022 ← 2022 年的订单
order_2023 ← 2023 年的订单
order_2024 ← 2024 年的订单

-- 按 ID 范围：每 1000 万一张表
order_0 ← user_id: 1 ~ 10,000,000
order_1 ← user_id: 10,000,001 ~ 20,000,000
  • 优点：简单直观、易维护；扩容方便，新数据自然落到新表；按范围查询（如查某月订单）效率高；
  • 缺点：热点问题——按时间分时最新一张表读写压力最大，老表基本闲置；数据分布可能不均匀。

3.2 策略二：按哈希分片（Hash）

对某个字段取模，均匀分散：

// 用 user_id 取模，决定落到哪张表
int tableIndex = userId % 4; // 4 张表 → 0, 1, 2, 3
String tableName = "order_" + tableIndex;

// 4 张表时，user_id=1001：1001 % 4 = 1 → order_1
  • 优点：数据分布均匀，没有热点；实现简单；
  • 缺点：扩容困难——从 4 张表扩到 8 张表，几乎所有数据都要重新分配（一致性哈希可缓解）；范围查询需要扫所有表。

3.3 策略三：一致性哈希

一致性哈希是普通哈希的升级版，专门解决扩容问题：把哈希值映射到一个环上，扩容时只影响相邻节点，而不是全部数据。

传统哈希扩容：4 表 → 8 表，几乎全部数据需要迁移
一致性哈希扩容：新增一个节点，只有约 1/N 的数据需要迁移

哈希环：
        0
      /   \
     3     1
      \   /
        2
新增节点后，只影响环上相邻的一小段数据

面试加分点：一致性哈希最早由 Karger 等人在 1997 年提出，用于解决分布式缓存的数据分布问题。核心思想是把节点和数据都映射到同一个哈希环上，顺时针找最近的节点。

3.4 策略四：按业务/地理位置分片

-- 按地域分
order_beijing   ← 北京用户
order_shanghai  ← 上海用户
order_guangzhou ← 广州用户

适用场景很明确：业务天然按地域隔离，大部分查询都在本地。

3.5 选型指南

场景 推荐策略
有明显时间维度，查询多按时间 Range（按时间）
数据量大但查询随机，追求均匀 Hash（取模）
需要频繁扩容 一致性哈希
业务天然地域隔离 地域分片

四、分库分表的落地姿势

分片策略定了，接下来要解决”怎么让代码知道数据在哪张表”。业界有三种主流做法。

4.1 姿势一：应用层硬编码（最原始）

// 每次查数据前，自己算出表名
public Order getOrder(Long userId, Long orderId) {
    int tableIndex = (int) (userId % 4);
    String sql = "SELECT * FROM order_" + tableIndex + " WHERE id = ?";
    return jdbcTemplate.queryForObject(sql, new OrderRowMapper(), orderId);
}

能用，但不够优雅：分片逻辑和业务逻辑耦合，改分片规则要改业务代码，不推荐。

4.2 姿势二：ORM 框架插件（最常用）

以 ShardingSphere-JDBC 为例，配置数据源和分片规则：

spring:
  shardingsphere:
    datasource:
      names: ds0
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/order_db
        username: root
        password: ${DB_PASSWORD:change-me}
    rules:
      sharding:
        tables:
          t_order: # 4 张表：t_order_0 ~ t_order_3
            actual-data-nodes: ds0.t_order_$->{user_id % 4}

业务代码完全不用管分片：

@Autowired
private JdbcTemplate jdbcTemplate;

public Order getOrder(Long userId, Long orderId) {
    // ShardingSphere 自动根据 user_id 路由到正确的表
    return jdbcTemplate.queryForObject(
        "SELECT * FROM t_order WHERE user_id = ? AND id = ?",
        new OrderRowMapper(), userId, orderId);
}

对业务代码零侵入，这是最推荐的落地方式。

4.3 姿势三：数据库中间件代理（最重）

类似 MyCat、ShardingSphere-Proxy，在应用和数据库之间加一层代理：

应用 → ShardingSphere-Proxy（中间件） → MySQL_1, MySQL_2, MySQL_3

优点是应用完全无感知；缺点是架构多了一层，维护成本增加，并有性能损耗。

4.4 ShardingSphere 核心概念速览

概念 说明
分片键（Sharding Key） 决定数据落到哪张表的字段，如 user_id
分片算法（Sharding Algorithm） user_id % 4、范围匹配等
分片策略（Sharding Strategy） 分片键 + 分片算法
绑定表（Binding Table） 有相同分片规则的主从表，JOIN 时避免笛卡尔积
广播表（Broadcast Table） 每个库都有一份全量数据的表，如字典表、配置表

五、分完之后的”连环坑”

分库分表不是终点，而是新的起点。以下问题必须提前想好。

5.1 全局唯一 ID 怎么生成

单库单表时代用 AUTO_INCREMENT 就够了；分库分表后多个表各自自增，ID 会冲突——order_0 有 id=1，order_1 也有 id=1。

方案 原理 优点 缺点
UUID UUID.randomUUID() 简单，无中心节点 字符串长，无序，索引性能差
雪花算法 Snowflake 64 位 Long：时间戳 + 机器 ID + 序列号 有序，性能高，趋势递增 依赖机器时钟，时钟回拨会出问题
号段模式 Segment 从数据库批量取一段 ID 性能好，有序 依赖数据库
Redis 自增 INCR 命令 简单，性能好 依赖 Redis，需持久化 
// 雪花算法 ID 结构（64 位）：
// ┌──1 位符号位──┬───41 位时间戳───┬──10 位机器 ID──┬──12 位序列号──┐
//     0          毫秒级时间差      机器+进程       同一毫秒递增

实际推荐：大多数场景用雪花算法（MyBatis-Plus 的 IdType.ASSIGN_ID 就是雪花算法实现），可配合美团 Leaf 或滴滴 TinyId 增强可靠性。

5.2 跨分片查询怎么办

这是分库分表最大的痛点——要查的数据分散在多个表里。

场景一：非分片键查询

分片键是 user_id，但要按 order_status 查所有”待支付”订单，只能把每个表都查一遍再合并：

// 这种查询要扫所有表，性能很差
List<Order> allOrders = new ArrayList<>();
for (int i = 0; i < 4; i++) {
    List<Order> orders = jdbcTemplate.query(
        "SELECT * FROM order_" + i + " WHERE status = ?",
        rowMapper, "UNPAID");
    allOrders.addAll(orders);
}

解法：

  • 建映射表（user_id → order_id），先用 userId 查映射表，再精确查询；
  • 异构索引：把数据同步到 Elasticsearch，ES 负责多维度查询，MySQL 只做分片键查询；
  • 基因法：把分片键信息编码到 ID 中，从 ID 反推出分片键。

场景二：跨分片 JOIN

分库分表后，ORDER BY、GROUP BY、JOIN、分页都会变得复杂。ShardingSphere 虽支持，但本质是在内存里合并排序，数据量大时性能堪忧。

最佳实践：尽量避免跨分片查询。设计分片键时充分考虑业务查询模式，让 80% 以上的查询都落在单个分片上。

5.3 分布式事务

单库事务靠 MySQL 的 UNDO/REDO 日志就能保证 ACID；分库后一个业务操作可能涉及多个数据库，事务保证难度陡增：

一个下单操作：
  扣库存（product_db）
  创建订单（order_db）
  扣余额（user_db）
这三个操作必须要么全成功，要么全失败！
方案 原理 适用场景
Seata AT 模式 自动回滚，对业务无侵入 强一致性要求
Seata TCC 模式 Try-Confirm-Cancel，需业务实现 一致性要求极高的场景
RocketMQ 事务消息 半消息 + 事务状态回查 最终一致性即可的场景
本地消息表 业务操作 + 消息表同库写入 简单场景

实用建议：大多数互联网业务不需要强一致性，用”本地消息表 + 定时任务补偿”保证最终一致性就够了，不要为了技术而技术。

5.4 数据迁移和历史数据归档

不可能一开始就分 64 张表——过度设计比不设计更可怕。通常先跑单表，数据量上来再拆分。平滑迁移思路：双写 → 历史数据迁移 → 读切换 → 单写新表。

步骤 1：新数据同时写旧表和新表（双写）
步骤 2：把历史数据迁移到新表（Canal + 消息队列，或定时任务分批跑）
步骤 3：读流量逐步切到新表（灰度发布）
步骤 4：割接完成，旧表下线

数据迁移一定要在业务低峰期操作，并做好数据校验。

七、动手建议

第一次接触分库分表，建议按这个节奏来：

  1. 先搞懂概念：垂直切 vs 水平切，Range vs Hash；
  2. 搭一个 Demo：ShardingSphere-JDBC + Spring Boot，本地起 2 个 MySQL 实例、建 4 张表，跑一遍 CRUD；
  3. 感受坑：写跨分片查询、尝试分页、做一次扩容数据迁移；
  4. 读源码：ShardingSphere 的路由引擎、SQL 改写、结果归并值得一读。

八、总结

分库分表本质上是用空间和复杂度换性能的手段。它不应该是接到需求后第一个想到的方案，而是用尽 SQL 优化、加缓存、读写分离等手段后依然扛不住时才使出的终极武器。

三个核心原则：

  1. 分片键是命根子——选错分片键，后面所有查询都是跨分片的，性能比不分还差；
  2. 能不分就不分——先优化 SQL、加索引、上缓存、读写分离，都试过了再分；
  3. 用中间件，别自己造轮子——ShardingSphere 已经帮你处理了 90% 的复杂度。
