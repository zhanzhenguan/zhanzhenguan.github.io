这篇是 Spring Boot 系列第二十七部分，用 Spring Boot 3 写一个对象存储服务，对外提供上传、查询、预签名外链、下载、删除五个接口。技术栈：Spring Boot 3.5.16、JDK 17、minio-java 8.6.0、MinIO Server。代码为通用示例，端点与凭据按实际环境调整并做好脱敏。

一、目标与接口设计

1.1 五个接口

方法 路径 作用
POST /oss/upload 上传文件，返回服务端生成的对象名
GET /oss/info 查询对象大小、MIME 类型、ETag
GET /oss/url 生成有时效的预签名 GET 链接
GET /oss/download 流式下载文件
DELETE /oss/delete 删除对象

应用默认跑在 8099 端口，MinIO 的 S3 API 在 9000，Web Console 在 9001。

1.2 两个提前定下的设计决定

桶保持私有，对外只读走预签名 URL。 很多示例会把桶策略设成 public read，然后直接拼 http://ip:9000/bucket/object 当外链。这在测试环境很方便，但等于把整个桶暴露出去。本工程不设置任何桶策略，外链由服务端按次签发、带过期时间，实测无签名直连返回 403。

对象名由服务端生成，客户端只拿到结果。 上传接口返回的 objectName 格式是 yyyy/MM/dd/<32位UUID>.<小写扩展名>。不用原始文件名，可以避免重名覆盖、中文与空格带来的 URL 编码问题，也避免客户端通过文件名注入路径。

二、环境与版本基线

2.1 版本选型：Boot 3.5.16 + minio-java 8.6.0

Spring Boot 用 3.5.16（JDK 17 兼容的 3.x 稳定版本），MinIO Java SDK 用 8.6.0。选型依据：

  • minio-java 8.6.0 是 8.x 稳定线最后一个版本，包含依赖升级与 CVE-2025-48924 修复；
  • 9.0.0 是整体重构的主版本，官方说明为「Refactor entire code for v9.0.0」「Sync APIs with S3 specification」，API 与 8.x 有明显差异，教程工程代码采用它的风险更高；
  • 8.6.0 发布时间晚于本机服务端，兼容性有保障；更早期的 8.2.x 属于 2021 年版本，与 2025 年服务端和 JDK 17 组合并不合适。

结论：选 8.x 稳定线的终点，不选刚重构完的 9.x，也不选五年前的旧版。

2.2 命名空间说明

本工程使用 Jakarta 命名空间（jakarta.validation.*、jakarta.servlet.*），内嵌 Tomcat 10.1.x，这是 Spring Boot 3 的标准组合。如果照 2.x 时代的代码写 javax.*，在 3.x 上会直接编译失败。

三、先分清 9000 和 9001

3.1 现象

本机 MinIO 在浏览器里打开的地址是 http://127.0.0.1:9001/browser，这是 Web Console；但 Java SDK 需要的是 S3 API 地址。两个端口同时监听，很容易填错。

3.2 结论

minio.endpoint 必须填 http://127.0.0.1:9000。填 9001 时，SDK 发出的 S3 请求会打到 Console 上，得到 HTML 页面或认证失败，典型报错是解析响应失败或 InvalidAccessKeyId。

一个直观判断方法：能返回 application/xml 且带 Server: MinIO 响应头的，才是 S3 API 端口。

3.3 先用签名请求核实凭据，别急着写代码

Console 的登录凭据与 S3 的 Access Key / Secret Key 在单节点部署下通常是同一组，但登录名不一定等于 Access Key。接入前先用一个最小的 AWS SigV4 请求验证，避免把错误凭据写进配置后反复排查：返回 200 并带 <ListAllMyBucketsResult> 就说明这组凭据能用于 S3 API；如果返回 403 InvalidAccessKeyId，先核对 Access Key，不要往下写代码。

四、创建 Maven 工程

4.1 pom.xml 关键依赖

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-validation</artifactId>
    </dependency>
    <dependency>
        <groupId>io.minio</groupId>
        <artifactId>minio</artifactId>
        <version>8.6.0</version>
        <exclusions>
            <!-- 排除 okhttp 5.x 空壳根模块 -->
            <exclusion>
                <groupId>com.squareup.okhttp3</groupId>
                <artifactId>okhttp</artifactId>
            </exclusion>
        </exclusions>
    </dependency>
    <!-- 真正的 okhttp3 类在 jvm 变体里 -->
    <dependency>
        <groupId>com.squareup.okhttp3</groupId>
        <artifactId>okhttp-jvm</artifactId>
        <version>5.1.0</version>
    </dependency>
</dependencies>

4.2 第一个坑：okhttp 5.x 的空壳 jar

第一次 mvn clean package 直接编译失败，根因不在业务代码，而在依赖解析：minio-java 8.6.0 的 POM 声明了 com.squareup.okhttp3:okhttp:5.1.0，但 okhttp 从 5.x 起是 Kotlin Multiplatform 工程，Maven Central 上的 okhttp-5.1.0.jar 只有 767 字节，是个不含类的根模块；真正的 okhttp3.* 类在 okhttp-jvm-5.1.0.jar（约 860 KB）里。

Gradle 会读 Gradle metadata 自动定位到 jvm 变体，而 Maven 只认 POM，于是编译期找不到类。修复方式就是上面 pom 里的两段：排除空壳 okhttp，显式引入 okhttp-jvm。判断依据是构建日志里那句 Downloaded ... okhttp-5.1.0.jar (767 B)——jar 小得反常。

五、配置文件与凭据隔离

5.1 application.yml

minio:
  endpoint: http://127.0.0.1:9000
  access-key: ${MINIO_ACCESS_KEY:}
  secret-key: ${MINIO_SECRET_KEY:}
  bucket: springboot-minio-demo
  presigned-expiry-seconds: 3600

logging:
  charset:
    console: UTF-8

logging.charset.console: UTF-8 避免 Windows 控制台把中文日志打成乱码；文件大小限制放在配置里，比在代码里硬编码更合适。

5.2 凭据隔离

主配置里全是占位符，真实凭据放在单独的 application-local.yml，默认激活 local profile，并在 .gitignore 中忽略该文件。这样工程拷给别人时，对方按自己的 MinIO 填一遍即可，主配置可以直接进版本库。所有配置项都支持环境变量覆盖，部署时无需改文件。

六、类型安全的配置属性

配置类不用散落的 @Value，而是用 Spring Boot 3 推荐的构造器绑定。record 是不可变的，字段集中、便于单元测试：

@ConfigurationProperties(prefix = "minio")
public record MinioConfig(
        String endpoint,
        String accessKey,
        String secretKey,
        String bucket,
        int presignedExpirySeconds) {
}

minio.access-key 通过宽松绑定映射到 accessKey 组件，minio.presigned-expiry-seconds 映射到 presignedExpirySeconds。配置 Bean 装配前检查必填项，凭据为空时直接抛 IllegalStateException 并给出提示，不会等到调用接口才报认证错误。

七、装配 MinioClient 与启动校验

MinioClient 是线程安全的，全局一个 Bean 即可，不需要每次请求新建。它是纯客户端，构造时不会发起网络请求，所以「启动校验」做的是配置完整性检查，真正的连通性由建桶动作验证：

@Bean
public MinioClient minioClient(MinioConfig config) {
    return MinioClient.builder()
            .endpoint(config.endpoint())
            .credentials(config.accessKey(), config.secretKey())
            .build();
}

八、启动时自动创建存储桶

三个要点：

  1. 用 ApplicationRunner 而不是 InitializingBean：Runner 在所有 Bean 就绪、上下文刷新完成后执行，时序更清晰，也便于拿到完整配置；
  2. 先查后建，天然幂等：多次启动不会重复创建，第二次启动日志为「存储桶已存在，跳过创建」；
  3. 不设置桶策略：保持私有。若需要公开读，应显式设置策略，而不是默认放开。
@Component
@RequiredArgsConstructor
public class MinioBucketInitializer implements ApplicationRunner {

    private final MinioClient minioClient;
    private final MinioConfig config;

    @Override
    public void run(ApplicationArguments args) throws Exception {
        boolean exists = minioClient.bucketExists(BucketExistsArgs.builder().bucket(config.bucket()).build());
        if (!exists) {
            minioClient.makeBucket(MakeBucketArgs.builder().bucket(config.bucket()).build());
        }
    }
}

这里带来一个明确的启动依赖：MinIO 不可达时应用会启动失败（快速失败）。对教程工程这是优点——连通性问题第一时间暴露；多实例生产部署时可以把建桶挪到运维初始化步骤。

九、对象名的生成与安全校验

9.1 生成规则

扩展名只接受 1~10 位字母数字并统一转小写，其他一律丢弃。上传 pixel.PNG 得到的对象名形如 2026/11/27/98075d4376354827bbe35915c36df03a.png。

9.2 校验规则

objectName 是外部可控入参，如果不校验就拼进 S3 请求路径，风险很直接。校验放在一个无依赖的工具类里：拦截 ../、绝对路径、双斜杠、反斜杠、NUL 与控制字符，再用白名单正则收口。所有信息查询、外链、下载、删除接口在操作前都会调用它。

9.3 单元测试覆盖

对象名校验工具类配若干纯单测，覆盖空值、路径穿越、非法字符、超长、正常名称、生成名安全性。它们不依赖 Spring 上下文和 MinIO，执行时间毫秒级。

十、封装五个存储操作

MinioStorageService 统一持有 MinioClient 与配置属性，对 Controller 只暴露业务语义方法。

10.1 上传

putObject 的 stream(in, size, -1) 中 -1 表示由 SDK 决定分片大小；小文件走单次 PUT，大文件自动分片。流用 try-with-resources 关闭，避免连接泄漏。

10.2 统一判定「对象不存在」

信息查询、外链、下载、删除都需要先确认对象存在，所以抽出一个私有方法：沿异常链检查 ErrorResponseException 的 S3 错误码（NoSuchKey / NoSuchObject / NoSuchBucket）与消息关键字。MinIO 不同版本对不存在对象返回的错误码不完全一致，只判一个码容易漏判。

10.3 生成预签名外链

两个边界值得注意：有效期上限 7 天是 S3 预签名机制的约束；签发前先 statObject，避免给一个不存在的对象生成「能打开但必然 404」的链接。

注意：X-Amz-Credential 里本来就包含 Access Key，这是 S3 规范，不是 Secret Key 泄露；但分享链接时仍应谨慎，因为链接在有效期内等同于一次授权访问。

10.4 下载

返回的是 InputStream，由 Controller 在写出时关闭，不把整个文件读进内存。

10.5 删除

S3 的删除本身是幂等的，这里先查存在性是为了让重复删除返回明确的 404，便于调用方感知状态。

十一、编写 REST 接口

11.1 控制器

类上的 @Validated 让方法参数上的 @Min / @Max 生效，校验失败抛 ConstraintViolationException，由全局异常处理器映射为 400。

11.2 下载为什么用 StreamingResponseBody

StreamingResponseBody 边读边写，内存占用与文件大小无关；filename*=UTF-8'' 是 RFC 5987 写法，保证中文文件名不乱码。实测响应头为 attachment; filename*=UTF-8''<对象名>。

十二、统一响应与异常映射

12.1 状态码约定

状态码 场景
200 操作成功
400 对象名非法、路径穿越、空文件、缺参、参数类型错误、有效期越界、非 multipart 请求
404 对象不存在、接口或静态资源不存在
405 请求方法不支持
413 文件超过大小限制
415 媒体类型不支持
502 MinIO 服务访问失败

12.2 第二个坑：参数错误被兜底成 500

首轮端到端补测发现：Spring MVC 抛出的 MultipartException、MethodArgumentTypeMismatchException 等参数异常没有被精确映射，落进了 @ExceptionHandler(Exception.class) 兜底，客户端一个拼写错误就在服务端留下一条 ERROR 堆栈。补齐显式映射即可。

教训：只要写了 @ExceptionHandler(Exception.class) 兜底，就必须把常见的 Spring MVC 参数异常逐个显式映射，否则客户端的参数错误会在服务端看起来像系统故障。

12.3 第三个坑：favicon 触发 500 堆栈

浏览器打开应用首页会自动请求 /favicon.ico，Spring 6 抛 NoResourceFoundException，同样会被兜底 handler 包装成 500 并打印整段堆栈。显式加一条映射后返回 404，日志保持干净。

最终全局异常处理器应精确覆盖 IllegalArgumentException、缺参、缺文件、参数类型不匹配、非 multipart、校验失败、请求体不可读、文件过大、方法不支持、媒体类型不支持、对象不存在、存储异常、接口/静态资源不存在等十多类异常，最后才留一个 Exception.class 兜底。

十三、编译、启动与实测验证

13.1 构建与单元测试

集成测试在启动 Spring 上下文时真实连接 MinIO，输出「MinIO 存储桶创建成功」，说明配置绑定、客户端装配、建桶逻辑整条链路可用。

13.2 端到端验证

类别 验证点
上传 文本文件、PNG 图片、对象名按日期分目录、扩展名小写、大小一致
信息 大小、ETag
外链 默认 3600 秒、自定义 120 秒、URL 含签名参数

在 MinIO Console（http://127.0.0.1:9001/browser）进入对应桶，能看到按日期分目录的对象；上传成功后刷新可见，删除后对象消失。Console 只用来观察结果，所有读写都走应用接口。

十四、常见问题

现象 根因与处理
启动报认证失败或响应解析失败 查 minio.endpoint：填成 9001（Console）会拿到 HTML；S3 API 端口应返回 application/xml 的 403，而不是 text/html 的 200
InvalidAccessKeyId S3 Access Key 与 Console 登录名不一定一致，先用 SigV4 自检脚本验证，再写配置
预签名 URL 打不开 依次排查桶名/对象名是否正确、URL 是否已过期、应用与 MinIO 地址是否可达；服务端配置外网地址而本机用 127.0.0.1 时，签发 URL 的 host 可能与客户端可达地址不一致，需统一 MINIO_ENDPOINT
编译报「找不到 okhttp3.HttpUrl 的类文件」 见 4.2：排除 okhttp:5.1.0，显式引入 okhttp-jvm:5.1.0
中文日志或文件名乱码 控制台加 logging.charset.console: UTF-8；下载响应用 filename*=UTF-8'' 编码；CMD 仍乱码执行 chcp 65001
参数写错返回 500 并打印堆栈 见 12.2：把 MultipartException、MethodArgumentTypeMismatchException 等 Spring MVC 参数异常显式映射为 400，不要只留 Exception.class 兜底

十五、生产化建议

  1. 凭据管理：通过环境变量或密钥管理服务注入，定期轮换，绝不写进公开仓库；
  2. 传输安全：MinIO 与应用之间启用 HTTPS，避免预签名 URL 和凭据在明文链路传输；
  3. 最小权限：为应用单独创建只读/只写限定桶的 Service Account，不要直接用 root 凭据；
  4. 外链治理：按最小有效期签发，考虑绑定客户端 IP、单次下载、审计日志；链接含 Access Key，分享需谨慎；
  5. 上传治理：补充文件类型白名单、病毒扫描、限流；超过大小上限改用分片上传或客户端直传（后端只签发临时凭证）；
  6. 可观测性：记录对象名、大小、耗时、失败原因；桶配置生命周期规则清理过期对象，配置容量与请求量告警；
  7. 启动依赖：建桶初始化让 MinIO 成为强依赖，多实例部署时可改为运维初始化或降级告警；
  8. 映射关系落库：对象名与业务主键、上传者、业务标签的对应关系建议持久化，便于审计、回溯与清理。

十六、小结

  1. 先把环境事实搞清楚——9000 与 9001 的区别、服务端版本、凭据是否真的能调 S3 API。这三件事没确认就写代码，后面所有报错都会变得难以归因。
  2. 把安全边界设在服务端——桶私有、对象名服务端生成、外部对象名白名单校验、外链按次签发并设上限。对象存储最容易被忽略的风险就是「顺手把桶设成 public」。
  3. 异常要精确到状态码——Exception.class 兜底不是错误处理，只是最后一道防线。参数错误、对象不存在、存储服务异常应当分别返回 400 / 404 / 502，日志里才不会出现「客户端拼错参数、服务端打印 ERROR 堆栈」这种假故障。
