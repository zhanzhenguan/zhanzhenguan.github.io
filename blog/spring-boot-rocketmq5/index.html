这篇是 Spring Boot 系列第十部分，整合 RocketMQ 5.x。技术栈：JDK 17 + Spring Boot 3.5.7 + RocketMQ 5.3.1 + rocketmq-v5-client-spring-boot-starter 2.3.6。5.x 接入方式与 4.x 差异较大，本文按 5.x 的 gRPC Proxy 模式梳理。代码为通用示例，连接信息用占位符。

一、5.x 架构与 4.x 差异

RocketMQ 5.x 在 Broker 前增加了 Proxy 接入层：新版客户端（rocketmq-client-java）通过 gRPC 协议连接 Proxy，不再直连 NameServer。

[应用: Spring Boot 3 + v5 starter]
        │ gRPC（endpoints，默认 8081）
        ▼
[Proxy] ──▶ [Broker: 存储 / 投递]
        │ 注册 / 路由
        ▼
[NameServer: 默认 9876]

两套 Starter 核心区别：

对比项 4.x：rocketmq-spring-boot-starter 5.x：rocketmq-v5-client-spring-boot-starter
底层协议 Remoting gRPC
发送模板 RocketMQTemplate RocketMQClientTemplate
接入地址 name-server（9876） endpoints（Proxy 8081）
监听接口 RocketMQListener<T>.onMessage(T) RocketMQListener.consume(MessageView)，返回 ConsumeResult
消息类型 API 隐含 按 Normal/FIFO/Delay/Transaction 明确区分，须与 Topic 类型匹配

两个最容易搞错的点：

  • endpoints 指向 Proxy 的 gRPC 端口 8081，不是 NameServer 的 9876；
  • 消息类型必须与 Topic 类型匹配，向 NORMAL 类型 Topic 发延迟消息会报消息类型不匹配错误。

二、服务端准备

2.1 启动三件套

本地开发用官方二进制包，依次启动 NameServer、Broker（带 Proxy），必要时单独启动 Proxy：

# 1) NameServer
nohup sh bin/mqnamesrv &

# 2) Broker + Proxy 同进程（Local 模式）
nohup sh bin/mqbroker -n localhost:9876 --enable-proxy &

# 3) 若 Broker 未带 --enable-proxy，可单独启动 Proxy 进程
nohup sh bin/mqproxy -n 127.0.0.1:9876 &

日志出现 grpc server start successfully 且 8081 端口监听正常即可。

2.2 按消息类型创建 Topic

5.x 客户端启动时预取路由，Topic 不存在会导致启动失败，必须先建后用，且一个 Topic 只承载一种消息类型：

NS=127.0.0.1:9876
bin/mqadmin updateTopic -n $NS -c DefaultCluster -t OrderNormalTopic    -a "+message.type=NORMAL"
bin/mqadmin updateTopic -n $NS -c DefaultCluster -t OrderFifoTopic     -a "+message.type=FIFO"
bin/mqadmin updateTopic -n $NS -c DefaultCluster -t OrderDelayTopic     -a "+message.type=DELAY"
bin/mqadmin updateTopic -n $NS -c DefaultCluster -t OrderTransTopic    -a "+message.type=TRANSACTION"

坑点：-a 后属性值的加号必须紧跟 key，写成 "+message.type=NORMAL"；加号后带空格会报 unsupported key: message.type。

四、生产者封装

在业务代码与 Template 之间加一层薄封装，统一做三件事：JSON 字符串作为消息体、对 SendReceipt 判空、统一日志与异常。

@Slf4j
@Service
@RequiredArgsConstructor
public class MqProducer {

    private final RocketMQClientTemplate template;
    private final ObjectMapper objectMapper;

    /** 普通消息，destination 格式：topic 或 topic:tag */
    public SendReceipt sendNormal(String destination, Object event) {
        SendReceipt receipt = template.syncSendNormalMessage(destination, json(event));
        return verify(destination, receipt);
    }

    /** 顺序消息：同一 messageGroup 内严格 FIFO（Topic 必须为 FIFO 类型） */
    public SendReceipt sendFifo(String destination, Object event, String messageGroup) {
        SendReceipt receipt = template.syncSendFifoMessage(destination, json(event), messageGroup);
        return verify(destination, receipt);
    }

    /** 延迟消息（Topic 必须为 DELAY 类型） */
    public SendReceipt sendDelay(String destination, Object event, Duration delay) {
        SendReceipt receipt = template.syncSendDelayMessage(destination, json(event), delay);
        return verify(destination, receipt);
    }

    private SendReceipt verify(String destination, SendReceipt receipt) {
        if (receipt == null) {
            throw new MqSendException("MQ send failed, no receipt: " + destination);
        }
        log.info("MQ sent, dest={}, messageId={}", destination, receipt.getMessageId());
        return receipt;
    }

    private String json(Object event) {
        if (event instanceof String s) {
            return s;
        }
        try {
            return objectMapper.writeValueAsString(event);
        } catch (JsonProcessingException e) {
            throw new MqSendException("MQ payload serialize failed", e);
        }
    }
}

要点：

  • 顺序消息的 messageGroup 选需要保序的业务实体 ID（如订单号），同组内严格 FIFO，不同组之间不保序；
  • 异步回调要挂在方法返回的 CompletableFuture 上，不要挂在入参 future 上。

五、消费者开发

5.1 消息体解析

5.x 消费端拿到的是 MessageView，getBody() 返回 ByteBuffer，需自行转字符串：

public final class MqMessages {
    private MqMessages() {}

    public static String bodyAsString(MessageView view) {
        ByteBuffer buffer = view.getBody();
        byte[] bytes = new byte[buffer.remaining()];
        buffer.get(bytes);
        return new String(bytes, StandardCharsets.UTF_8);
    }
}

5.2 普通消费者与异常策略

@Slf4j
@Component
@RequiredArgsConstructor
@RocketMQMessageListener(
        consumerGroup = "GID_order_created",
        topic = "${app.mq.normal-topic:}",
        tag = "created")
public class OrderCreatedConsumer implements RocketMQListener {

    private final ObjectMapper objectMapper;
    private final OrderNotifyService notifyService;

    @Override
    public ConsumeResult consume(MessageView messageView) {
        String body = MqMessages.bodyAsString(messageView);
        try {
            OrderCreatedEvent event = objectMapper.readValue(body, OrderCreatedEvent.class);
            notifyService.handle(event);   // 内部做幂等
            return ConsumeResult.SUCCESS;
        } catch (JsonProcessingException e) {
            // 格式错误，重试无意义：记录后确认，避免毒消息反复重投
            log.error("bad payload, messageId={}", messageView.getMessageId(), e);
            return ConsumeResult.SUCCESS;
        } catch (Exception e) {
            log.warn("consume failed, messageId={}", messageView.getMessageId(), e);
            return ConsumeResult.FAILURE;   // 触发重试
        }
    }
}

异常处理原则：可重试错误（数据库、下游超时）返回 FAILURE 退避重试；不可重试错误（消息格式错）记录后返回 SUCCESS。超过最大重试次数（默认 16 次）进入死信队列 %DLQ%{consumerGroup}，需配置告警。

5.3 幂等消费

RocketMQ 保证至少一次投递，网络抖动、消费超时、重平衡都会产生重复消息，消费端必须幂等。推荐业务唯一键 + 唯一索引，且幂等记录与业务处理在同一本地事务：

@Service
@RequiredArgsConstructor
public class IdempotentService {

    private final JdbcTemplate jdbcTemplate;

    /** 返回 true 表示首次处理；false 表示重复消息 */
    public boolean tryAcquire(String consumerGroup, String bizKey) {
        try {
            jdbcTemplate.update(
                    "INSERT INTO mq_consume_log(consumer_group, biz_key) VALUES (?, ?)",
                    consumerGroup, bizKey);
            return true;
        } catch (DuplicateKeyException e) {
            return false;
        }
    }
}

幂等键优先用业务主键（订单号）。messageId 只能挡住 Broker 侧重投，挡不住生产端业务重发。

5.4 顺序与延迟消费者

顺序消费者写法与普通消费者一致，区别只在订阅 FIFO Topic。同一 messageGroup 的消息按顺序串行到达，业务代码不要再丢线程池并发处理。

延迟消息到点只是「触发一次检查」，必须按业务状态幂等判断：例如超时关单时，仅当订单仍为 CREATED 才关闭，已支付/已关闭则幂等跳过。

六、事务消息：下单与库存扣减最终一致

事务消息解决「本地数据库事务」与「消息发送」之间的最终一致性。5.x 流程：

  1. 生产者发送半消息到 Broker，此时消费者不可见；
  2. 生产者执行本地事务（如写订单表）；
  3. 根据结果调用 commit() 或 rollback()；
  4. 若 Broker 长时间未收到二次确认，回查应用侧的 RocketMQTransactionChecker.check()。

与 4.x 的关键区别：本地事务由调用方在发送之后自行执行并提交/回滚，监听器只负责回查。

@Slf4j
@Service
@RequiredArgsConstructor
public class OrderTxService {

    private final RocketMQClientTemplate template;
    private final TransactionTemplate transactionTemplate;
    private final OrderRepository orderRepository;
    private final ObjectMapper objectMapper;
    private final MqTopicProperties topics;

    public void createOrder(OrderCreatedEvent event) throws Exception {
        Message msg = MessageBuilder
                .withPayload(objectMapper.writeValueAsString(event))
                .setHeader("orderNo", event.orderNo())
                .build();

        // 1. 发送半消息（消费者暂不可见）
        String dest = topics.transTopic() + ":created";
        Pair<SendReceipt, Transaction> pair = template.sendTransactionMessage(dest, msg);
        Transaction tx = pair.getTransaction();

        // 2. 执行本地事务
        try {
            transactionTemplate.executeWithoutResult(status -> orderRepository.save(event));
        } catch (Exception e) {
            tx.rollback();   // 3a. 本地事务失败：回滚半消息
            throw e;
        }
        tx.commit();         // 3b. 本地事务成功：提交半消息
    }
}

回查逻辑必须只读、可重复执行，用业务主键查本地表，不依赖内存状态：

@Slf4j
@RocketMQTransactionListener
@RequiredArgsConstructor
public class OrderTransactionChecker implements RocketMQTransactionChecker {

    private final OrderRepository orderRepository;

    @Override
    public TransactionResolution check(MessageView messageView) {
        String orderNo = messageView.getProperties().get("orderNo");
        if (orderNo == null) {
            return TransactionResolution.ROLLBACK;
        }
        try {
            return orderRepository.existsByOrderNo(orderNo)
                    ? TransactionResolution.COMMIT
                    : TransactionResolution.ROLLBACK;
        } catch (Exception e) {
            log.warn("check local tx failed, orderNo={}", orderNo, e);
            return TransactionResolution.UNKNOWN;   // 暂时无法判断，稍后再次回查
        }
    }
}

注意：TransactionTemplate 不在 Spring Boot 自动装配范围内，直接注入会报 NoSuchBeanDefinitionException，需要手动声明 Bean。

七、踩坑汇总

# 坑 现象 解决
1 mqadmin 属性格式 unsupported key: message.type -a "+message.type=NORMAL"，加号紧跟 key，不能有空格
2 端口冲突 应用 8080 启动失败 Proxy 占用 8080 作 Remoting 端口，应用换 8088
3 异步回调不触发 回调挂在入参 future 上 挂在 asyncSend 方法返回的 CompletableFuture 上
4 TransactionTemplate 注入失败 NoSuchBeanDefinitionException 它不在自动装配范围，手动 @Bean 声明

八、生产注意事项

  1. Topic 规划：一个业务事件一个 Topic，一个 Topic 只承载一种消息类型；
  2. 消费端必须幂等：至少一次投递语义下，重复消息是常态而非异常；
  3. endpoints 别填错：指向 Proxy（8081），不是 NameServer（9876）；
  4. 顺序消费有代价：某条消息反复重试会阻塞同组后续消息，不可重试的错误记录后返回 SUCCESS。

九、小结

  • RocketMQ 5.x 客户端经 gRPC 连 Proxy，模板换成 RocketMQClientTemplate，消费接口返回 ConsumeResult，消息类型须与 Topic 匹配；
  • 生产者封装普通、顺序、延迟、事务四类消息；消费者解析 MessageView，按错误类型决定重试还是确认；
  • 幂等靠业务唯一键 + 唯一索引，并与业务处理同事务；事务消息走半消息 → 本地事务 → 提交/回滚 → 回查的最终一致流程；
  • 重点避开属性格式、端口冲突、异步回调挂载点、TransactionTemplate 手动装配这几类坑。
