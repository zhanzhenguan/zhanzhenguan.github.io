一、版本基线：版本交给 BOM 管理

结论：Spring Boot 3.5.16 + Spring Kafka 3.3.16 + kafka-clients 3.9.2 + JDK 17。

组件 版本 说明
JDK 17 Spring Boot 3.x 最低基线，也是 Kafka 3.9 官方推荐版本
Spring Boot 3.5.16 3.5 系列 OSS 版本
Spring for Apache Kafka 3.3.16 由 Spring Boot 3.5.16 依赖管理，无需手动指定
Apache Kafka Broker 3.9.2 3.x 系列补丁版本
kafka-clients 3.9.2 由 Spring Boot 3.5.16 统一管理

关键原则：spring-kafka 和 kafka-clients 的版本都交给 Spring Boot BOM 管理，不要在 pom 里手写版本号。Boot 3.5.16 管理的就是 spring-kafka 3.3.16 + kafka-clients 3.9.2，与 3.9.2 Broker 同协议系列。若公司父 POM 或 BOM 覆盖了版本，先看依赖树再动手：

mvn dependency:tree -Dincludes=org.apache.kafka,org.springframework.kafka

看到 kafka-clients:3.9.2 且只有一个版本即可。版本状态提醒：3.9.2 在官方归档列表中，受支持发布线已进入 4.x；选 3.9.2 适合学习、维护已有 3.x 集群和兼容性验证，全新生产项目应评估 Kafka 4.x。

二、用 Docker 跑起 Broker（KRaft，无 ZooKeeper）

本地开发不再在 Windows 上装二进制包，直接用官方 apache/kafka 镜像以 KRaft 模式单节点启动，无需 ZooKeeper。前置条件：Docker Desktop / Docker Engine 已运行，宿主机 9092 端口未被占用，镜像 apache/kafka:3.9.2（拉取失败可降级到 3.9.1 或 latest）。

2.1 方式一：docker run

Linux / macOS / WSL：

docker rm -f kafka 2>/dev/null || true

docker run -d --name kafka --hostname kafka \
  -p 9092:9092 \
  -v kafka-data:/tmp/kraft-combined-logs \
  -e KAFKA_NODE_ID=1 \
  -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP="CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT" \
  -e KAFKA_ADVERTISED_LISTENERS="PLAINTEXT_HOST://localhost:9092,PLAINTEXT://kafka:19092" \
  -e KAFKA_LISTENERS="CONTROLLER://:29093,PLAINTEXT_HOST://:9092,PLAINTEXT://:19092" \
  -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS="1@kafka:29093" \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  -e CLUSTER_ID="4L6g3nShT-eMCtK--X86sw" \
  -e KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1 \
  -e KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=1 \
  -e KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=1 \
  -e KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS=0 \
  -e KAFKA_LOG_DIRS=/tmp/kraft-combined-logs \
  apache/kafka:3.9.2

Windows PowerShell 参数一致，续行符换成反引号：

--hostname kafka 不能省：KRaft 控制器投票者 1@kafka:29093 要靠这个主机名解析到本容器；纯 docker run 不显式指定 hostname 时，容器内主机名默认是容器 ID，会导致控制器选主失败。

启动与清理：

docker compose down -v    # 停止并清空数据卷，重置集群

2.3 监听器与连接地址

监听器 地址 用途
PLAINTEXT_HOST localhost:9092 宿主机上的应用、命令行客户端连接
PLAINTEXT kafka:19092 同一 Docker 网络内其他容器互连
CONTROLLER kafka:29093 KRaft 内部控制器通信，不对外暴露

宿主机应用连 127.0.0.1:9092；若另一个应用也容器化，加入同一网络后连 kafka:19092，不要填 localhost。advertised.listeners 必须填客户端实际用来连接的地址，填错会出现「能连上但拿不到分区元数据」的问题。

2.4 验证 Broker 是否存活

docker exec -it kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

输出为空、命令不报错就是成功——刚初始化的集群本来就没有 topic。连不上时会阻塞约 60 秒抛 TimeoutException；「秒回 + 空输出 + 无异常」即已连上。

2.5 几个注意点

  • 持久化：数据落在命名卷 kafka-data，挂载到容器内 /tmp/kraft-combined-logs；只删容器不丢数据，删卷才清空历史消息与位点。
  • CLUSTER_ID：开发用固定值即可；换全新集群时用 docker run --rm apache/kafka:3.9.2 /opt/kafka/bin/kafka-storage.sh random-uuid 重新生成，并清空旧数据卷后再启动。
  • 单节点配置仅用于本地开发：PLAINTEXT 无认证、单副本；生产环境应多副本多 Broker、配 SASL/SSL，Topic 与 ACL 由运维流程统一管理。

四、application.yml：可靠性配置

spring:
  kafka:
    bootstrap-servers: 127.0.0.1:9092
    producer:
      acks: all
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
      properties:
        enable.idempotence: true
        retries: 2147483647
        delivery.timeout.ms: 120000
    consumer:
      group-id: order-service-group
      enable-auto-commit: false
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
    listener:
      ack-mode: record
      concurrency: 3

逐项说明：

配置 含义 为什么
acks: all 等待 ISR 全部确认 配合 min.insync.replicas 才有完整意义；本地单副本环境先养成习惯
enable.idempotence: true 幂等生产者 Broker 按 ProducerID + 序列号去重，避免重试导致重复写入；只保证生产端会话内不重，不能替代消费端业务幂等
retries: 2147483647 生产者发送重试次数 配合幂等与 delivery.timeout.ms；没有幂等时无限重试会制造重复消息，两者必须一起出现
delivery.timeout.ms: 120000 发送总超时 重试的时间上限；形式上的「无限重试」真正的边界是这里
enable-auto-commit: false 关闭客户端自动提交 交给 Listener Container 管理，避免「消息还没处理完 Offset 就提交」导致丢消息
auto-offset-reset: earliest 无有效 Offset 时从头消费 只影响从未提交过 Offset 的新消费组，不影响已有进度的组
ack-mode: record 单条处理成功后提交 逐条消费最易理解；批量场景再评估 batch 模式
concurrency: 3 监听容器并发线程数 每个 @KafkaListener 起 3 个消费者实例；不应盲目大于分区数

两个易混淆概念：生产者 retries 是发送请求失败后的客户端重试；消费重试是业务监听器抛异常后的重新投递，二者不是一回事。序列化用 String，消息体在业务代码里用 Jackson 转 JSON 字符串，这样死信队列可原样保存消息文本，也避免跨服务传类型头带来的耦合。

五、Topic 声明：交给 KafkaAdmin

应用启动时 KafkaAdmin 自动创建 Topic，开发联调无需敲命令行：

@Configuration
public class KafkaTopicConfig {

    @Bean
    public NewTopic orderCreatedTopic() {
        return TopicBuilder.name("order-created")
                .partitions(6)
                .replicas(1)
                .build();
    }

    @Bean
    public NewTopic orderCreatedDlt() {
        return TopicBuilder.name("order-created-dlt")
                .partitions(6)
                .replicas(1)
                .build();
    }
}

两点提醒：

  1. 分区数决定消费并行度上限：一个消费组同一时刻最多只有「分区数」个消费者在干活；
  2. 生产环境不要依赖应用启动时自动建 Topic。Topic、ACL、保留策略应由运维或发布流程统一管理，NewTopic 声明只适合开发与联调环境。DLT 分区数必须不小于源 Topic，因为失败消息按同编号分区映射。

六、事件模型与生产者

6.1 事件对象

@Data
@Builder
public class OrderEvent {
    /** 事件唯一标识，消费幂等键 */
    private String eventId;
    /** 消息 Key，保证同一订单落在同一分区 */
    private String orderId;
    private String userId;
    private BigDecimal amount;
    private String eventType;
    private long eventTime;
}

两个设计点：eventId 用 UUID，是消费幂等唯一标识；orderId 用作消息 Key。事件模型是跨服务契约，应保持稳定，不要直接拿数据库 Entity 当消息体。

6.2 生产者与发送确认

高频误区：KafkaTemplate.send() 返回 CompletableFuture，很多人以为方法返回没抛异常就是「发送成功」。不是。future 完成才代表 Broker 确认，真正的业务确认必须写在回调里：

@Slf4j
@Service
@RequiredArgsConstructor
public class OrderEventProducer {

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper objectMapper;

    public void send(String topic, OrderEvent event) throws JsonProcessingException {
        String payload = objectMapper.writeValueAsString(event);
        kafkaTemplate.send(topic, event.getOrderId(), payload)
                .whenComplete((result, ex) -> {
                    if (ex == null) {
                        log.info("消息已发送：topic={}, partition={}, offset={}",
                                result.getRecordMetadata().topic(),
                                result.getRecordMetadata().partition(),
                                result.getRecordMetadata().offset());
                    } else {
                        // 生产环境这里要落库进补偿任务，不能只打日志
                        log.error("消息发送失败：orderId={}", event.getOrderId(), ex);
                    }
                });
    }
}

6.3 Key 为什么重要

Kafka 按 Key 的 hash 选分区，同一个 Key 的消息稳定进入同一分区，Kafka 只保证分区内顺序。orderId 做 Key，同一订单的「创建 → 支付 → 发货」事件按序落在同一分区，消费端按序处理。代价是：分区数变化会改变 Key→分区的映射，强顺序业务扩分区前必须评估迁移方案。

七、消费者：容器管 Offset

Offset 机制是初学者最容易出错的地方，本例做法：

  • 配置关闭客户端自动提交（enable-auto-commit: false）；
  • Listener Container 的 ack-mode: record：单条消息处理成功后由容器提交 Offset；
  • 方法抛异常时进入错误处理流程，这条消息的 Offset 不会被提交。

反例是业务没处理完就手动提交 Offset——一旦处理失败而 Offset 已提交，消息就永远丢了。不要自己调 consumer.commitSync()，把提交时机交给容器。

@Slf4j
@Component
@RequiredArgsConstructor
public class OrderCreatedConsumer {

    private final ObjectMapper objectMapper;

    @KafkaListener(topics = "order-created", groupId = "order-service-group")
    public void onMessage(ConsumerRecord<String, String> record) throws JsonProcessingException {
        OrderEvent event = objectMapper.readValue(record.value(), OrderEvent.class);
        log.info("收到订单事件：eventId={}, orderId={}, partition={}, offset={}",
                event.getEventId(), event.getOrderId(), record.partition(), record.offset());
        // 业务处理（内部做幂等，见第十节）
    }
}

八、消费异常、重试与死信队列（DLT）

8.1 两类性质不同的失败

  • 短暂故障：网络抖动、下游数据库重启、外部接口超时——重试通常能自愈；
  • 永久错误：JSON 格式坏了、业务状态非法——重试一万次也不会成功，反复重试只是浪费资源。

正确姿势是「可重试异常有限重试 + 不可重试异常直接进死信」。

8.2 错误处理器配置

@Slf4j
@Configuration
@RequiredArgsConstructor
public class KafkaErrorHandlerConfig {

    @Bean
    public CommonErrorHandler kafkaErrorHandler(KafkaTemplate<String, String> kafkaTemplate) {
        DeadLetterPublishingRecoverer recoverer =
                new DeadLetterPublishingRecoverer(kafkaTemplate,
                        (consumerRecord, ex) -> new TopicPartition(
                                consumerRecord.topic() + "-dlt", consumerRecord.partition()));

        DefaultErrorHandler errorHandler = new DefaultErrorHandler(
                recoverer, new FixedBackOff(1000, 3));

        // 格式错误属于不可重试，一次进 DLT，不浪费三次重试
        errorHandler.addNotRetryableExceptions(IllegalArgumentException.class);
        return errorHandler;
    }
}

三个设计点：

  1. 重试有上限：FixedBackOff(1000, 3) 表示失败后每隔 1 秒重试 3 次，共 4 次尝试，之后不再无限循环；
  2. DLT 同分区映射：失败消息进入 order-created-dlt 的同编号分区，所以 DLT 分区数必须不小于源 Topic；
  3. Bean 名有讲究：Spring Boot 自动配置里监听容器的错误处理器 Bean 名就是 kafkaErrorHandler（@ConditionalOnMissingBean），自己的 Bean 用同名声明即可原位覆盖默认行为，不需要再手动装配 ContainerFactory。

框架层的坑：抛进错误处理器的异常会被包一层 ListenerExecutionFailedException，「不可重试」的判断依据是 Spring 从 cause 里解出来的根因类型。

8.3 死信监听器与二进制头

DeadLetterPublishingRecoverer 写入的死信头里，原始 Topic、异常类型、异常信息是字符串字节，但原始分区是 int、原始 Offset 是 long 的二进制字节。一律按 UTF-8 字符串解码，分区和 Offset 会显示成空白或乱码；这两个头要用 ByteBuffer 按 int/long 解码：

@Slf4j
@Component
public class OrderCreatedDltListener {

    @KafkaListener(topics = "order-created-dlt", groupId = "order-service-dlt-group")
    public void onDlt(ConsumerRecord<String, String> record) {
        String originalTopic = new String(record.headers().lastHeader("kafka_dlt-original-topic").value(), StandardCharsets.UTF_8);
        int originalPartition = record.headers().lastHeader("kafka_dlt-original-partition") == null ? -1
                : ByteBuffer.wrap(record.headers().lastHeader("kafka_dlt-original-partition").value()).getInt();
        long originalOffset = record.headers().lastHeader("kafka_dlt-original-offset") == null ? -1L
                : ByteBuffer.wrap(record.headers().lastHeader("kafka_dlt-original-offset").value()).getLong();
        String exceptionType = new String(record.headers().lastHeader("kafka_dlt-exception-cause-fqcn").value(), StandardCharsets.UTF_8);

        log.warn("收到死信消息：topic={}, partition={}, offset={}, 原始消息={}",
                record.topic(), record.partition(), record.offset(), record.value());
        log.warn("死信详情：原始Topic={}, 原始分区={}, 原始Offset={}, 异常类型={}",
                originalTopic, originalPartition, originalOffset, exceptionType);
    }
}

DLT 不是消息垃圾桶，生产上需要配套：监控告警、保存原始 Topic/分区/Offset/异常堆栈、人工核查修复后的重放流程，以及数据保留周期与脱敏策略。

九、集成测试：嵌入式 Broker

测试不能要求开发者先手动启动一个 Kafka。spring-kafka-test 提供的 @EmbeddedKafka 在测试进程里拉起嵌入式 Broker，自动把地址注入配置：

@EmbeddedKafka(partitions = 3, topics = {"order-created"})
@SpringBootTest
class OrderEventFlowTest {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    @MockBean
    private OrderCreatedConsumer consumer;

    @Test
    void shouldConsumeSentEvent() throws JsonProcessingException {
        OrderEvent event = OrderEvent.builder()
                .eventId(UUID.randomUUID().toString())
                .orderId("ORDER-TEST-001")
                .userId("1001")
                .amount(new BigDecimal("99.90"))
                .eventTime(System.currentTimeMillis())
                .build();

        kafkaTemplate.send("order-created", event.getOrderId(), toJson(event));

        // 轮询等待真实监听器被调用，不用 Thread.sleep
        Mockito.verify(consumer, Mockito.timeout(10_000).times(1))
                .onMessage(any(ConsumerRecord.class));
    }
}

两条测试纪律：

  1. 不要用 Thread.sleep() 做同步。用 Mockito.timeout(...) 或 Awaitility 内部轮询直到条件满足，既不浪费时间也不产生 flaky；
  2. 测的是完整链路：真实序列化 → 嵌入式 Broker → 真实监听器，而不是 mock 出来的「看起来消费了」。

十、生产前补课清单

本文完成了「发得出、收得到、错了有去处」的最小闭环，距离生产级还差几件事，按优先级：

  1. 消费幂等：至少一次语义下消息会重复（重试、再均衡都会造成），用 eventId 建消费记录表 + 唯一索引，与业务更新放同一个数据库事务。不要用「先在 Redis 打标记再写库」的方案——Redis 成功而数据库失败时，消息会被错误地认为已处理。
  2. 数据库与 Kafka 双写：直接「先写库再发消息」或反过来都有原子性缺口。标准解法是 Outbox 模式——业务数据与待发送事件同一本地事务落库，后台任务扫描投递，消费端靠 eventId 幂等兜底。
  3. 监控：Consumer Lag、DLT 数量、Producer 失败数接入告警；Broker 侧看 UnderReplicatedPartitions 和磁盘容量。Consumer Lag 持续增长就是消费速率跟不上生产速率的信号。
  4. 参数别照抄：batch.size、linger.ms、max.poll.records、concurrency 没有万能值，用真实消息体压测出基线再单变量调整。
  5. 安全：生产环境不要用无认证的 PLAINTEXT listener，凭据进环境变量或密钥管理系统，不要提交进 Git。

十一、小结

  • 版本基线交给 Spring Boot BOM 管理，不要手写 spring-kafka / kafka-clients 版本；本地用 Docker 以 KRaft 单节点跑 Broker，注意 advertised.listeners 与持久化数据卷，并按「空输出不报错」判断 Broker 存活；
  • 生产者确认只认 future 回调，不认方法返回；Key 决定分区，Kafka 只保证分区内顺序；
  • Offset 提交交给容器管理，不要手动 commitSync()；可重试异常有限退避重试，不可重试异常直接进 DLT；
  • 死信头里分区 int、Offset long 是二进制字节，需用 ByteBuffer 解码；
  • 生产闭环的地基是「至少一次 + 消费幂等」，双写缺口用 Outbox 模式解决，并配套 Lag、DLT、失败率监控。
