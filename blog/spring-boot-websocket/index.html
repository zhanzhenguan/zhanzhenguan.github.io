这篇是 Spring Boot 系列第十七部分，用 STOMP over WebSocket 实现一个聊天室：群聊广播、点对点私聊、机器人回复、连接状态监听、定时系统消息。技术栈：Spring Boot 3.5.16、JDK 17、spring-boot-starter-websocket、Thymeleaf，前端 SockJS + STOMP.js。代码为通用示例，地址与端口按实际环境调整。

一、WebSocket 简介

WebSocket 是在单个 TCP 连接上进行全双工通信的协议，允许服务器和客户端实时双向数据传输。HTTP 是「请求—响应」模式：客户端不发问，服务器不吭声；WebSocket 握手成功后双方变成「对讲机」，谁都能随时说话。

1.1 核心特点

  1. 持久连接：一次握手，持续通信；
  2. 全双工：客户端和服务器都能主动发送消息；
  3. 低延迟：无需重复建立连接；
  4. 轻量级：数据帧头部开销小。

1.2 工作流程

  1. 握手：客户端发送 HTTP 请求，协议升级为 WebSocket；
  2. 连接建立：服务器同意升级，建立持久连接；
  3. 数据传输：双方可随时发送/接收消息；
  4. 连接关闭：任一方都可主动关闭连接。

1.3 应用场景

场景 说明
实时聊天 即时消息应用
在线游戏 实时状态同步
股票行情 实时价格推送
协作工具 多人在线编辑
直播弹幕 实时评论展示

1.4 与 HTTP 对比

特性 HTTP WebSocket
连接方式 请求-响应 持久连接
通信方向 单向 双向
开销 每次请求都有头部 握手后开销极小
实时性 需要轮询 真正实时

二、技术选型：原生 WebSocket vs STOMP

2.1 两种方案

  • 原生 WebSocket：只提供底层帧通道，订阅、路由、分发都要手写；
  • STOMP over WebSocket：在 WebSocket 之上加一层文本消息协议，自带订阅/路由/目的地机制。

聊天室这种有「广播 + 点对点」需求的场景，STOMP 的订阅/路由能省掉大量手写分发代码，Spring 对它的支持也最完整，本文选择 STOMP over WebSocket。

2.2 消息路由前缀

四条核心路由约定是整个项目的「地图」：

前缀 作用 示例
/topic 广播消息前缀 /topic/public 公共聊天室
/queue 队列消息前缀 /queue/private 私聊消息
/app 应用消息前缀 客户端发到 /app/chat.sendMessage
/user 用户专用前缀 /user/queue/private 用户私聊队列
/ws WebSocket 端点 客户端连接地址

消息类型用枚举区分，前端按类型渲染不同样式（JOIN / CHAT / LEAVE / BOT / ADMIN）。

四、核心代码实现

4.1 WebSocket 配置类

整个项目最核心的配置类，三个方法各管一件事：

@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")
                .setAllowedOriginPatterns("*")
                .withSockJS();
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        // 广播 + 点对点目的地，由内置 SimpleBroker 内存代理处理
        registry.enableSimpleBroker("/topic", "/queue");
        // 客户端发送消息的应用入口前缀
        registry.setApplicationDestinationPrefixes("/app");
    }
}

三个关键点：

  1. @EnableWebSocketMessageBroker 启用 STOMP 消息代理，没有它所有 @MessageMapping 都不生效；
  2. setAllowedOriginPatterns("*") 用的是 Patterns 版本；若用 setAllowedOrigins("*")，在携带凭证的场景下会直接报错；
  3. withSockJS() 提供降级方案：浏览器不支持 WebSocket 时自动切到 HTTP 长轮询，保证连接能建立。

4.2 消息实体

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class ChatMessage {

    /** JOIN / CHAT / LEAVE / BOT / ADMIN */
    private String type;
    private String username;
    private String content;

    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime timestamp;

    /** 机器人回复标记，防死循环 */
    private boolean autoReply;
}

两个设计细节：

  1. @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")：不指定格式，LocalDateTime 默认序列化成带 T 的 ISO 串，前端直接显示一个 T；
  2. autoReply 是防死循环开关：机器人回复的消息带这个标记，回复判断时直接跳过，否则机器人会跟自己聊上一整天。

4.3 群聊控制器

@Slf4j
@Controller
@RequiredArgsConstructor
public class ChatController {

    private final SimpMessagingTemplate messagingTemplate;

    /** 客户端发到 /app/chat.sendMessage */
    @MessageMapping("/chat.sendMessage")
    @SendTo("/topic/public")
    public ChatMessage sendMessage(@Payload ChatMessage message,
                                  SimpMessageHeaderAccessor accessor) {
        message.setTimestamp(LocalDateTime.now());
        return message;
    }

    /** 用户加入：把用户名存进 WebSocket 会话属性 */
    @MessageMapping("/chat.addUser")
    @SendTo("/topic/public")
    public ChatMessage addUser(@Payload ChatMessage message,
                              SimpMessageHeaderAccessor accessor) {
        accessor.getSessionAttributes().put("username", message.getUsername());
        message.setType("JOIN");
        message.setTimestamp(LocalDateTime.now());
        return message;
    }
}

三个注解是 STOMP 开发的「三板斧」：

  • @MessageMapping("/chat.sendMessage")：类似 HTTP 的 @PostMapping，客户端发到 /app/chat.sendMessage 的消息落到这个方法；
  • @SendTo("/topic/public")：方法返回值自动序列化为 JSON，广播到 /topic/public，所有订阅者都能收到；
  • @Payload：把 STOMP 消息体反序列化成 ChatMessage。

SimpMessageHeaderAccessor 的关键动作：getSessionAttributes().put("username", ...) 把用户名存进 WebSocket 会话。为什么不在断开事件里直接拿？因为断开事件触发时客户端已经「跑了」，只能从会话属性里捞出断开前的用户名——这是事件监听器能拿到用户名的前提。

4.4 私聊控制器（点对点）

@Controller
@RequiredArgsConstructor
public class PrivateChatController {

    private final SimpMessagingTemplate messagingTemplate;

    @MessageMapping("/chat.private")
    public void sendPrivate(@Payload ChatMessage message,
                            SimpMessageHeaderAccessor accessor) {
        // 实际路由为 /user/{userId}/queue/private
        messagingTemplate.convertAndSendToUser(
                message.getTo(), "/queue/private", message);
    }
}

convertAndSendToUser(userId, "/queue/private", message) 的实际路由是 /user/{userId}/queue/private——目标用户前端订阅 /user/queue/private 时，STOMP 自动把订阅映射到自己专属的队列，别人订阅同名目的地也收不到你的私聊，这就是点对点的本质。

4.5 事件监听器

断开事件里的消息需要重新包装才能访问会话属性：

@Slf4j
@Component
@RequiredArgsConstructor
public class WebSocketEventListener {

    @EventListener
    public void handleDisconnect(SessionDisconnectEvent event) {
        StompHeaderAccessor accessor = StompHeaderAccessor.wrap(event.getMessage());
        String username = (String) accessor.getSessionAttributes().get("username");
        log.info("用户离开聊天室：{}", username);
    }
}

这里拿到的 username 就是加入时存进会话属性的那个。

4.6 智能回复与定时消息

智能回复服务的灵魂是 shouldReply：过滤掉 BOT / ADMIN 类型且 autoReply=true 的消息，否则机器人回复的 BOT 消息会再次进入回复流程，触发新一轮回复，消息雪崩。

定时消息服务：

@Service
@RequiredArgsConstructor
public class ScheduledBroadcastService {

    private final SimpMessagingTemplate messagingTemplate;

    /** 每 30 秒一条系统提醒；首次发送延后 1 分钟，避免上线即推送 */
    @Scheduled(fixedRate = 30 * 60 * 1000, initialDelay = 60 * 1000)
    public void broadcastSystemNotice() {
        ChatMessage msg = ChatMessage.builder()
                .type("ADMIN").username("系统").content("欢迎使用聊天室")
                .timestamp(LocalDateTime.now()).build();
        messagingTemplate.convertAndSend("/topic/public", msg);
    }
}

一个容易忽略的细节：@Scheduled(fixedRate = ...) 默认应用启动时立即执行一次；加 initialDelay 控制首次发送时机。

4.7 启动类

@EnableScheduling 不能忘：只写 @Scheduled 不加这个开关，定时任务一条都不会执行，而且没有任何报错——这是定时任务问题里最「哑巴」的一种。

@SpringBootApplication
@EnableScheduling
public class WebsocketDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(WebsocketDemoApplication.class, args);
    }
}

五、前端接入

5.1 引入前端依赖

两个库各干各的活：SockJS 负责「怎么连」（连接 + 降级），STOMP.js 负责「说什么」（订阅、发送、路由）。

5.2 客户端连接与订阅

三个订阅/发送路径对应路由设计：连接 /ws，订阅 /topic/public（广播）和 /user/queue/private（私聊），发送到 /app/chat.sendMessage。

特别注意 XSS 防护：聊天内容是任意用户输入，直接拼 innerHTML 是教科书级 XSS 漏洞。所有用户输入渲染前必须转义，用 textContent 或 createTextNode，不要把用户输入裸拼进 innerHTML。

六、运行与验证

  1. 启动应用，看到 Started WebsocketDemoApplication 即成功；
  2. 浏览器访问 http://localhost:8080/ 进入聊天室；SockJS 端点返回 websocket: true 说明 WebSocket 通道就绪；健康检查 /actuator/health；
  3. 端到端流程：两个标签页用不同用户名进入 → 收到 JOIN 广播和欢迎消息 → 发送消息触发机器人回复 → 新用户加入时广播自动推送 → 退出时收到 LEAVE 广播 → 服务端可主动推送系统消息。

七、踩坑与注意事项

  1. 端口冲突：8080 被占用时应用起不来（Port 8080 was already in use）。启动前确认端口空闲；端口改了就同步改前端连接地址；
  2. 机器人死循环：shouldReply 必须过滤 BOT/ADMIN 类型且 autoReply=true 的消息，否则机器人回复自己，消息雪崩；
  3. @EnableScheduling 别漏：@Scheduled 没有这个开关不生效，且无任何报错；
  4. fixedRate 启动即执行：定时任务默认应用启动先跑一次，需要 initialDelay 控制首次时机；
  5. XSS 防护：聊天内容渲染前必须 HTML 转义，不要裸拼 innerHTML；
  6. 生产收紧跨域：setAllowedOriginPatterns("*") 只适合开发，上线改成具体域名列表；
  7. SimpleBroker 的天花板：enableSimpleBroker 是单机内存代理，不支持集群和多实例部署。需要横向扩展时换 enableStompBrokerRelay，对接 RabbitMQ（STOMP 插件）或 ActiveMQ，代码层面只需改配置类一行，Controller 层零改动；
  8. 会话属性是断开事件的唯一线索：连接断开后客户端信息就没了，靠 SessionDisconnectEvent + 会话属性才能拿到「是谁离开了」，所以加入时那次 getSessionAttributes().put("username", ...) 不可省略。

八、小结

这套聊天室覆盖了 Spring Boot 整合 WebSocket 的完整闭环：STOMP 协议分层（端点 /ws → 前缀路由 → SimpleBroker）、群聊广播、点对点私聊、机器人智能回复、连接状态监听、定时系统消息、SockJS 降级。

核心记忆点是三组前缀：/topic 广播、/queue 点对点、/app 客户端入口，再加 /ws 连接端点。理解这四个地址的作用，Spring WebSocket 的消息流向就一目了然。
