这篇是 Spring Boot 系列第九部分，整合 RabbitMQ：按生产者工程与消费者工程拆分，梳理消息流转、Topic 路由、手动确认与可靠性保障。代码为通用示例，连接信息用占位符。

一、基本概念与消息流转

可以把 RabbitMQ 理解为应用程序之间的「消息中转站」：生产者把待处理任务发到 RabbitMQ，消费者再从队列取出执行，两者不必在同一应用、也不必同时在线。

消息基本流转顺序：生产者（Producer）→ 交换机（Exchange）→ 队列（Queue）→ 消费者（Consumer）。

  • 生产者：产生消息，例如订单创建后发送一条通知消息；
  • 交换机：接收消息并按规则路由，不保存消息；根据交换机类型、绑定关系和路由键决定消息进入哪个队列；
  • 队列：暂存消息，消费较慢时消息先在队列等待；
  • 消费者：监听队列并执行业务逻辑，如发短信、邮件或更新业务数据。

本例拆成生产者、消费者两个 Spring Boot 工程，使用 Topic 交换机，按不同 RoutingKey 把邮件、短信消息分别投递到对应队列。

二、依赖

两个工程都引入 spring-boot-starter-amqp，它是 Spring Boot 集成 AMQP 消息中间件的启动依赖，引入后即可使用 RabbitTemplate、@RabbitListener 等组件：

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>

RabbitTemplate 主要用于发送消息；@RabbitListener 主要用于监听队列接收消息。两个工程都需要该依赖，因为都要与 RabbitMQ 建立连接。

三、连接配置

3.1 连接参数

spring:
  rabbitmq:
    host: 127.0.0.1
    port: 5672
    username: demo
    password: ${RABBITMQ_PASSWORD:change-me}
    virtual-host: /
  • server.port 是应用自身 Web 端口（生产者 8081、消费者 8082），与 RabbitMQ 的 AMQP 端口不同；
  • AMQP 通信端口默认 5672，管理控制台端口通常是 15672，不要混淆；
  • virtual-host 用于隔离不同应用的交换机、队列和权限；生产者和消费者必须连接到同一个虚拟主机才能访问相同消息资源；
  • 本机学习可用 guest/guest，远程或生产环境应创建专用用户并分配最小必要权限。

3.2 消费者监听参数

消费者工程按需配置监听容器：

spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual      # 手动确认
        concurrency: 1                # 启动消费者数
        max-concurrency: 10           # 最大消费者数
        prefetch: 100                 # 未确认前预取消息数
  • acknowledge-mode: manual：手动确认，业务成功后主动 ACK；只设 manual 却不调用确认方法，消息会一直处于 Unacked；
  • concurrency / max-concurrency：初始与最大消费者数量，并发越高消费能力越强，但也会加大下游数据库、外部接口压力；
  • prefetch：确认前最多预取的未确认消息数，过大占用内存并可能导致消息分配不均。

四、配置类：交换机、队列与绑定

配置类把交换机、队列及绑定关系声明为 Spring Bean，应用启动时 Spring AMQP 同步到 RabbitMQ，资源不存在则创建。本例使用 Topic 交换机：

@Configuration
public class RabbitmqConfig {

    public static final String EXCHANGE = "exchange_topics_inform";
    public static final String QUEUE_EMAIL = "queue_inform_email";
    public static final String QUEUE_SMS = "queue_inform_sms";

    @Bean
    public TopicExchange topicExchange() {
        return ExchangeBuilder.topicExchange(EXCHANGE).durable(true).build();
    }

    @Bean
    public Queue emailQueue() {
        return QueueBuilder.durable(QUEUE_EMAIL).build();
    }

    @Bean
    public Queue smsQueue() {
        return QueueBuilder.durable(QUEUE_SMS).build();
    }

    @Bean
    public Binding emailBinding(Queue emailQueue, TopicExchange topicExchange) {
        return BindingBuilder.bind(emailQueue).to(topicExchange).with("inform.email");
    }

    @Bean
    public Binding smsBinding(Queue smsQueue, TopicExchange topicExchange) {
        return BindingBuilder.bind(smsQueue).to(topicExchange).with("inform.sms");
    }
}
  • durable(true)：交换机/队列定义持久化，RabbitMQ 重启后保留定义；
  • 交换机负责路由，队列负责存储等待消费的消息，二者是不同对象；
  • Topic 路由键由英文句点分隔的单词组成：* 匹配一个单词，# 匹配零个或多个单词，例如 inform.#.email.# 可匹配 inform.email 与 inform.order.email.notice。

注意：生产者与消费者对同名资源声明的类型、持久化等参数必须一致，否则 RabbitMQ 可能返回 PRECONDITION_FAILED。建议把名称集中定义为常量或抽到公共模块。

五、生产者：RabbitTemplate 发送

注入 RabbitTemplate 即可发送，convertAndSend 常见参数依次为交换机名称、RoutingKey、消息内容：

@Service
public class InformProducer {

    private final RabbitTemplate rabbitTemplate;

    public InformProducer(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    public void sendEmail(String message) {
        rabbitTemplate.convertAndSend(RabbitmqConfig.EXCHANGE, "inform.email", message);
    }

    public void sendSms(String message) {
        rabbitTemplate.convertAndSend(RabbitmqConfig.EXCHANGE, "inform.sms", message);
    }
}

convertAndSend 只代表把消息交给 RabbitMQ；消息是否成功路由、是否被消费、业务是否处理成功，需要通过发布确认、队列状态和消费者日志进一步验证。

六、消费者：监听队列与手动 ACK

消费者工程同样声明相同的交换机、队列与绑定，保证单独启动时拓扑存在。用 @RabbitListener 监听队列：

@Component
public class InformListener {

    @RabbitListener(queues = RabbitmqConfig.QUEUE_EMAIL)
    public void handleEmail(String msg, Message message, Channel channel) throws IOException {
        long tag = message.getMessageProperties().getDeliveryTag();
        try {
            // 业务处理
            channel.basicAck(tag, false);
        } catch (Exception e) {
            // 业务失败：拒绝消息；最后一个参数 false 表示不重新入队
            channel.basicNack(tag, false, false);
        }
    }

    @RabbitListener(queues = RabbitmqConfig.QUEUE_SMS)
    public void handleSms(String msg, Message message, Channel channel) throws IOException {
        long tag = message.getMessageProperties().getDeliveryTag();
        channel.basicAck(tag, false);
    }
}
  • msg：转换后的消息正文；Message：AMQP 消息对象，可取属性、消息头与 deliveryTag；Channel：底层通信通道，用于手动 ACK/NACK；
  • basicAck(tag, false)：确认消息；basicNack(tag, false, requeue)：拒绝消息，requeue 为是否重新入队；
  • requeue=false 且配置了死信交换机/队列时，消息按死信规则转入；否则可能被丢弃。requeue=true 会重新入队，持续失败时可能反复消费，应设计有限次数重试。

七、消息可靠性

7.1 消息确认（ACK）

ACK 是消费者向 RabbitMQ 发送的完成信号。自动确认由框架处理；手动确认需在业务代码中主动调用。建议业务处理成功后再 ACK：先 ACK 再执行业务，中途异常时 RabbitMQ 已认为完成，消息无法自动重投；一直不 ACK 则消息处于 Unacked，连接关闭后可能重新投递。

7.2 持久化与发布确认

durable(true) 只表示交换机/队列定义持久化，不等于消息一定不丢。提升可靠性还需结合：消息持久化、生产者发布确认、路由失败处理与消费者确认机制。

  • Publisher Confirm：判断 RabbitMQ 是否确认接收生产者消息；
  • Return 回调：处理消息无法路由到任何队列的情况。

7.3 幂等消费

消息队列通常是至少一次投递，消费者可能因网络中断、确认超时或重试重复收到同一消息。消费者业务应保证幂等：同一消息处理一次与多次，最终结果一致。常见做法是为消息设置唯一业务编号，数据库建唯一约束或记录处理状态；消费前检查是否已处理，已处理则直接确认，避免重复扣款、重复发券、重复创建数据。

八、常见问题排查

现象 排查方向
Connection refused RabbitMQ 服务是否启动、host/port 是否正确、防火墙与安全组是否放行 AMQP 端口
ACCESS_REFUSED 用户名、密码、virtual-host 是否正确，用户是否具备 configure/write/read 权限
发送后队列无消息 交换机名称、路由键、Binding 是否正确；Topic 通配符是否匹配
队列有消息但消费者不处理 消费者是否启动、@RabbitListener 是否扫描成功、队列名是否正确、是否异常阻塞
消息重复消费 ACK 是否正常、异常重试与网络中断情况，结合业务唯一标识做幂等
消息一直 Unacked 手动确认逻辑是否遗漏、业务方法是否长时间未返回、消费者是否阻塞

九、生产环境建议

  • 账号安全：每个应用独立账号、最小权限、强密码，不在配置文件或代码仓库明文保存生产密码；
  • 重试与死信：配置有限次数重试，超过次数进入死信队列，并建立人工排查或补偿流程；
  • 并发控制：按业务处理能力调整 concurrency、max-concurrency、prefetch，避免过高压垮下游；
  • 监控告警：关注队列堆积量、消费速率、Unacked 数、连接状态与死信数量；
  • 日志追踪：消息携带唯一业务编号或 TraceId，生产者与消费者都记录，便于跨服务排查。

十、小结

  • 消息链路为生产者 → 交换机 → 队列 → 消费者；交换机负责路由，队列负责存储，两者分离；
  • 引入 spring-boot-starter-amqp，生产者用 RabbitTemplate.convertAndSend，消费者用 @RabbitListener 监听；
  • Topic 交换机靠路由键与 */# 通配符绑定队列；手动确认模式下业务成功后 basicAck，失败按策略 basicNack；
  • 可靠性需要 ACK、持久化、发布确认与幂等消费共同保障；生产环境关注并发、死信、监控与链路追踪。
