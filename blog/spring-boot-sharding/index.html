这篇是 Spring Boot 系列第五部分，聚焦分库分表中间件 ShardingSphere-JDBC：先理解它解决什么问题、采用什么代理模式，再梳理分片策略设计与接入方式。代码为通用示例，数据库地址、账号均用占位符。

一、基本概念

Sharding-JDBC 是 Apache ShardingSphere 生态中的核心组件，现已更名为 ShardingSphere-JDBC，是一个轻量级 Java 框架，专门用于解决分库分表问题。

1.1 客户端代理模式

Sharding-JDBC 本质是数据库中间件，但采用客户端代理模式，而非传统的服务端代理模式。它在应用程序与数据库之间增加一层逻辑：应用看起来像在操作一个数据库，底层实际可能操作多个数据库、多张表。

这种设计的特点：

  • 对应用透明：只需配置分片规则，业务代码基本不需要修改；
  • 无单点故障：客户端模式下中间件逻辑随应用进程运行，不存在独立代理服务的单点；
  • 性能开销小：省去一次独立代理服务的网络跳转，开销相对较低。

与之相对，ShardingSphere-Proxy 是服务端代理模式：独立部署一个代理服务，应用通过代理访问数据库，对应用透明但多一层网络跳转。

二、为什么要分库分表

分库分表是数据库架构演进中的重要阶段，主要解决单库在大规模数据与高并发访问下的瓶颈。

2.1 数据量增长的挑战

业务数据量指数级增长时，单表达到千万级后即使有索引，查询性能也会明显下降；同时备份恢复时间变长、在线 DDL（加索引、改表结构）耗时甚至影响业务，存储成本快速上升。

2.2 并发访问的性能瓶颈

单库并发处理能力有上限：InnoDB 行级锁在高并发下仍会出现锁竞争，热点数据（如热门商品库存更新）导致请求排队；数据库连接数通常只能支撑几百到几千并发连接，应用扩容后连接容易成为瓶颈，CPU、内存、磁盘 IO 与查询缓存命中率也会承压。

2.3 可用性与风险控制

所有数据集中在一个库时，库故障会导致整个系统不可用；主从切换过程也存在短暂中断。把数据分散到多个库，可降低单点故障造成的数据丢失风险，某库出问题只影响部分用户。

2.4 地理分布与合规

全国性/全球性业务中，数据集中在一处会让远程用户访问延迟偏高；按地域分库可让用户就近访问。部分地区法规要求数据本地化，也需要按地域拆分。

2.5 业务隔离

不同业务模块资源需求差异大（用户中心读多、订单写多、日志占空间大），分库存放可针对性优化，也便于模块化开发维护，团队独立负责各自库表，大变更互不影响。

2.6 扩展性与维护

单库纵向扩容（升级硬件）成本高且有天花板；分库分表实现横向扩展，增加节点即可提升整体能力，也能更好利用多台服务器的硬件资源。维护上，大库备份恢复慢、在线维护风险高；拆分后维护分散到多个小库，单次影响范围可控，监控诊断也更容易定位问题。

2.7 成本与时机权衡

分库分表会增加系统复杂性，但长期看通常值得：多台中配服务器替代单台高配服务器可降低硬件成本，成熟中间件也在降低开发难度。关键是在合适时机决策——既不要过早优化，也不要等到系统无法承载才被动改造；微服务架构天然适合按服务边界拆分数据库。

三、分片策略设计

3.1 分库策略

通常按业务维度设计：

  • 按用户 ID 分库：最常见，用户 ID 取模分到不同数据库；
  • 按地域分库：如北京用户存北京库、上海用户存上海库。

3.2 分表策略

一般按数据量或时间维度：

  • 按数据量分表：数据增长相对均匀的场景，如订单表按订单 ID 取模分成多张表；
  • 按时间分表：有明显时间特征的数据，如日志表按月分表，每月一张表。

3.3 复合分片策略

同时使用多个分片键进行分库分表，适用于复杂业务场景。

四、接入示例

版本说明：以下以 ShardingSphere 4.x 的 sharding-jdbc-spring-boot-starter 风格为例；5.x 起模块更名为 shardingsphere-jdbc-core，配置结构与依赖坐标有调整，生产接入请以对应版本官方文档为准。

4.1 添加依赖

<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>sharding-jdbc-spring-boot-starter</artifactId>
    <version>4.1.1</version>
</dependency>

4.2 配置分片规则

在 application.yml 中配置多个数据源与分库分表规则。示例两个库 ds0、ds1，订单表按用户 ID 分库、按订单 ID 分表：

spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        url: jdbc:mysql://ds0-host:3306/demo?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
        username: demo
        password: ${DB_PASSWORD:change-me}
        driver-class-name: com.mysql.cj.jdbc.Driver
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        url: jdbc:mysql://ds1-host:3306/demo?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
        username: demo
        password: ${DB_PASSWORD:change-me}
        driver-class-name: com.mysql.cj.jdbc.Driver
    sharding:
      tables:
        t_order:
          actual-data-nodes: ds$0..1.t_order_$1..2
          database-strategy:
            standard:
              sharding-column: user_id
              precise-algorithm-class-name: com.example.alg.DatabaseShardingAlgorithm
          table-strategy:
            standard:
              sharding-column: order_id
              precise-algorithm-class-name: com.example.alg.OrderTableShardingAlgorithm

4.3 自定义分片算法

实现 PreciseShardingAlgorithm 接口，在 doSharding 中根据分片键值与可用节点计算目标库表：

public class OrderTableShardingAlgorithm implements PreciseShardingAlgorithm<Long> {

    @Override
    public String doSharding(Collection<String> availableTargetNames,
                              PreciseShardingValue<Long> shardingValue) {
        long orderId = shardingValue.getValue();
        int size = availableTargetNames.size();
        // 按订单 ID 取模路由到 t_order_1 / t_order_2 ...
        return "t_order_" + (orderId % size + 1);
    }
}

4.4 分层与表结构

接入后常规分层保持不变：实体类（如 User、Order、OrderItem、Dict）、Mapper 接口、Service 接口与实现类、Controller，外加请求对象与统一返回结果封装；启动类正常扫描即可。

表结构上，需要在每个数据库中创建对应的分表，例如 t_order_item_1、t_order_item_2、t_order_item_3……逻辑表名由分片规则映射到这些实际表。

五、小结

  • ShardingSphere-JDBC 是客户端代理模式的分库分表中间件，嵌入应用进程，对业务代码透明，无独立代理单点；
  • 分库分表用于应对单库数据量、并发、可用性、地理分布、业务隔离与横向扩展等瓶颈，但要权衡复杂度，选择合适时机；
  • 分片策略分库（用户 ID、地域）、分表（数据量、时间）与复合分片；接入时配置多数据源、逻辑表与分片规则，必要时自定义精确分片算法；
  • 版本演进上 4.x 与 5.x 依赖坐标和配置结构不同，生产接入以对应版本官方文档为准。
