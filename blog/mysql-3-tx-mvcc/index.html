深入理解 MySQL：事务 ACID、隔离级别、锁机制与 MVCC

2026年11月28日 · 约 5 分钟 · 1602 字 #MySQL#数据库#事务#锁#MVCC#后端

这一篇承接索引篇，进入 MySQL 中最”硬核”的模块：事务、锁与 MVCC。它们也是面试中区分初级与高级开发的分水岭。面向 Java 开发梳理概念与机制，SQL、代码为通用示例。

一、事务：让一组操作同生共死

1.1 事务是什么

事务（Transaction）是一组要么全部成功、要么全部失败的数据库操作。用 Spring 声明式事务表示：

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountMapper.decrease(fromId, amount); // 扣钱
    // 如果这里抛异常，扣的钱会自动退回
    accountMapper.increase(toId, amount);   // 加钱
}

@Transactional 告诉 Spring：这两个操作绑定成一个事务，任何一个失败，前面的操作也全部撤销。

1.2 ACID：事务的四个铁律

特性 通俗解释 数据库怎么做到的
原子性 Atomicity 要么全做，要么全不做 undo log（记录反操作，失败时回滚）
一致性 Consistency 数据始终满足业务规则 其他三个特性共同保证
隔离性 Isolation 并发事务互不干扰 MVCC + 锁
持久性 Durability 提交后数据不丢失 redo log（崩溃后用它恢复）

一个帮助理解的类比：事务像 Git 的 commit——没提交前修改都在暂存区，随时可撤销；COMMIT 相当于 push，提交后永久保存；ROLLBACK 相当于 git reset --hard，回到修改前状态。

二、隔离级别：解决并发的”度”

2.1 三种并发问题

假设有两个事务 T1、T2 同时运行，可能出现三类问题：

脏读（Dirty Read）：读到了别人没提交的数据。

T1：修改 name='张三' → '李四'，还没提交
T2：读到了 '李四'          ← 脏读
T1：回滚，name 还是 '张三'
T2 读到的 '李四' 是从未真正存在过的脏数据

不可重复读（Non-Repeatable Read）：同一事务内两次读同一行，结果被别人修改后不同。

T1：第一次读 name = '张三'
T2：修改 name = '李四' 并提交
T1：第二次读 name = '李四'  ← 不可重复读

幻读（Phantom Read）：有人插入/删除数据，导致结果集行数变化。

T1：SELECT * FROM user WHERE age > 20 → 5 行
T2：INSERT INTO user(age) VALUES(25)  → 插入并提交
T1：SELECT * FROM user WHERE age > 20 → 6 行  ← 幻读

快速区分：脏读读了未提交数据；不可重复读是同一行被改；幻读是结果集行数因增删而变。

2.2 四种隔离级别

-- 查看当前级别
SELECT @@transaction_isolation;
-- 设置级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
隔离级别 脏读 不可重复读 幻读 实现方式
READ UNCOMMITTED ✅ 发生 ✅ 发生 ✅ 发生 几乎没人用
READ COMMITTED ❌ 不会 ✅ 发生 ✅ 发生 每次查询生成新 ReadView
REPEATABLE READ（MySQL 默认） ❌ 不会 ❌ 不会 部分解决 事务开始时生成一个 ReadView + 间隙锁
SERIALIZABLE ❌ 不会 ❌ 不会 ❌ 不会 读写全加锁，完全串行

常见追问：为什么 MySQL 默认是 RR 而不是 RC？

历史原因：早期 binlog 只有 STATEMENT 格式（记录 SQL 语句本身），RC 级别下主库和从库执行同一条 SQL 可能得到不同结果。现在虽推荐 ROW 格式，但 RR 已成为事实标准；另外 RR 配合间隙锁能解决幻读，RC 做不到。

三、锁机制：并发控制的”交警”

3.1 锁的分类地图

┌── 共享锁（S 锁 / 读锁）：允许别人读，不让别人写
┌── 行锁 ─┤
│        └── 排他锁（X 锁 / 写锁）：别人既不能读也不能写
│
├── 记录锁（Record Lock）：锁住一行
├── 间隙锁（Gap Lock）：锁住行与行之间的间隙
└── 临键锁（Next-Key Lock）：记录锁 + 间隙锁
锁 ───┤
│        ┌── 意向共享锁（IS 锁）
└── 表锁 ─┼── 意向排他锁（IX 锁）
         └── 自增锁（AUTO-INC）

3.2 共享锁与排他锁

-- 共享锁（S 锁）：读时加，允许别人也读，但不允许别人写
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;

-- 排他锁（X 锁）：写时加，别人既不能读也不能写
SELECT * FROM user WHERE id = 1 FOR UPDATE;
-- INSERT / UPDATE / DELETE 默认就加 X 锁

锁兼容矩阵：

S 锁 X 锁
S 锁 ✅ 可以共存 ❌ S 与 X 冲突
X 锁 ❌ X 排斥一切 ❌ X 排斥一切

3.3 临键锁（Next-Key Lock）：防幻读的利器

在 REPEATABLE READ 隔离级别下，InnoDB 默认使用临键锁 = 记录锁 + 间隙锁。

-- 假设 user 表有 id = 5, 10, 15 三行
-- 间隙分布：(-∞, 5), [5, 10), [10, 15), [15, +∞)
SELECT * FROM user WHERE id > 8 AND id < 13 FOR UPDATE;

实际加锁范围：

[5, 10) + [10, 15) + {记录 10}
  ↑间隙锁   ↑间隙锁      ↑记录锁
效果：既不能修改 id=10 的行，也不能在 5~15 之间插入新行

为什么需要间隙锁？如果没有它，虽然锁住了 id=10 这行，但别的事务可能在查询范围内插入一条 id=11 的记录，让结果集在不知情下被改变——这就是幻读。间隙锁像在每个行之间拉了一条”警戒线”。

3.4 死锁：并发编程的经典陷阱

-- 事务 A
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1; -- 锁住 id=1
UPDATE account SET balance = balance + 100 WHERE id = 2; -- 等待锁 id=2
COMMIT;

-- 事务 B（同时执行）
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 2; -- 锁住 id=2
UPDATE account SET balance = balance + 100 WHERE id = 1; -- 等待锁 id=1
COMMIT;
-- → 死锁：A 等 B 放锁，B 等 A 放锁，循环等待
-- InnoDB 检测到死锁后回滚其中一个事务，报错：
-- Deadlock found when trying to get lock; try restarting transaction

避免死锁的三条黄金法则：

  1. 按相同顺序访问资源：所有事务都按 id 升序操作，锁的获取顺序一致就不会死锁；
  2. 缩短事务时间：事务里不要放 RPC 调用、文件 IO 等耗时操作，锁持有时间越短，死锁概率越低；
  3. 适当降低隔离级别：RC 级别下间隙锁较少，死锁率也相应降低。

四、MVCC：读写不冲突的秘密

4.1 一句话理解 MVCC

MVCC（Multi-Version Concurrency Control，多版本并发控制）的核心思想：读操作不加锁，通过查看数据的旧版本来获取一致性视图。

就像编辑一个 Word 文档：你正在改的内容别人看不到，别人看到的还是旧版本，保存之后别人才看到新版。MVCC 在数据库里做了同一件事。

4.2 隐藏字段与版本链

InnoDB 每行数据都带有平时看不到的隐藏列，最关键的两个：

┌────┬──────┬─────┬───────────┬──────────────┐
│ id │ name │ age │ DB_TRX_ID │ DB_ROLL_PTR  │
├────┼──────┼─────┼───────────┼──────────────┤
│ 1  │ 张三 │ 25  │ 100       │ 0x...        │
└────┴──────┴─────┴───────────┴──────────────┘
       ↑ 最近修改这一行的事务 ID   ↑ 指向 undo log 的指针

表若没有主键，InnoDB 还会生成隐藏的行 ID（DB_ROW_ID）作为聚簇索引键。

每次更新数据，旧版本存入 undo log，通过 DB_ROLL_PTR 指针串成版本链：

当前行（name='王五', trx=300）
  ↓ DB_ROLL_PTR
undo log v1（name='李四', trx=200）
  ↓ DB_ROLL_PTR
undo log v2（name='张三', trx=100）

4.3 ReadView：事务的”快照相机”

ReadView 是事务读取数据时创建的快照，记录这个瞬间有哪些事务仍在活跃（还没提交）：

ReadView 属性 含义
m_ids 创建快照时所有”活跃中”的事务 ID
min_trx_id m_ids 中最小的那个
max_trx_id 下一个待分配的事务 ID
creator_trx_id 创建这个 ReadView 的事务自己

4.4 可见性判断：该看到哪个版本

当一条数据的 trx_id = 150，当前事务按以下规则判断：

规则 1：trx_id == creator_trx_id  → ✅ 自己的修改当然可见
规则 2：trx_id < min_trx_id       → ✅ 修改者在快照前就提交了
规则 3：trx_id >= max_trx_id      → ❌ 修改者在快照后才开始，不可见
规则 4：trx_id IN m_ids           → ❌ 修改者在快照时还没提交，不可见
规则 5：以上都不满足               → ✅ 修改者在快照前已提交，可见

4.5 RC vs RR：ReadView 生成时机决定一切

两种隔离级别的本质区别就是 ReadView 的生成时机：

READ COMMITTED（读已提交）：
  事务中每次 SELECT → 生成新的 ReadView
  → 能看到别的事务新提交的数据 → 导致"不可重复读"

REPEATABLE READ（可重复读）：
  事务中第一次 SELECT → 生成 ReadView，之后复用
  → 看不到别的事务新提交的数据 → 保证"可重复读"

理解了 MVCC 再回看三种并发问题会豁然开朗：脏读、不可重复读、幻读，本质上都是”事务在什么时候、看到了什么版本的数据”的问题。

五、小结

学完本篇，应能回答：ACID 四个特性分别由什么机制保证；脏读、不可重复读、幻读的区别；四种隔离级别各解决什么问题；S/X 锁兼容矩阵；临键锁如何防幻读、间隙锁锁住什么；死锁成因与避免方式；ReadView 如何判断可见性；RC 与 RR 的本质区别。

三句最关键的认知：

  1. ACID 各有机制兜底：原子性靠 undo log 回滚，持久性靠 redo log 恢复，隔离性由 MVCC 加锁共同实现；
  2. 锁处理写冲突，间隙锁补幻读：行锁分 S/X，临键锁 = 记录锁 + 间隙锁；按固定顺序访问、缩短事务是避免死锁的核心；
  3. MVCC 让读写不互斥：读不加锁，靠版本链 + ReadView 判断可见性；RC 每次读新建快照，RR 首次读建快照后复用。
