MySQL 七个底层机制：优化器成本、索引下推、覆盖索引、filesort、深分页、MVCC 与在线 DDL

2026年11月28日 · 约 13 分钟 · 4355 字 #MySQL#数据库#优化器#索引#MVCC#DDL#底层机制

日常写 SQL 只负责说”要什么”，怎么拿数据由 MySQL 自己决定；它每个决定的依据来自我们给的 SQL、索引、表结构和数据分布。这一篇梳理 MySQL 拿数据时背后的七个底层机制，基于 MySQL 8.0 编写，部分参数与命令在其他版本可能不同。

一、优化器：选的是”它以为最便宜”的索引

我们写的是声明式 SQL，优化器拿到的却是一堆统计数字——它做的是估算，不是精确计算。这两者的差别，正是慢 SQL 的主要来源。

1.1 成本模型三笔账

成本项 什么时候产生
磁盘读成本（io_block_read_cost） 从磁盘读一个页
内存读成本（memory_block_read_cost） 从缓冲池读一个页（默认约为磁盘读的 1/4）
CPU 成本（row_evaluate_cost、key_compare_cost 等） 要比较多少行、要过滤多少行

优化器枚举可能的执行路径，挑总成本最低的那条。问题在于：这些成本按”估计行数”算出，而估计行数来自索引统计信息——统计信息不准，选出的路就是错的。

1.2 统计信息为什么会不准

InnoDB 索引统计默认持久化（innodb_stats_persistent = ON），靠随机抽样若干索引页（innodb_stats_persistent_sample_pages，默认 20 页）推算整个索引的区分度。估算失准主要来自两件事：

  • 基数采样误差：抽 20 页看到的”不同值个数”未必等于真实基数；优化器对等值条件的估算公式是 总行数 ÷ 基数，基数一偏，行数就跟着偏；
  • 均匀分布假设：优化器默认每个取值出现的行数大致相同，只有建了直方图才会看真实分布。

两者叠加就可能挑错路：比如 user_id 平均每个用户一万行，某个大客户自己就有四十万行——按平均值估，代价被严重低估。

-- 重新采样统计信息（会短暂加锁，大表谨慎）
ANALYZE TABLE t_order;

-- 更精准：给"没索引但参与 WHERE 过滤"的列建直方图
ANALYZE TABLE t_order UPDATE HISTOGRAM ON status, channel WITH 64 BUCKETS;

直方图直接刻画列值分布，比索引采样更接近真实分布。当某个没建索引的列承担关键过滤、而优化器总估错行数时，直方图是第一个该试的手段。

1.3 怎么知道估算错得多离谱

8.0.18 之前只能靠 SHOW SESSION STATUS LIKE 'Handler_read%' 这类计数器反推；8.0.18 起有了 EXPLAIN ANALYZE——把语句真正执行一遍，把估算值和实测值并排打印出来：

EXPLAIN ANALYZE
SELECT order_no, amount FROM t_order
WHERE user_id = 10086 AND status = 1;
-> Filter: (t_order.`status` = 1) (cost=31652 rows=12) (actual time=0.083..795 rows=37 loops=1)
-> Index lookup on t_order using idx_user_id (user_id=10086)
   (cost=31652 rows=86317) (actual time=0.076..795 rows=42183 loops=1)

输出是树形（FORMAT=TREE 是唯一支持格式），每行对应一个迭代器：cost 是估的代价，actual time 是实际耗时（首行..全部行，ms），loops 是执行次数；rows 出现两次——前面是优化器估的，后面是实际的（loops > 1 时那是每轮平均值，总行数还要乘 loops）。

关键看同一位置的两个 rows：内层估 86317、实际 42183，差 2 倍；上一层 Filter 估 12、实际 37，差 3 倍。比率偏差大的一层说明统计信息不可信，绝对行数偏差大的一层才真正决定 SQL 慢在哪。差得越离谱（尤其一个数量级以上），说明不是索引不好，而是优化器对数据分布一无所知——该补统计信息、建直方图、改写 SQL，而不是继续堆索引。

注意：EXPLAIN ANALYZE 会真正执行语句。它对多表 UPDATE/DELETE 也支持，跑下去会真改数据（单表 DML 不在支持范围内，会报 ERROR 1288），生产环境别随手跑。

二、索引下推：联合索引为什么只用了第一列

假设有索引 (zipcode, lastname, firstname)，查询是：

SELECT * FROM people
WHERE zipcode = '95054'
  AND lastname LIKE '%etrunia%'
  AND address LIKE '%Main Street%';

三个条件待遇完全不同：

条件 能不能定位索引 能不能提前过滤
zipcode = '95054' ✅ 等值匹配，直接定位 ✅
lastname LIKE '%etrunia%' ❌ 前导通配符，无法定位 ✅ lastname 在索引里
address LIKE '%Main Street%' ❌ ❌ address 不在索引里

lastname 虽不能”定位”，但值存在索引条目上；address 不在索引里，索引条目上根本没有它。

2.1 ICP 的价值：减少回表

这就是 Index Condition Pushdown（ICP，索引条件下推），MySQL 5.6 引入、默认开启。价值只有一个：减少回表次数。回表是随机 IO，是索引路线上最贵的一步，能少读一行就是一行。

EXPLAIN SELECT * FROM people
WHERE zipcode = '95054' AND lastname LIKE '%etrunia%';
-- Extra: Using index condition

2.2 ICP 帮不上忙的三个边界

边界 说明 后果
条件里的列必须在索引里 只推”索引列”上的条件 address 这种不在索引里的列推不下去
只对二级索引有意义 聚簇索引整行数据本来就在引擎里，谈不上”下推” 主键查询上 ICP 没有收益
只作用于 range / ref / eq_ref / ref_or_null 全表扫描没有”索引条目”可推 ALL 类型用不上

读 EXPLAIN 的常见误读：Using index condition 是”条件下推到引擎层了”，不是”不用回表了”。把它当成覆盖索引，会以为已经优化完了，实际问题还在。

三、覆盖索引：把回表彻底省掉

二级索引上 user_id = 10086 只找到主键值，要拿 order_no、amount 还得拿主键去聚簇索引再查一次——一次索引查找可能变成几万次随机 IO。消除思路很直白：查询要的列全都在二级索引里，就根本不用回表。

-- 已有联合索引 idx_user_status (user_id, status)

-- 要取的 order_no、amount 不在索引里 → 必须回表
EXPLAIN SELECT order_no, amount FROM t_order WHERE user_id = 10086;

-- 要取的列全在索引里 → 覆盖索引，全程不回表
EXPLAIN SELECT user_id, status FROM t_order WHERE user_id = 10086;
-- Extra: Using index

Using index 就是覆盖索引的标志。它不是”用了一个索引”，而是”查询需要的列全都在索引里”。

3.1 为什么查主键列天然就是覆盖

InnoDB 二级索引叶子节点存的不是行地址，而是索引列 + 主键值：

-- id 是主键，本身就存在 idx_user_id 的叶子上 → 不用回表
EXPLAIN SELECT id FROM t_order WHERE user_id = 10086;
-- Extra: Using index

这条规则很实用：所有”先按条件查主键、再拿主键做别的事”的写法，天然是覆盖索引，也是后面深分页解法的基础。

3.2 代价：每个二级索引都拖着主键走

覆盖索引不是免费的——主键越长，所有二级索引就越大。用 CHAR(36) 的 UUID 做主键，在 utf8mb4 下每条二级索引记录都要背上这 144 字节：索引变大、一个页装的条目变少、树变高、IO 变多。这也是”自增小整数主键优于 UUID”最底层的原因——它不只影响聚簇索引的插入顺序，还成倍放大到每一个二级索引上。

3.3 Extra 高频标识对照

Extra 标识 真实含义 常见误读
Using index 覆盖索引，不需要回表 ——（这个才是好消息）
Using index condition 条件下推到引擎层，仍要回表 ❌ 误当成覆盖索引
Using where 拿到行之后还要在 Server 层过滤 常被当成”用上了索引”
Using filesort 需要额外排序，索引用不上顺序 ❌ 误当成”用到了排序文件”
Using temporary 内部临时表（常见于 group by、distinct、union） ——

想知道联合索引用到了几列，看 key_len：它等于参与定位的列宽之和，只用到第一列时就等于第一列宽度。

四、filesort：ORDER BY 的成本花在哪

看到 filesort，很多人第一反应是”要写磁盘了”。这个名字起得不好——它可能全程都在内存里完成，一个字节都不落盘。

4.1 什么时候出现

排序能不能免费，取决于索引的有序性能不能被复用：

-- idx_user_created (user_id, created_at)

-- ✅ 索引本身已按 (user_id, created_at) 有序，定位 + 排序一步到位
EXPLAIN SELECT * FROM t_order WHERE user_id = 10086 ORDER BY created_at DESC;

-- ❌ 排序键和索引顺序对不上，只能自己排
EXPLAIN SELECT * FROM t_order WHERE user_id = 10086 ORDER BY amount DESC;
-- Extra: Using filesort

判断规则一句：ORDER BY 的列能不能接在等值条件列之后、构成索引的一个连续前缀。 能，顺序就是白送的；不能，就得自己排。

一旦要自己排，成本分两段。监控上有个指标专门盯第二段：Sort_merge_passes。这个值持续增长，说明排序已经在落盘归并了（SHOW SESSION STATUS LIKE 'Sort%' 可看到）。

版本变化（最容易写错）：网上大量文章还在教”调小 max_length_for_sort_data，强制走双路排序”——这套说法在 8.0.20 之后已彻底失效。该变量（worklog WL#13600）已废弃，排序算法改由优化器自己决定，可变长字段用打包（packed addons）方式放进排序缓冲区。另外从 8.0.12 起，排序缓冲区是按需增长的，不再一上来就把 sort_buffer_size 分配满。

4.2 消除 filesort 的两种手法

手法一：把排序键接进联合索引。 收益最高——WHERE user_id = ? ORDER BY created_at DESC 配 (user_id, created_at)，定位和排序一次搞定。

手法二：方向不一致时用降序索引。 这是 8.0 才有的能力。ORDER BY status ASC, created_at DESC 用普通索引 (user_id, status, created_at) 做不到（第三列方向反了），而 8.0 的降序索引可以精确匹配：

ALTER TABLE t_order ADD INDEX idx_mixed (user_id, status ASC, created_at DESC);

8.0 之前没有降序索引，“两列排序方向混排”是老版本绕不过去的坎；8.0 上这道坎已经没了。

五、深分页：LIMIT 1000000, 10 为什么越翻越慢

-- 已有二级索引 idx_created (created_at)
SELECT * FROM t_order ORDER BY created_at LIMIT 1000000, 10;

这条 SQL 只返回 10 行，却可能比全表扫描还慢。LIMIT offset, n 的语义是”先取前 offset + n 行，丢掉前 offset 行，返回剩下 n 行”，所以必须先真的把那 1000010 行读出来。更麻烦的是：排序键落在二级索引上时，走索引能省一次排序，代价却是这一百万行里每一行都要回表一次。

5.1 方案一：延迟关联

既然白扫不可避免，就让白扫不带着回表一起做。利用”查主键天然是覆盖索引”：

SELECT o.*
FROM t_order o
JOIN (
  SELECT id FROM t_order ORDER BY created_at LIMIT 1000000, 10
) t ON o.id = t.id
ORDER BY o.created_at;

内层子查询只取 id，而 id 就存在 idx_created 叶子上，全程在索引里走、不回表；把 offset 的巨大开销压缩成一次顺序索引扫描后，再拿 10 个主键回表取完整数据——总共只有 10 次回表。

5.2 方案二：游标分页

如果翻页场景允许”只能往后翻”，连那 100 万行的索引扫描都能省掉：

-- 记住上一页最后一行的 id，下一页从它之后开始
SELECT * FROM t_order WHERE id > 1000000 ORDER BY id LIMIT 10;

WHERE id > ? 配合聚簇索引直接定位起点，这是唯一一种代价与页码无关的方案。这里拿 id 举例，换成 created_at 也一样——只是 created_at 可能重复，得把 id 一起带上比较，保证游标唯一且有序。

5.3 取舍

方案 时间稳定性 能否跳页 适用
原始 LIMIT offset, n ❌ 越翻越慢 ✅ 页码小、数据量小的场景
延迟关联 ⚠️ 仍随 offset 增长（但只扫索引） ✅ 必须跳页、offset 不太大的场景
游标分页 ✅ 与页码无关 ❌ 只能顺序往后 信息流、日志、增量拉取

延迟关联有一个前提——ORDER BY 的列在索引里。如果排序本身要走 filesort，内层子查询就变不成”纯索引扫描”，收益会大幅缩水。这两个机制连在一起，不能只挑一个用。

六、MVCC 与间隙锁：同一行，两个事务看到的可能不是同一版本

反直觉的事实：在 InnoDB 里，你读到的这一行很可能不是磁盘上那一行。原因是 undo log——每次修改一行，InnoDB 把旧值写进 undo log，用回滚指针把版本串成一条链。

每行隐藏两个字段：DB_TRX_ID（最后一次修改它的事务 ID）和 DB_ROLL_PTR（指向 undo 里上一个版本）。读到某一行、而当前版本对你”不可见”时，InnoDB 顺链往回找，直到找到你能看见的版本。

判断”能不能看见”靠 ReadView，核心是四个数字：m_ids（建快照那一刻还没提交的事务 ID 列表）、min_trx_id（列表最小值）、max_trx_id（下一个将分配的事务 ID）、creator_trx_id（我自己）。

6.1 RC 和 RR 的差别，就是快照什么时候建

隔离级别 ReadView 建立时机 结果
READ COMMITTED 每次 SELECT 都新建一个 同一事务两次查询可能看到不同结果（不可重复读）
REPEATABLE READ（默认） 事务里第一次读时建立，之后一直复用 整个事务看到同一个版本快照

RR 的”可重复读”不是靠锁实现的，是靠”快照只用一次”实现的。读的一致性靠 MVCC，写的一致性才靠锁。

6.2 幻读靠间隙锁挡

快照解决了”读到什么”，但解决不了：我锁住的行，会不会在我锁的时候旁边又被人插进来一行。

RR 下，UPDATE/DELETE/SELECT ... FOR UPDATE 用 next-key lock，是”记录锁 + 间隙锁”的组合。间隙锁有几个反直觉性质：

  • 间隙锁之间互不冲突：两个事务可以同时持有同一个间隙的 gap lock，因为共同目标只是”阻止插入”——直到有人真往间隙插数据才会互相等；
  • 唯一索引 + 唯一等值条件时，不锁间隙：唯一索引上不可能再插一个同样的值，锁没必要延伸到间隙；
  • RC 下间隙锁基本关闭，只在外键约束检查和唯一键冲突检测时才用。代价是幻读会回来——更好的并发和更少死锁，换的是丢失 RR 的幻读防护，需自行权衡。

6.3 最典型的事故形态

UPDATE t_order SET status = 0 WHERE order_no = 'A123'; -- order_no 上没索引

没有索引就不能”只锁一行”，引擎只能扫描整个聚簇索引，把扫过的范围全部加上 next-key lock——别的会话想往表里插任何一行，都会卡在间隙锁上。这是”更新一行却把表锁死”最典型的原因。

插入一行之前，InnoDB 要先在目标间隙加一个插入意向锁（insert intention lock，间隙锁的特殊形式）；间隙已被别的事务 gap lock 占着，插入就得等。线上突然出现一片”插入超时”时，第一件事就该看有没有哪个事务持着大范围间隙锁没提交。

七、在线 DDL：ALTER TABLE 到底锁不锁表

“锁不锁表”这个问题本身问得不准确。真正该问三件事：要不要重建表、期间能不能并发写、会不会被前面的事务堵住。

MySQL 8.0 上 DDL 有三种算法，成本差了三个数量级：

算法 做法 是否重建表 期间并发 DML 典型操作
COPY 建新表，逐行拷贝数据 ✅ 是 ❌ 禁止 改列类型、改字符集
INPLACE 在原表上就地完成 视操作而定 ✅ 多数可（LOCK=NONE） 加/删二级索引、改索引名
INSTANT 只改元数据 ❌ 否 ✅ 可 加列、删列（8.0.12 / 8.0.29 起）

7.1 INSTANT 的边界比以为的窄

INSTANT 代价和表大小彻底解耦，几亿行加一列也是秒级，但能力被版本切开：

能力 起始版本 约束
在表末尾加列 8.0.12 表不能用 COMPRESSED 行格式、不能有全文索引
在任意位置加列、删除列 8.0.29 同上；单条 ALTER 不能和其他不支持 INSTANT 的动作混用

临时表和数据字典表空间里的表都不支持 INSTANT；ALGORITHM=INSTANT 只能配 LOCK=DEFAULT；加自增列时不允许并发 DML。

原理是只改数据字典、不动任何数据行，老数据行靠行版本解析。每张表最多 64 个行版本，可以查出来：

SELECT NAME, TOTAL_ROW_VERSIONS
FROM information_schema.INNODB_TABLES
WHERE NAME = 'test/t_order';

一旦撞到 64，就必须重建一次表才能继续用 INSTANT——这就是”为什么我的 INSTANT 忽然不 INSTANT 了”的答案。

版本变化：8.0.29 的即时加/删列引入了新的 redo 日志格式，打破向后兼容：老版本 MySQL、旧版 Percona XtraBackup 都无法直接处理（8.0.29 初期还有崩溃恢复相关的数据损坏缺陷，Percona 后续做了修复）。升级路径和备份工具版本要一起规划。

7.2 真正让你”锁表”的通常不是 DDL 本身

ALTER TABLE 在执行开始和结束的两个瞬间，需要拿到 MDL_EXCLUSIVE（元数据排他锁）。为拿到它，DDL 得等的不是一个事务提交，而是所有持有 MDL_SHARED 的会话都退出——任何一句还没结束的普通查询，都持有 MDL_SHARED。

事故链是：DDL 只等了一个长事务，但它后面排着的所有查询全都在等 DDL。 排查时看这两张表：

-- 是谁在挡着 DDL / 有没有长事务
SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_NAME = 't_order';

SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;

做任何 DDL 之前，先确认没有长事务（尤其没有 autocommit = 0 之后忘了提交的连接），并给 DDL 会话设一个 lock_wait_timeout，让它等不到就自己退出，而不是一直堵着后面的查询。

7.3 超大表：把重建挪到另一张影子表上

即便选 INPLACE，重建表本身对几亿行依然意味着巨大 IO 和主从延迟，而且同一张表上的 DDL 只有一条路，没有”分批做”的余地。第三方工具把这件事拆到另一张影子表上：

工具 同步机制 特点
pt-online-schema-change 在原表建触发器 兼容面广，但触发器给原表加了写放大
gh-ost 读 binlog（无触发器） 原表零侵入，可暂停、可限速，运维更可控

两者思路一致：把存量数据搬过去、增量变更持续同步过去，最后用一个短暂的 RENAME 完成切换——真正”锁定”原表的时间，从”整个重建过程”压缩到最后那次改名。

八、小结

七个机制说的是同一件事的两面：你写的是”要什么”，MySQL 干的是一堆你没说出口的决定。 慢往往不是因为写错了，而是不知道它在替你做哪些决定。

三句最关键的认知：

  1. 优化器靠估算选路：统计信息不准就会选错索引；用直方图补分布、用 EXPLAIN ANALYZE 对比估算与实测，而不是盲目堆索引；
  2. 索引路线要分清三层：ICP 只是引擎层提前过滤、仍要回表；覆盖索引才真正免回表；filesort 看索引有序性能否复用；
  3. 写与变更各有底线：MVCC 用快照保证读一致性、间隙锁防幻读；在线 DDL 先排查 MDL 长事务，超大表走影子表工具把锁表时间压到最后改名。
