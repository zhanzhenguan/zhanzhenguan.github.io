MySQL 索引探秘：B+Tree、聚簇/二级索引、回表与最左前缀

2026年11月28日 · 约 5 分钟 · 1802 字 #MySQL#数据库#索引#B+Tree#性能优化#后端

承接基础入门篇，这一篇聚焦 MySQL 性能优化的绝对核心——索引。面向 Java 开发梳理索引的数据结构、存储形态、使用规则与常见优化手段，SQL 与配置为通用示例。

一、索引是什么

抛开课本定义：查新华字典时不会从第一页逐个翻，而是先查拼音目录逐层缩小范围，这就是索引的作用。MySQL 的索引是一种有序的数据结构，让数据库以极少的磁盘 I/O 定位目标数据。

磁盘 I/O 之所以关键，是因为内存读取在纳秒级、磁盘读取在毫秒级，两者相差约 10 万倍；一次磁盘寻道的时间，CPU 可以执行数十万条指令。因此衡量数据库性能的核心指标不是”扫描了多少行”，而是”用了多少次磁盘 I/O”。

二、B+Tree：索引的发动机

2.1 为什么选 B+Tree

数据库索引可以用哈希表、二叉树、B 树等多种结构，InnoDB 最终选择 B+Tree，这是对”数据量大、高并发、支持范围查询”三大需求权衡后的结果。

2.2 结构长什么样

            [8 | 15]                 ← 非叶子节点（只存索引键，不存数据）
            /   |   \
       [3|6]  [10|12]  [18|22]       ← 非叶子节点，继续缩小范围
        / \    /  \      /  \
     [1|2]↔[4|5]↔[6|7] ...           ← 叶子节点（存全部数据，双向链表连接）

看懂三句话：

  1. 上层是非叶子节点，相当于”路牌”，告诉你往哪走，本身不存数据；
  2. 最下层是叶子节点，相当于”目的地”，存储所有记录；
  3. 所有叶子节点之间用双向链表相连，方便前后遍历。

2.3 四个核心优势

特性 说明 带来的好处
数据全在叶子节点 非叶子节点只存键值，不放数据 一个节点能装更多键，树更矮，磁盘 I/O 更少
叶子节点是双向链表 所有叶子节点首尾相连 范围查询（BETWEEN、>、<、ORDER BY）极快
树高极低 千万级数据表树高通常只有 3-4 层 一次查询只需 3-4 次磁盘 I/O
查询稳定 每次都要走到叶子节点 O(log n) 复杂度，性能可预测

2.4 一次索引查询做了多少次 I/O

以 2000 万行的表为例估算：

B+Tree 每个节点约 16KB（InnoDB 页大小）
主键 BIGINT（8 字节）+ 指针（6 字节），每个节点可存约 1170 个键

层 1（根节点）：1 个节点，1170 个指针
层 2：1170 个节点，1170 × 1170 ≈ 137 万条键
层 3（叶子）：137 万 × 1170 ≈ 16 亿行 → 远超 2000 万

所以 2000 万数据只需要 2-3 层，一次主键查询 2-3 次磁盘 I/O。

这就是大表仍能”秒级”响应的秘密：靠极矮的树高把磁盘 I/O 压到个位数。

三、聚簇索引与二级索引：数据存在哪

3.1 聚簇索引（主键索引）

InnoDB 中，表数据按主键顺序物理存储在 B+Tree 的叶子节点里，也就是说主键索引的叶子节点就是一整行数据。

聚簇索引（主键 id）：
[id=1, 张三, 25, 北京] ↔ [id=2, 李四, 30, 上海] ↔ [id=3, 王五, 28, 广州]
↑ 叶子节点直接存储整行数据的所有列

这也解释了为什么自增主键很重要：主键递增时，新数据直接追加到 B+Tree 末尾；如果用随机 UUID，就要在树中间插入，可能触发页分裂（一个数据页装不下，被迫拆成两页），性能大幅下降。

3.2 二级索引（辅助索引）

除主键以外的索引统称二级索引。它的叶子节点存的不是整行数据，而是主键值。

二级索引（name 列上的索引）：
[李四, id=2] ↔ [王五, id=3] ↔ [张三, id=1]
↑ 叶子节点只存 (索引键, 主键值)，不存其他列

3.3 回表是什么，为什么要尽量避免

以 SELECT * FROM user WHERE name = '张三'; 为例：

第 1 步：在 name 索引树中查找"张三" → 得到主键 id=1
第 2 步：拿着 id=1 再去主键索引树中查找 → 得到整行数据

第 2 步就是回表——多走了一次主键索引树的查找，相当于多一倍磁盘 I/O。

3.4 覆盖索引：一劳永逸避免回表

-- ❌ 需要回表：name 索引只有 name + id，age、city 要回表取
SELECT id, name, age, city FROM user WHERE name = '张三';

-- ✅ 覆盖索引：建包含所有所需列的联合索引
CREATE INDEX idx_name_age_city ON user(name, age, city);

-- 所需列都在索引里，不需要回表
SELECT name, age, city FROM user WHERE name = '张三';

判断是否命中覆盖索引：执行 EXPLAIN 看 Extra 列，出现 Using index 即表示覆盖索引生效。

四、联合索引与最左前缀原则

4.1 最左前缀原则

联合索引按创建时的列顺序排序，就像字典先按拼音首字母排、再按第二个字母排：

CREATE INDEX idx_a_b_c ON test(a, b, c);
-- 排序逻辑：先按 a 排，a 相同再按 b 排，b 相同再按 c 排

最左前缀原则：查询条件必须从索引最左列（a）开始，且中间不能跳过，才能利用索引。

-- ✅ 走索引
SELECT * FROM test WHERE a = 1;                    -- 用到 a
SELECT * FROM test WHERE a = 1 AND b = 2;         -- 用到 a, b
SELECT * FROM test WHERE a = 1 AND b = 2 AND c = 3; -- 用到 a, b, c
SELECT * FROM test WHERE a = 1 AND c = 3;         -- 只用到 a（跳过 b，c 用不到）

-- ❌ 不走索引
SELECT * FROM test WHERE b = 2;                   -- 没有 a，无从查起
SELECT * FROM test WHERE b = 2 AND c = 3;         -- 同上
SELECT * FROM test WHERE c = 3;                    -- 同上

一句话记住：没有最左边那一列，后面的列就像断了线的珠子——散了。

4.2 索引下推（MySQL 5.6+）

-- 联合索引 idx_name_age(name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
  • 没有索引下推：先找出所有 name LIKE '张%' 的主键 → 全部回表 → 再在 Server 层筛掉 age != 25 的行；
  • 有索引下推：找到 name LIKE '张%' 后，直接在索引中判断 age = 25，只对满足条件的行回表。

相当于把 WHERE 条件的过滤工作”下推”到存储引擎层，减少不必要的回表。对应 EXPLAIN Extra 中的 Using index condition。

五、EXPLAIN：SQL 优化的显微镜

EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY create_time DESC;

EXPLAIN 是最常用的 SQL 分析工具，重点看 type、Extra、key、rows 几个字段。

5.1 type：访问类型（最重要）

从优到差排列：

system    → 表只有一行（系统表）
const     → 主键或唯一索引等值查询，最多一行        ✅ 优秀
eq_ref    → JOIN 时用主键或唯一索引关联            ✅ 优秀
ref       → 普通索引等值查询                      ✅ 良好
range     → 索引范围扫描（>、<、BETWEEN、IN）      ⚠️ 还行
index     → 全索引扫描（扫描整个索引树）           ❌ 较差
ALL       → 全表扫描                              ❌ 最差

实际开发标准：至少达到 range 级别；看到 type=ALL 就是全表硬扫，必须优化。

5.2 Extra：额外信息

值 含义 级别
Using index 覆盖索引，不回表 🟢 最优
Using where Server 层做过滤 🟡 正常
Using index condition 索引下推生效 🟢 好
Using filesort 需要额外排序 🔴 需要优化
Using temporary 用了临时表 🔴 严重问题

5.3 key 和 rows

  • key：实际使用的索引名；为 NULL 说明索引没生效；
  • rows：优化器预估要扫描的行数，越小越好，是判断优化效果的直观指标。

六、SQL 优化实战

6.1 深分页：延迟关联

-- ❌ 深分页问题：扫描前 100010 行，再扔掉前 100000 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;

MySQL 不知道第 100000 行在哪，只能从第 1 行开始数。推荐延迟关联：

-- ✅ 先在索引中定位主键，再用主键关联取全量数据
SELECT o.*
FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t
  ON o.id = t.id;

子查询只扫 id 索引（覆盖索引、不回表），定位到 10 个主键后再关联获取完整数据。

6.2 JOIN 优化：小表驱动大表

-- ❌ 关联字段没索引 → 被驱动表每次都要全表扫描
SELECT * FROM user u
JOIN orders o ON u.id = o.user_id
WHERE u.name LIKE '%张%';

-- ✅ 优化方式
-- 1. orders.user_id 上建索引（被驱动表的关联列必须有索引）
-- 2. user 表先执行 WHERE 过滤，用小结果集驱动大表
-- 3. 去掉前缀模糊 '%张'，改成 '张%'，让 user.name 索引生效

核心原则：JOIN 时优化器会自动选小表作驱动表，但被驱动表的 JOIN 列上必须有索引，否则每次关联都是一次全表扫描。

6.3 ORDER BY 优化：利用索引排序

-- ❌ Extra 出现 Using filesort（需要额外排序，消耗大）
SELECT * FROM orders WHERE status = 1 ORDER BY create_time DESC;

-- ✅ 建联合索引，让 WHERE 和 ORDER BY 共用一个索引
CREATE INDEX idx_status_ctime ON orders(status, create_time);
SELECT * FROM orders WHERE status = 1 ORDER BY create_time DESC;

索引本身就按 (status, create_time) 排序，命中后不需要额外排序。

6.4 建索引的六要六不要

六要：

  1. WHERE、JOIN、ORDER BY 的列要建索引；
  2. 区分度高的列要建索引（手机号、邮箱等）；
  3. 优先建覆盖索引，减少回表；
  4. 字符串字段考虑前缀索引，如 idx(title(20))；
  5. 联合索引把区分度高的列放左边；
  6. 频繁查询的列优先考虑。

六不要：

  1. 不在大字段上建索引（TEXT、BLOB）；
  2. 不在低区分度列建索引（如性别只有男女）；
  3. 不在索引列上做函数/表达式运算；
  4. 不使用 % 开头的模糊匹配；
  5. 不建过多索引（单表建议不超过 5 个）；
  6. 不忽略最左前缀原则。

6.5 COUNT 优化

-- InnoDB 下 COUNT(*) 和 COUNT(1) 效率相同，优化器会改写
-- COUNT(col) 只统计 col 非 NULL 的行，可能比 COUNT(*) 慢

-- ✅ 需要粗略值时
SELECT TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mydb'
  AND TABLE_NAME = 'orders';

-- ✅ 需要精确值时：用汇总表 + 定时任务维护

七、小结

学完本篇，应能回答：B+Tree 长什么样、为什么 MySQL 选它；聚簇索引与二级索引的本质区别；什么是回表、覆盖索引如何避免；最左前缀原则与索引下推解决了什么问题；EXPLAIN 的 type 和 Extra 怎么看；深分页、JOIN、ORDER BY 如何优化。

三句最关键的认知：

  1. 索引是有序数据结构：用极矮的 B+Tree 把磁盘 I/O 压到个位数，范围查询靠叶子链表；
  2. 回表是额外一次主键查找：覆盖索引让所需列都落在索引里，Using index 是命中标志；
  3. 联合索引遵守最左前缀：从最左列连续使用，跳过的列用不到；EXPLAIN 里 type=ALL、Using filesort、Using temporary 是明确的优化信号。
