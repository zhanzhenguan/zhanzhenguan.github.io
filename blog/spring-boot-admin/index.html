这篇是 Spring Boot 系列第二十四部分，应用监控的可视化篇。每个 Spring Boot 应用自带 Actuator 暴露监控端点，但 Actuator 输出的是 JSON 接口；应用多了之后，Spring Boot Admin（SBA）把这些数据聚合起来，提供统一 Web 管理界面。技术栈：Spring Boot 3.5.16、JDK 17、Spring Boot Admin 3.5.11。代码为通用示例，敏感信息按实际环境脱敏。

一、Spring Boot Admin 是什么

1.1 一句话定位

Actuator 是数据提供方，负责采集和暴露监控端点；Spring Boot Admin 是可视化平台，负责拉取、聚合、展示这些数据。SBA 界面里可以看应用列表、健康状态、JVM 内存、线程、日志级别调整。

1.2 架构：Server + Client

SBA 由两部分组成：

  1. Admin Server：独立的 Spring Boot 应用，提供 Web 界面，接收各应用注册，轮询它们的 Actuator 端点并聚合展示；
  2. Admin Client：集成在每个被监控的业务应用里，启动后向 Server 主动注册，并让 Server 能访问自己的 Actuator 端点。

工作流程：启动 Server → 业务应用集成 Actuator 与 Client → Client 向 Server 注册 → Server 轮询拉取数据 → 管理人员在页面上查看和操作。除 Client 主动注册外，SBA 也支持通过 Eureka、Consul 等服务发现机制接入（微服务环境常用），本文用最直接的 Client 注册方式跑通核心链路。

1.3 适用场景与边界

SBA 适合中小型项目的统一监控、微服务应用状态总览、开发测试环境故障排查。但要说明边界：官方文档明确表示，SBA 不是 Grafana、Datadog 这类专业可观测平台的替代品——它不提供历史数据存储、告警规则、分布式追踪能力，擅长的是「轻量的、面向应用本身的实时监控与管理界面」。生产环境常见组合：SBA 看实时状态 + Prometheus/Grafana 看趋势和告警。

二、版本基线

2.1 SBA 版本与 Spring Boot 版本对应

SBA 版本线 对应 Spring Boot 能否用于本项目
2.x Spring Boot 2.x 否（我们要 Boot 3）
3.5.x Spring Boot 3.5.x 是
4.x（当前 latest 4.1.5） Spring Boot 4.x 否（Boot 3 项目不兼容）

容易踩的坑：Maven Central 上 SBA 的 latest 标签目前指向 4.1.5，那是给 Spring Boot 4 用的。Boot 3 项目必须选 3.5.x 线。

2.2 选型结论

本项目固定：Spring Boot 3.5.16 + Spring Boot Admin 3.5.11。核实依据：Maven Central de.codecentric:spring-boot-admin-starter-server 的 3.5.x 线最新为 3.5.11；其依赖 spring-boot-starter 版本为 3.5.14，与 3.5.16 同属 3.5.x 线，兼容；官方安装文档给出的 Quick Start 即为 spring-boot-admin-starter-server 3.5.x 用法。

三、整体设计与工程结构

Server 和 Client 是两个独立的 Spring Boot 应用（端口不同、职责不同），所以用 Maven 聚合工程管理，一个仓库两个模块。SBA 版本只在聚合 POM 里定义一次，两个模块通过 ${spring-boot-admin.version} 引用，避免版本漂移。

四、搭建 Admin Server

4.1 server 模块依赖

spring-boot-admin-starter-server 内部已经传递依赖了 spring-boot-admin-server、spring-boot-admin-server-ui（整个 Web 界面）、Thymeleaf 和 Actuator。显式写 spring-boot-starter-web 是官方 Quick Start 的推荐做法，让 Servlet 容器来源更清晰。

4.2 启动类：一个注解开启 Server

Server 端 Java 代码就这一个类，@EnableAdminServer 通过 Spring 自动发现机制加载全部所需配置：

@SpringBootApplication
@EnableAdminServer
public class AdminServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(AdminServerApplication.class, args);
    }
}

4.3 第一个坑：Thymeleaf 模板位置 WARN

spring.thymeleaf.check-template-location: false 是实测踩出来的。SBA 的 UI 页面由 spring-boot-admin-server-ui 自己打包提供，并不从 classpath:/templates/ 加载，但 Boot 的 Thymeleaf 自动配置启动时仍会检查这个目录，于是打出 Cannot find template location 的 WARN。按提示关掉检查即可，WARN 消失，UI 完全不受影响。

五、搭建 Admin Client

5.1 client 模块依赖

注意客户端用的是 starter-client，与 server 端是两个不同坐标，别引反了：

<dependency>
    <groupId>de.codecentric</groupId>
    <artifactId>spring-boot-admin-starter-client</artifactId>
</dependency>

5.2 注册与端点暴露配置

逐条说明为什么这么配：

  • spring.boot.admin.client.url：注册目标，Client 启动后按固定周期（默认 10 秒）向它 POST 注册信息，失败自动重试；
  • management.endpoints.web.exposure.include: "*"：Boot 2 之后 Actuator 默认只暴露 health，不放开的话 Server 拿不到 JVM、日志等数据；"*" 在 YAML 里必须加引号；
  • show-details: always：默认 never，不开的话健康接口对外只有 {"status":"UP"}，组件级详情（磁盘、自定义指示器）全看不到；
  • management.info.env.enabled: true：Boot 2.6 起 info 端点的 env 内容默认关闭，不开则界面 Info 页缺信息；
  • info.app.*：静态应用信息，注册后直接展示在详情页。
spring:
  boot:
    admin:
      client:
        url: http://localhost:8080

management:
  endpoints:
    web:
      exposure:
        include: "*"
  endpoint:
    health:
      show-details: always
  info:
    env:
      enabled: true

info:
  app:
    name: admin-client
    version: 1.0.0

5.3 客户端启动类

Client 端连注解都不用加——引入 starter + 配置 Server 地址，注册就自动完成。

六、写业务代码，让监控有内容可看

光注册上去，界面上只有空壳。给 Client 加一组真实业务：订单 CRUD 提供流量和日志，一个可切换的自定义健康指示器演示状态联动。

6.1 统一返回与异常处理

这里的 basePackages = "com.example.adminclient.controller" 是重点。不加限定的话，@ExceptionHandler(Exception.class) 会把 Actuator 端点、静态资源抛出的框架级异常（媒体类型协商失败、404 之类）包装成业务 500 + ERROR 堆栈，日志全是噪音。限定到业务包后，框架的异常交还框架处理。

6.2 订单 CRUD

list() 和 detail() 里用 log.debug——后面演示日志动态调级时，把级别调成 DEBUG，这些日志就会开始出现，效果直观。

6.3 自定义健康指示器：模拟外部依赖

真实系统里健康状态往往由外部依赖决定：数据库连不上、支付通道超时，应用就该从 UP 变 DOWN。教程里用内存开关模拟这个链路：

@Component("payment-channel")
public class PaymentChannelHealthIndicator implements HealthIndicator {

    private volatile boolean channelUp = true;

    @Override
    public Health health() {
        return channelUp ? Health.up().build() : Health.down().build();
    }

    public void setChannelUp(boolean up) {
        this.channelUp = up;
    }
}

@Component("payment-channel") 的名字就是它在 /actuator/health components 里的 key。

七、启动与注册验证

7.1 启动顺序

先 Server 后 Client（Client 支持失败重试，顺序反了也能自己注册上，见第十三章）。

7.2 确认注册成功的三种方式

  1. 看 Client 日志：出现注册成功记录；
  2. 查 Server 的注册 API：/instances 返回实例列表；
  3. 打开管理界面：浏览器访问 Server 地址，Wallboard 上出现 admin-client 卡片，绿色 UP。

八、管理界面导览

界面核心页面（均为实测）：

  • Wallboard（首页）：所有注册应用的卡片墙，UP 绿、DOWN 红，应用下线变 OFFLINE；
  • Details：点进应用实例后的总览页，包含 Health、Info，以及 JVM 内存（堆/非堆、各内存池）、线程（总数/活跃/守护）、CPU 使用率实时图表，数据来自 Client 各 Actuator 端点，默认按周期刷新；
  • Log：实时日志流（基于 WebSocket 输出）+ 每个 logger 的级别调整入口；
  • Environment / Beans / Mappings / Conditions：分别对应 /actuator/env、/actuator/beans、/actuator/mappings、/actuator/conditions 的可视化版本，排查「配置从哪来」「这个 Bean 存不存在」「这个路径被谁映射」时好用；
  • Metrics：/actuator/metrics 的树状浏览，可以展开看任意指标明细。

这些能力全部依赖第 5.2 节的 include: "*" 配置——不放开端点，界面这些标签页就是空的。

九、健康监控：自定义指示器与状态联动

9.1 单应用视角

payment-channel 就是第 6.3 节写的自定义指示器，与 diskSpace、ping 等 Boot 内置指示器并列。

9.2 UP → DOWN → UP 完整联动实测

模拟支付通道异常，Client 整体健康立即变化。两个细节：

  1. /actuator/health 的 HTTP 状态码跟随整体健康：UP 是 200，DOWN 是 503，body 始终是完整 JSON。写监控对接代码时判断 body 里的 status 字段，别只看 HTTP 码；
  2. 任一组件 DOWN，整体就是 DOWN——这是聚合语义。

Server 侧不是实时的：它按默认周期（状态生命周期约 10 秒 + 轮询）重新拉取 Client 健康，实测 15 秒左右界面与 /instances API 里的状态从 UP 变成 DOWN，恢复同理。这个延迟是设计行为（避免健康抖动造成状态闪烁）；生产上需要更快感知，可以调 spring.boot.admin.monitor.default-status-lifetime 和 period。

十、日志动态调级

排查线上问题最常用的能力：不重启应用，把某个 logger 从 INFO 调成 DEBUG。

10.1 用端点操作

两点实测细节：

  • 成功响应是 204 No Content（空 body），不是 200；
  • 调级后请求一次演示接口，Client 控制台立刻出现 DEBUG 日志（调级前 OrderController.list() 里的 log.debug 不输出）；验证完恢复。

在 Admin 界面的 Log 页做同样的事，是下拉框操作，效果一致。动态调级改的是运行时日志框架状态，应用重启后回到配置文件的级别，所以文件里的级别就是「默认级别」。

十一、集成测试

两个模块各一个集成测试类。Client 测试有个特别之处：测试环境禁用注册，避免向不存在的 Server 周期注册产生干扰日志。Server 测试里给 /instances 显式设置了 Accept: application/json，原因见第十三章踩坑第 2 条。

十二、端到端验证：30 项断言清单

类别 断言 结果
Server health 200、Admin UI 首页可达 2/2
业务接口 创建 200、非法参数 400、不存在 404、列表有数据 4/4

Client 端点 env / beans / mappings / conditions / configprops / loggers / metrics / threaddump 全部 200 8/8
info info 端点暴露应用信息 1/1

十三、踩坑复盘

13.1 Server 启动时 Thymeleaf WARN

Cannot find template location: classpath:/templates/。根因与解法见 4.3——SBA UI 不走这个目录，spring.thymeleaf.check-template-location=false 关闭检查。

13.2 /instances 与 UI 首页的 Accept 协商

用 Accept: application/hal+json 请求 http://localhost:8080/instances 会得到 406 Not Acceptable；UI 首页 / 用纯 JSON Accept 同样 406。正确姿势：

  • /instances：Accept: application/json，返回实例数组；
  • UI 首页：Accept: text/html（或 */*）。

TestRestTemplate.getForEntity 默认 Accept 的协商结果恰好会命中 406，所以测试里要显式设置请求头。

13.3 健康为 DOWN 时 HTTP 状态码是 503

第一次写验证脚本时，DOWN 的断言按 s == 200 判断，直接失败。实际上 Actuator 健康端点 HTTP 状态跟随聚合结果：UP=200、DOWN=503、OUT_OF_SERVICE=503，body 始终完整。这是对接监控系统时最值得记住的一条。

13.4 loggers 端点 POST 成功返回 204

POST /actuator/loggers/{name} 设置级别成功返回 204 No Content（空 body），写自动化断言别按 200 校验。

13.5 Server 停机，Client 会怎样

复验期间重启过一次 Server，Client 日志出现注册失败；Server 恢复后，Client 在下一个注册周期自动重新注册成功，全程无需重启 Client。SBA Client 的注册是「周期 + 失败重试」模型，Server 短暂不可用不影响整体可用性。

13.6 全局异常处理器必须限定包

SBA 场景下应用会被各种框架内部请求打进来（注册心跳、端点轮询、UI 静态资源），@RestControllerAdvice 不限定 basePackages 的话，这些请求的框架异常都会被业务兜底逻辑接住，产生大量误导性的 500 与 ERROR 堆栈。

十四、生产化建议

  1. 加安全：Server 界面和 Client 端点现在都是裸奔的。至少给 Server 加 Spring Security（官方 sample 有现成配置），Client 的 include: "*" 收敛为实际需要的端点列表，env、beans、configprops 这类信息泄露风险高的端点尤其要控；
  2. 状态告警：SBA Server 有状态变化事件机制，接 spring-boot-admin-starter-mail 可以在应用 DOWN/OFFLINE 时发邮件，钉钉、企微机器人用自定义 AbstractStatusChangeNotifier 也能接；
  3. 接入方式升级：微服务环境建议改服务发现接入（Eureka/Consul/Nacos），新应用上线自动出现在监控里，不需要逐个配 Client；
  4. 配合专业监控：SBA 看实时状态很顺手，但历史趋势、告警规则、容量规划还是要 Prometheus + Grafana，两者互补；
  5. HTTPS 与网络隔离：Client 的 management 端点会暴露运行时信息，生产环境应只对内网开放（或独立 management port），Server UI 走 HTTPS；
  6. 注册信息持久化：默认存在内存里，Server 重启后要等 Client 重新注册（Client 会自动补注册，通常几秒到几十秒内恢复），有持久化需求可配置 Hazelcast 集群存储。

十五、小结

回顾整条链路：

  • Admin Server：spring-boot-admin-starter-server + @EnableAdminServer，两行代码得到一个功能完整的监控中心；
  • Admin Client：spring-boot-admin-starter-client + 一段注册配置，业务应用自动上墙；
  • 监控数据：全部来自 Actuator 端点，SBA 不重复造轮子，只做聚合与可视化；
  • 核心能力实测：注册与容错重试、组件级健康展示与 UP/DOWN 联动（约 15 秒延迟）、日志级别动态调整（204 响应、立即生效）、Environment/Beans/Mappings 可视化。

三个最容易复盘的点：

  1. 版本别选错：Boot 3 用 SBA 3.5.x，Maven Central 的 latest 4.x 属于 Boot 4；
  2. 端点要放开：Client 必须暴露 Actuator 端点并开 show-details，否则 Server 界面是空的；
  3. 健康状态码：UP=200、DOWN/OUT_OF_SERVICE=503，对接监控判断 body status，别只看 HTTP 码。

备注：本篇为个人学习整理，内容基于公开学习资料归纳，代码片段为通用示例；内存仓储仅用于演示，真实项目应替换为持久层并补充认证授权。
