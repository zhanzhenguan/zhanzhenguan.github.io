一、SSO 解决什么问题

1.1 一次登录，多系统通行

没有 SSO 时，企业内部 OA、CRM、ERP 各一套账号密码、登录三次；接入 SSO 后，各系统信任同一个身份中心，用户在中心登录一次，其它系统直接放行。

1.2 传统登录与 SSO 的差别

对比项 传统独立登录 SSO
账号管理 每个系统各自维护 身份中心集中管理或联邦认证
登录入口 多个登录页 统一认证入口
密码策略 各系统各一套 统一密码策略、MFA、账号生命周期
登录体验 切换系统可能重复登录 中心会话有效时无需再输入密码
权限体系 各系统自管 认证集中，业务权限仍分系统授权
审计 日志分散 认证事件集中可审计

1.3 概念澄清：SSO 不是 JWT，也不是 Redis 共享 Session

  • JWT 只是一种令牌格式，SSO 可以用 JWT，也可以不用；
  • Redis 共享 Session 解决的是「同一应用多实例之间会话共享」，跟跨系统认证没有关系；
  • SSO 是一套跨应用的身份认证协议与会话协作机制，主流实现是 OIDC（现代 Web）或 SAML 2.0（遗留系统）。

不要把「把 Session 塞进 Redis」当成 SSO 方案，也不要用「复制 JSESSIONID」这种方式伪造单点登录。

二、版本基线与技术选型

2.1 版本矩阵

组件 版本 说明
JDK 17 Spring Boot 3.5 运行时要求
Spring Boot 3.5.16 父 POM 统一管理依赖版本
Spring Security 6.5.11 由 Boot BOM 管理，不要手动指定
Keycloak 26.8.2 身份提供方，需要 Java 21+ 运行
Maven 3.9.3 多模块构建

Spring Boot BOM 已管好 Spring Security 版本，自己再写 <version> 容易出现版本错配（如 Security 6.4 配 Boot 3.5 的 API）。

2.2 为什么选 OIDC 而不是自研 Token

自研「登录发 Token、网关校验 Token」也能跑，但会立刻遇到一串问题：Token 怎么签名、密钥怎么轮换、授权码怎么防重放、state 和 nonce 怎么校验、SPA 和移动端怎么接、怎么对接企业 AD。OIDC 把这些都标准化了，Spring Security 也把客户端侧实现做完了（发起授权、校验 state/nonce、换 Token、验签 ID Token）。应用侧要做的只剩下配置和业务权限映射。

2.3 授权码流程（Authorization Code Flow）

服务端 Web 应用一律用授权码流程：

  1. 浏览器访问受保护页面，应用返回 302，跳到 Keycloak 授权端点；
  2. 用户在 Keycloak 页面输入账号密码；
  3. Keycloak 把浏览器重定向回应用的 redirect_uri，URL 上带一个一次性授权码 code；
  4. 应用后端拿 code 走服务端通道去 Token 端点换 ID Token + Access Token；
  5. 应用校验 ID Token，建立自己的本地 Session。

密码只提交给身份中心，业务应用永远接触不到用户密码；code 即使被截获，没有客户端密钥也换不到 Token。这就是服务端应用使用 Confidential Client（带 Client Secret）的原因。Implicit Flow（Token 直接放 URL 片段返回）已明确不推荐，新系统不要用。

三、整体架构与请求链路

3.1 组件与端口

组件 端口 角色
Keycloak 8180 身份提供方（IdP / OP），维护 SSO 会话、签发 Token
App-A 8081 OIDC 客户端（Relying Party），client_id = app-a
App-B 8082 OIDC 客户端，client_id = app-b
API 服务 8083 Resource Server，校验 Access Token

App-A 与 App-B 是两个独立的客户端身份，各有自己的 Client Secret 和回调地址。它们不共享 JSESSIONID，共享的是 Keycloak 端那份登录会话。

3.2 两次访问的时序

  • 首次登录：浏览器 → App-A 未认证 → 302 跳 Keycloak → 登录 → 回调 App-A → 换 Token → 建本地 Session；
  • 第二个应用访问：同一浏览器打开 App-B → 未带本地 Session → 跳 Keycloak → 浏览器携带 Keycloak SSO Cookie，中心会话仍有效 → 直接回调 App-B 建立本地 Session，不再要密码。

四、启动 Keycloak 身份中心

4.1 两种运行方式

  • Docker Compose：最省事，适合有 Docker 的环境；
  • 官方发行包 + Java：适合本机没有 Docker 的情况。

Compose 片段（三注意）：

services:
  keycloak:
    image: quay.io/keycloak/keycloak:26.8.2
    command: ["start-dev", "--import-realm"]
    environment:
      KEYCLOAK_ADMIN: admin
      KEYCLOAK_ADMIN_PASSWORD: ${KC_ADMIN_PASSWORD:change-me}
    ports:
      - "127.0.0.1:8180:8080"
    volumes:
      - ./data/import:/opt/keycloak/data/import
  1. --import-realm 让 Keycloak 启动时自动导入 data/import/ 下的 Realm 文件，省掉手工建用户、建客户端；
  2. 端口映射写成 127.0.0.1:8180:8080，只绑回环地址，管理端口不暴露到局域网；
  3. start-dev 只能用于本地开发，生产必须用 start 模式 + 外部数据库 + HTTPS。

发行包方式：Keycloak 26.x 需要 Java 21 及以上版本。

4.2 验证 Discovery 元数据

OIDC 元数据地址是 {issuer}/.well-known/openid-configuration，Spring Security 靠它自动发现各端点。

这里的 issuer 必须和应用配置里的 issuer-uri 完全一致，包括协议、主机名、端口。浏览器访问用 localhost、应用配置写 127.0.0.1，就会报 issuer 不匹配。

五、Realm、用户、角色与客户端

5.1 概念划分

概念 说明 本示例
Realm 租户 / 认证域，用户、客户端、角色都归属其中 demo
User 登录用户 demo-user（USER）、admin-user（USER + ADMIN）
Realm Role Realm 级角色 USER、ADMIN
Client 接入的客户端应用 app-a、app-b、api-cli
SSO Session Keycloak 维护的登录会话 浏览器 Cookie 承载

Realm 导入文件里 "temporary": false 很重要：设成 true 时用户首次登录会被强制改密码，自动化测试和演示都会卡住。

5.2 客户端参数

App-A / App-B 的差异只在 Client ID、Secret、端口和回调地址：

配置项 App-A App-B
Client ID app-a app-b
Client authentication On（机密客户端） On
Standard flow On On
Direct access grants Off Off
Root URL http://localhost:8081 http://localhost:8082
Valid redirect URIs http://localhost:8081/login/oauth2/code/keycloak http://localhost:8082/login/oauth2/code/keycloak
Valid post logout redirect URIs http://localhost:8081/* http://localhost:8082/*
Web origins http://localhost:8081 http://localhost:8082

回调地址是精确匹配：协议、域名、端口、路径任一处不同都会被 Keycloak 拒绝，返回 Invalid parameter: redirect_uri；通配符能用但生产环境不建议开太大。

另有一个 api-cli 客户端，只用来在本地用密码模式换 Access Token 调 API（directAccessGrantsEnabled: true）。生产环境不要开这种客户端，它是给测试脚本用的。

5.3 让 Realm Role 进入 ID Token

Keycloak 默认把 Realm Role 放在 realm_access.roles 里，但不一定写进 ID Token。浏览器端应用从 ID Token 读身份，所以要在客户端上显式加一个协议映射：rolePrefix 留空——Spring 侧的 ROLE_ 前缀由自己的代码加，重复加会变成 ROLE_ROLE_ADMIN。

配置完必须先看实际签发的 Token 声明再写映射代码。

六、Spring Boot 客户端工程

6.1 依赖

只需要 OAuth2 Client 这一个 Starter。不需要旧版 Keycloak Adapter，也不需要自己写授权码交换逻辑——spring-boot-starter-oauth2-client 已经把 OIDC 客户端做完了。

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-client</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

6.2 application.yml

spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: ${OIDC_CLIENT_ID:app-a}
            client-secret: ${OIDC_CLIENT_SECRET:change-me}
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope: openid
        provider:
          keycloak:
            issuer-uri: http://localhost:8180/realms/demo
server:
  servlet:
    session:
      cookie:
        name: ${SESSION_COOKIE_NAME:APP_A_SESSION}

三个容易踩的点：

  1. redirect-uri 用 {baseUrl} 占位，不要写死 http://localhost:8081/...；走反向代理时 {baseUrl} 按请求推导，写死会直接错；
  2. scope 必须有 openid，没有它就不是 OIDC 流程，拿不到 ID Token；
  3. server.servlet.session.cookie.name 必须每个应用不同。

6.3 同一份代码跑两个应用

App-A 和 App-B 业务逻辑完全一样，差别只有四个环境变量：

环境变量 App-A App-B
SERVER_PORT 8081 8082
OIDC_CLIENT_ID app-a app-b
OIDC_CLIENT_SECRET app-a-secret-2026 app-b-secret-2026
SESSION_COOKIE_NAME APP_A_SESSION APP_B_SESSION

为什么 Cookie 名要区分？ 浏览器 Cookie 不区分端口。App-A 和 App-B 都在 localhost 上，如果都用默认 JSESSIONID，后登录的应用会把前一个应用的会话 Cookie 覆盖掉，表现为「登录了 A，打开 B 又要登录」「来回跳转」「会话串号」。部署到不同域名不会有这个问题，但本地演示必须有这个配置。

七、Security OAuth2 Login

7.1 配置要点

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers("/", "/login").permitAll()
                        .requestMatchers("/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .oauth2Login(oauth -> oauth
                        .userInfoEndpoint(info -> info.userAuthoritiesMapper(roleMapper())));
        return http.build();
    }

    @Bean
    public GrantedAuthoritiesMapper roleMapper() {
        return new OidcAuthoritiesMapper();
    }
}

授权失败时框架默认走 sendError(403)，浏览器看到 Whitelabel 兜底页；第九节用 AccessDeniedHandler 改成标准 JSON 响应。

7.2 Spring Security 内置的四个端点

端点 作用
GET /oauth2/authorization/keycloak 发起授权请求（keycloak 是 registrationId）
GET /login/oauth2/code/keycloak 授权回调地址，必须与 Keycloak 侧登记一致
GET /login 默认登录页
POST /logout 本地登出，默认要求 POST + CSRF Token

不需要自己写登录接口，直接访问 /oauth2/authorization/keycloak 就会跳转到 Keycloak。

7.3 千万别设成 STATELESS

浏览器端 SSO 客户端里加 sessionCreationPolicy(STATELESS) 会直接坏掉。原因：OIDC 登录完成后，应用需要自己的本地 Session 记住「这个浏览器已经认证过」，后续每次请求靠 Cookie 恢复认证上下文；设成无状态，等于每次请求都要重新走一遍 OIDC 流程，表现为无限重定向登录页。

一句话：纯 JWT API 用无状态，浏览器 Web 应用用 Session。

八、把 Keycloak 角色映射成 Spring 权限

8.1 角色声明位置

角色类型 Token 中的位置
Realm Role realm_access.roles
Client Role resource_access.{clientId}.roles

Spring Security 不会自动把 realm_access.roles 转成 ROLE_ADMIN。不做映射，hasRole("ADMIN") 永远返回 false，接口一直 403。

public class OidcAuthoritiesMapper implements GrantedAuthoritiesMapper {

    @Override
    public Collection<? extends GrantedAuthority> mapAuthorities(Collection<? extends GrantedAuthority> authorities) {
        Set<GrantedAuthority> mapped = new LinkedHashSet<>();
        authorities.forEach(a -> mapped.add(a));
        // 从 ID Token / UserInfo 的 realm_access.roles 提取角色，转成 ROLE_ 前缀
        return mapped;
    }
}

四个细节：

  1. 用 LinkedHashSet 而不是 HashSet，保留原始权限顺序，调试输出更可读；
  2. ID Token 和 UserInfo 两处都查，不同 Keycloak 映射配置下角色可能只出现在其中一处；
  3. getUserInfo() 要判空，某些配置下不会调用 UserInfo 端点，直接取值会 NPE；
  4. 角色名 toUpperCase()，保证 admin 和 ADMIN 都能匹配 hasRole("ADMIN")。

8.2 一个真实踩到的坑：OidcUser#getAuthorities() 不是最终权限

OidcUser#getAuthorities() 返回的是 OIDC 服务生成的原始权限；经过 GrantedAuthoritiesMapper 转换后的权限挂在 Authentication 上，真正参与授权判断的是后者。排查权限问题时，永远先看 Authentication#getAuthorities()。

九、用户信息接口与权限控制

9.1 两个注意点

  1. @AuthenticationPrincipal 不能省。写成 me(OidcUser oidcUser) 时，Spring MVC 会把它当普通模型属性绑定，直接抛 No primary or single unique constructor found for interface OidcUser，接口 500；
  2. 用户唯一标识用 sub，不要用 email 或姓名。邮箱会改、姓名会重名，sub 才稳定；拿到 sub 后与本地用户表建立映射关系。

9.2 权限控制两处都要做

URL 规则做粗粒度，方法注解做细粒度：hasRole("ADMIN") 匹配 ROLE_ADMIN；hasAuthority("report:read") 才是精确匹配。权限必须在服务端校验，前端隐藏按钮只是体验优化。

9.3 授权失败统一返回 JSON

403 虽然状态码正确，但页面往往是 Whitelabel 兜底页。原因是授权校验发生在两个不同位置，需要两套机制分别处理：

校验位置 异常在哪抛 谁来处理
URL 规则（/admin/**） Security 过滤器链，早于 DispatcherServlet AccessDeniedHandler
方法注解（@PreAuthorize） 控制器方法调用时 @RestControllerAdvice

@RestControllerAdvice 只能捕获后者。前者的异常框架默认交给 AccessDeniedHandlerImpl，它调用 response.sendError(403)，容器随即转发到 /error；项目没配错误视图就渲染成 Whitelabel 页。

自己实现 AccessDeniedHandler，直接写出响应体，不再走 sendError，也就不会再转发到 /error：

@Component
public class RestAccessDeniedHandler implements AccessDeniedHandler {
    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response,
                       AccessDeniedException e) throws IOException {
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"error\":\"access_denied\",\"message\":\"权限不足，拒绝访问\"}");
    }
}

在 SecurityConfig 里挂上。注意：只配置 accessDeniedHandler，不要顺手配置 authenticationEntryPoint。oauth2Login 内部已注册 LoginUrlAuthenticationEntryPoint，未登录时靠它跳转到 Keycloak；一旦显式指定自己的入口点，登录重定向就失效，表现为访问受保护页面不再跳转登录页，而是直接返回 401。

十、登录、Token 与 Session 的关系

10.1 三类 Cookie / Session

名称 保存位置 作用
Keycloak SSO Cookie 浏览器 ↔ Keycloak 域名 证明浏览器在身份中心已有登录会话
App-A Session Cookie 浏览器 ↔ App-A 域名 标识用户在 App-A 的本地会话
App-B Session Cookie 浏览器 ↔ App-B 域名 标识用户在 App-B 的本地会话

三者独立。App-B 能免密登录，靠的是浏览器带着 Keycloak 的 SSO Cookie，不是因为它能读到 App-A 的 Session。

10.2 为什么 Web 应用还要 Session

OIDC 只负责「认证这个用户是谁」这一件事，认证结果需要落在应用侧才能支撑后续几百次请求。做法是登录成功后建立本地 Session，之后靠 Cookie 恢复上下文。Keycloak 负责跨应用统一认证体验，业务应用各管各的 Session，职责清晰。

10.3 多实例部署

App-A 起三个实例时，本地 Session 在实例之间不共享，用户会在实例之间跳着登录。这时用 Spring Session + Redis 把会话集中存储即可。再强调一次：这是应用会话共享，不是 SSO 本身。

十一、单点登出

11.1 三种「登出」

动作 效果
本地登出 只清理当前应用 Session
RP-Initiated Logout 本地登出 + 重定向到 Keycloak end_session_endpoint 结束中心会话
全局登出 需 Back-Channel / Front-Channel Logout 通知其他客户端清理各自会话

setPostLogoutRedirectUri 指向的地址必须登记在 Keycloak 客户端的 Valid post logout redirect URIs 里，否则登出后 Keycloak 会拒绝跳回。首页登出按钮必须是 POST 且带 CSRF Token，不要为了方便把 /logout 改成 GET。

11.2 为什么登出了 App-A，App-B 还活着

App-A 和 App-B 的本地 Session 是两份东西。结束 Keycloak 中心会话，不会自动销毁 App-B 已建立的本地 Session。常见调和做法：缩短本地 Session 有效期，敏感操作要求重新认证；配置 Back-Channel Logout，让各客户端收到登出通知后主动销毁会话；关键业务每次校验 Token 的 exp，而不是长期信任本地会话。「跳转到 Keycloak 登出页」不等于「所有应用会话都已清除」，多浏览器、多客户端场景下要实测确认。

十二、API 服务接入 JWT Resource Server

12.1 依赖与配置

Resource Server 只写 issuer-uri 就够了：Spring Security 自动拉 Discovery 元数据、取 JWKS 公钥，验证签名并校验 iss、exp、nbf。

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>
</dependency>
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8180/realms/demo
@Configuration
public class ApiSecurityConfig {

    @Bean
    public SecurityFilterChain apiFilterChain(HttpSecurity http) throws Exception {
        http.csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/public/**").permitAll()
                    .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter())));
        return http.build();
    }
}

关 CSRF 的前提是：令牌只通过 Authorization: Bearer 传，不依赖浏览器自动带的 Cookie。如果 API 也接受 Cookie 认证，就必须重新评估 CSRF 防护。

12.2 角色转换与权限位置

Resource Server 默认只把 scope / scp 映射成 SCOPE_ 前缀权限，hasRole("ADMIN") 需要自己加转换。

这里有个坑：权限不在 Jwt 上。Jwt 只有声明，权限在 JwtAuthenticationToken 上。控制器里应注入 Authentication 再取授权，而不是直接从 Jwt 拿。

12.3 千万别把 ID Token 当 Access Token

两个 Token 长得都像 JWT，但用途完全不同：ID Token 给客户端识别用户，aud 是客户端 ID；Access Token 给 API 用，aud 应该是 API。用 ID Token 调 API，轻则 401，重则因缺少 audience 校验被放行（安全问题）。生产环境建议在 Keycloak 侧配 Audience Mapper，在 Resource Server 侧校验 aud。

十三、前后端分离与 BFF

13.1 SPA 用授权码 + PKCE

Vue / React 这类纯浏览器应用是 Public Client，没法安全保存 Client Secret。正确姿势是 Authorization Code Flow + PKCE，配合成熟的 OIDC 前端库。绝对不要把 Confidential Client 的 Secret 写进 JavaScript 或打包产物，那是公开的。

13.2 BFF 模式

安全要求高的系统可在前端和 API 之间加一层 BFF：浏览器只拿 HttpOnly + Secure + SameSite 的 Cookie，Access Token 存服务端，由后端代理访问 API。代价是要处理好 CSRF、Session 和 XSS。

13.3 CORS 不是 SSO

CORS 解决浏览器跨源访问限制，不负责认证，也实现不了单点登录。配了 CORS 也照样必须校验 Token。

十四、总结：这套方案的分工

  1. Keycloak 负责「你是谁」——统一认证、SSO 会话、用户与角色、签发 Token；
  2. Spring Security OAuth2 Client 负责浏览器端「走完协议」——发起授权、处理回调、校验 ID Token、建立本地 Session；
  3. 业务系统 负责「你能干什么」——把角色映射成自己的权限模型，在接口上做授权校验；
  4. Resource Server 负责 API 侧「令牌可信吗」——验签、校验 issuer / 时效 / 权限。
