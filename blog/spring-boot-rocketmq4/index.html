这篇是 Spring Boot 系列第十一部分，整合 RocketMQ 4.x。技术栈：JDK 17 + Spring Boot 2.7.18 + Broker 4.9.4 + rocketmq-spring-boot-starter 2.2.2。4.9.x 仍是很多团队在用的稳定版本，这篇重点记录版本匹配、本地事务一致性与消费幂等这些容易踩隐性坑的部分。代码为通用示例，连接信息用占位符。

一、先定版本：starter 与客户端必须匹配 Broker

结论：Spring Boot 2.7.18 + rocketmq-spring-boot-starter 2.2.2。

不要盲目上 2.3.x。Apache RocketMQ Spring 父 POM 里锁定的底层客户端版本：

Starter 版本 父 POM 中的 rocketmq.version 适配 4.9.x Broker
2.2.0 4.8.0 同系列，可试
2.2.1 4.9.1 可以
2.2.2 4.9.3 可以，与 4.9.4 同属 4.9 系列
2.2.3 5.0.0 不建议
2.3.6 5.3.2 不建议

从 2.2.3 开始，Starter 底层已经换成 RocketMQ 5.x 客户端。跑在 4.9.x Broker 上未必启动失败，更常见的表现是某些请求 Broker 不认、或客户端解析不了响应，出现 NoSuchMethodError、ClassNotFoundException 或莫名其妙的超时；编译期完全正常，排查成本很高。

锁定 2.2.2 后，它父 POM 依赖 rocketmq-client 4.9.3，与 4.9.4 Broker 同协议系列。依赖拉下来后务必自己核一遍：

mvn dependency:tree -Dincludes=org.apache.rocketmq

看到 rocketmq-client:4.9.3 且只有一个版本即可。

二、环境确认：先看端口，再看日志

先确认服务端真的在监听：

netstat -ano | findstr :9876
netstat -ano | findstr :10911
  • 9876：NameServer，只维护路由信息，不存消息；
  • 10911：Broker 主端口，真正负责消息存储与投递。

生产端连接 9876 拿路由，真正落盘发生在 10911，两者不要混淆。

参数含义：

  • producer.group：不是随便写的标签，事务消息回查、发送指标都按这个组归属，必须有业务含义；
  • send-message-timeout：单次同步发送的阻塞上限，不是重试总时长；
  • retry-times-when-send-failed：只对同步发送生效，指「没收到确认」的重试，不包含 Broker 明确返回失败的情况。

五、消息契约：时间用 epoch 毫秒，别用 LocalDateTime

消息 DTO：

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class OrderEvent implements Serializable {

    /** 事件唯一标识，消费幂等键 */
    private String eventId;
    private String orderId;
    /** CREATED / PAID / STATUS_CHANGED / CLOSED */
    private String eventType;
    private String status;
    private String userId;
    private BigDecimal amount;
    /** 事件发生时间，epoch 毫秒 */
    private long eventTime;
    private int schemaVersion;
    private String remark;
}

注意 eventTime 是 long 而不是 LocalDateTime。原因：rocketmq-spring 的 MappingJackson2MessageConverter 内部 自己 new 了一个 ObjectMapper，不会复用容器里注册了 JavaTimeModule 的实例。接口层用 LocalDateTime 正常，一进消息就抛：

Java 8 date/time type `java.time.LocalDateTime` not supported by default

解决方式有三种：注册自定义 MessageConverter、给字段加 @JsonSerialize、或直接用 epoch 毫秒。消息契约跨语言、跨版本，时间戳是最稳的表达，也让消费端不依赖任何 Jackson 扩展。

另外，不要把数据库实体直接当消息发出去。实体字段随表结构变化，消息契约一变所有订阅方都得跟着改；DTO 独立演进、加字段给默认值，才能向后兼容。

六、五种发送方式，收敛到一个出口

业务代码不要到处 @Autowired RocketMQTemplate，封成统一出口：

@Slf4j
@Component
@RequiredArgsConstructor
public class OrderEventProducer {

    private static final long SEND_TIMEOUT = 3000L;
    private final RocketMQTemplate rocketMQTemplate;

    private Message<OrderEvent> buildMessage(OrderEvent event) {
        return MessageBuilder.withPayload(event)
                .setHeader(RocketMQHeaders.KEYS, event.getOrderId())
                .build();
    }

    /** 同步：等 Broker 确认 */
    public SendResult sendSync(String destination, OrderEvent event) {
        return rocketMQTemplate.syncSend(destination, buildMessage(event), SEND_TIMEOUT);
    }

    /** 异步：不阻塞，但必须处理失败回调 */
    public void sendAsync(String destination, OrderEvent event) {
        rocketMQTemplate.asyncSend(destination, buildMessage(event), new SendCallback() {
            @Override
            public void onSuccess(SendResult result) {
                log.info("[异步发送-成功] msgId={}", result.getMsgId());
            }

            @Override
            public void onException(Throwable e) {
                // 生产环境这里要落库进补偿任务，不能只打日志
                log.error("[异步发送-失败] orderId={}", event.getOrderId(), e);
            }
        }, SEND_TIMEOUT);
    }

    /** 单向：不等待任何确认 */
    public void sendOneWay(String destination, OrderEvent event) {
        rocketMQTemplate.sendOneWay(destination, buildMessage(event));
    }

    /** 顺序：hashKey 决定进哪个队列 */
    public SendResult sendOrderly(String destination, OrderEvent event, String hashKey) {
        return rocketMQTemplate.syncSendOrderly(destination, buildMessage(event), hashKey, SEND_TIMEOUT);
    }

    /** 延迟：只有 Broker 预置的等级，没有任意时间 */
    public SendResult sendDelay(String destination, OrderEvent event, int level) {
        return rocketMQTemplate.syncSend(destination, buildMessage(event), SEND_TIMEOUT, level);
    }
}

目的地写法是 topic:tag：

rocketMQTemplate.syncSend("order-topic:created", message, 3000);

KEYS 是特殊 header，控制台可按它检索消息，排查线上问题很有用；但它不是幂等键——只用于检索，不保证唯一，也不参与投递判断，幂等要靠业务自己的 eventId。

五种方式选型：

方式 是否等确认 性能 适用场景
同步 syncSend 等 低 订单、支付等必须知道结果的
异步 asyncSend 不等，回调通知 中 高吞吐又要能感知失败
单向 sendOneWay 不等，无回调 高 日志、埋点，允许丢
顺序 syncSendOrderly 等 低 同一实体的状态流转
延迟 sendDelay 等 中 超时关单、延迟提醒

七、事务消息：订单落库与事件投递的一致性

普通消息存在两难：先写库再发消息，消息失败则库里有订单但下游不知道；先发消息再写库，写库失败则下游收到不存在的订单。本地事务管不了 MQ。

RocketMQ 的解法是半消息：先把消息发给 Broker 但标记为不可投递，然后执行本地事务；成功提交消息，失败回滚。Broker 长时间收不到确认，会反过来回查生产者这笔事务到底成没成。

7.1 发送端

public OrderEvent placeOrder(PlaceOrderCommand command) {
    if (orderRepository.exists(command.getOrderId())) {
        throw new IllegalStateException("订单已存在，请勿重复提交：" + command.getOrderId());
    }

    OrderEvent event = OrderEvent.builder()
            .eventId(UUID.randomUUID().toString())
            .orderId(command.getOrderId())
            .eventType("CREATED")
            .status(OrderStatus.CREATED)
            .userId(command.getUserId())
            .amount(command.getAmount())
            .eventTime(System.currentTimeMillis())
            .schemaVersion(1)
            .build();

    TransactionSendResult result =
            rocketMQTemplate.sendMessageInTransaction(TX_TOPIC, buildMessage(event), command);

    if (result.getLocalTransactionState() != LocalTransactionState.COMMIT_MESSAGE) {
        throw new IllegalStateException("订单创建未生效，orderId=" + command.getOrderId());
    }
    return event;
}

第三个参数 arg 会原样传给本地事务监听器。这里把整个下单命令塞进去，本地事务就不必再从消息体反序列化一次。

7.2 本地事务与回查

@RocketMQTransactionListener
@RequiredArgsConstructor
public class OrderTransactionListener implements RocketMQLocalTransactionListener {

    private final LocalTransactionService localTransactionService;

    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(Message message, Object arg) {
        PlaceOrderCommand command = (PlaceOrderCommand) arg;
        try {
            localTransactionService.createOrder(command);
            return RocketMQLocalTransactionState.COMMIT;
        } catch (DuplicateKeyException e) {
            // 并发重复提交，回滚半消息，避免下游再收一条重复事件
            return RocketMQLocalTransactionState.ROLLBACK;
        } catch (Exception e) {
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }

    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message message) {
        String orderId = (String) message.getHeaders().get(RocketMQHeaders.KEYS);
        if (orderId == null || orderId.isEmpty()) {
            return RocketMQLocalTransactionState.UNKNOWN;
        }
        return localTransactionService.exists(orderId)
                ? RocketMQLocalTransactionState.COMMIT
                : RocketMQLocalTransactionState.ROLLBACK;
    }
}

两个设计决定：

第一，本地事务必须放在独立 Bean 里。 createOrder 带 @Transactional，若与调用方在同一类就是自调用，不走 Spring 代理，事务注解静默失效——代码能跑但回滚不了，这种 bug 最难发现。

第二，回查不能依赖内存状态。 回查发生在 Broker 判断「消息状态不明」时，可能几十秒后，也可能生产者已经重启过。判定依据只能是数据库持久化结果；查不出来（如消息缺 KEYS）返回 UNKNOWN，让 Broker 继续问，而不是拍脑袋给 COMMIT。

7.3 重复提交两道防线

最初一版本地事务遇到主键冲突就返回 COMMIT，理由是「订单已存在说明之前成功」。实测问题：同一 orderId 提交两次，第二次虽没插进库，但半消息被提交，下游又收到一条创建事件，通知流水多一条。幂等做在了订单表，没做在事件上。

正确做法：入口先 exists 挡掉；并发场景漏过去的靠 DuplicateKeyException 回滚半消息。两道防线保证消息不重复投递。

sendMessageInTransaction 返回的 LocalTransactionState 只有 COMMIT_MESSAGE 才继续往下走；UNKNOWN 意味着 Broker 稍后回查，此时补发延迟消息没有意义。

八、消费端要处理的三件事

8.1 Tag 过滤：一个 Topic，多个订阅方

@Component
@RocketMQMessageListener(
        topic = MqConst.ORDER_TOPIC,
        consumerGroup = MqConst.GROUP_CREATED,
        selectorExpression = MqConst.TAG_CREATED)
public class OrderCreatedConsumer implements RocketMQListener<OrderEvent> {

    @Override
    public void onMessage(OrderEvent event) {
        try {
            consumeService.handleCreated(event);
        } catch (Exception e) {
            log.error("[消费失败] orderId={}", event.getOrderId(), e);
            throw new RuntimeException(e);   // 必须抛，否则框架认为消费成功
        }
    }
}

同一个 order-topic 下，created 和 paid 各有消费者，用不同消费组。标准做法：不同业务方用不同 Group，各管各的位点。两个业务方塞进同一个 Group，消息会被分摊，每个业务方只收到一部分，这是很常见的误用。

8.2 顺序消费

@RocketMQMessageListener(
        topic = MqConst.ORDER_TOPIC,
        consumerGroup = MqConst.GROUP_STATUS,
        selectorExpression = MqConst.TAG_STATUS,
        consumeMode = ConsumeMode.ORDERLY)

生产端配合 syncSendOrderly(destination, message, orderId)，同一 orderId 哈希到同一队列；消费端 ORDERLY 按队列加锁顺序消费。

代价要说清楚：一条消息卡住，整个队列后面的消息都等着。顺序消费的业务逻辑必须短、可控，不要在里面同步调外部接口。RocketMQ 4.x 的顺序是队列内有序，不是 Topic 全局有序；不同订单之间没有先后关系。

8.3 幂等：数据库唯一键，别靠内存

幂等表关键 DDL：

CREATE TABLE mq_consume_record (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    consumer_group VARCHAR(128) NOT NULL,
    event_id      VARCHAR(64) NOT NULL,
    created_at    BIGINT NOT NULL,
    CONSTRAINT uk_group_event UNIQUE (consumer_group, event_id)
);

消费逻辑：

@Transactional(rollbackFor = Exception.class)
public void handleCreated(OrderEvent event) {
    if (!firstConsume(MqConst.GROUP_CREATED, event)) {
        return;
    }
    notifyRepository.insert(event.getOrderId(), event.getEventId(),
            "CREATED", System.currentTimeMillis());
}

private boolean firstConsume(String consumerGroup, OrderEvent event) {
    boolean first = consumeRecordRepository.tryInsert(
            consumerGroup, event.getEventId(), System.currentTimeMillis());
    if (!first) {
        log.warn("[幂等拦截] 重复消息已忽略，eventId={}", event.getEventId());
    }
    return first;
}

tryInsert 捕获 DuplicateKeyException 返回 false，表示这条消息处理过。

关键点在 @Transactional 的位置：必须在 Service 上，不能在 onMessage 上。 onMessage 由 RocketMQ 线程直接调用，不经过 Spring 代理，注解不生效。

为什么一定要事务：「写幂等记录」和「写业务数据」必须同生共死——

  • 业务成功、记录没写 → 下次重试重复处理；
  • 记录写了、业务失败 → 消息被永久标记「已消费」，业务永远丢了（更致命且隐蔽）。

放在同一事务里，业务抛异常 → 事务回滚 → 幂等记录一并回滚 → 下次重试还能完整走一遍。另外不要在代码里 catch 住异常只打日志然后正常返回：框架看到方法正常结束就认为消费成功，消息再也不会重投，等于静默丢消息。

九、延迟消息做超时关单

RocketMQ 4.x 延迟消息只有固定等级，没有任意时间。默认 18 个等级：1s、5s、10s、30s、1m、2m……2h，等级 3 对应 10 秒。

// 下单成功后补发，失败也不影响主流程，由兜底任务补偿
producer.sendDelay(ORDER_TIMEOUT_TOPIC, timeoutEvent, 3);

消费端不能「收到就关单」，必须回查业务状态：

@Transactional(rollbackFor = Exception.class)
public void handleTimeoutCheck(OrderEvent event) {
    if (!firstConsume(MqConst.GROUP_TIMEOUT, event)) {
        return;
    }
    OrderRecord order = orderService.findOrder(event.getOrderId()).orElse(null);
    if (order == null) {
        log.warn("[消费-timeout] 订单不存在，忽略超时消息，orderId={}", event.getOrderId());
        return;
    }
    if (OrderStatus.CREATED.equals(order.getStatus())
            && orderService.closeOrderIfUnpaid(order.getOrderId())) {
        log.info("[消费-timeout] 订单超时未支付，已关闭，orderId={}", event.getOrderId());
    } else {
        log.info("[消费-timeout] 订单当前状态为 {}，无需关单", order.getStatus());
    }
}

关单本身是条件更新：UPDATE ... SET status='CLOSED' WHERE order_id=? AND status='CREATED'。返回 0 行说明订单已被支付或已被别的线程关掉，直接跳过。这条 SQL 是并发安全的关键，别用「先查再改」。

十、踩坑清单

1. 端口冲突报了个没配过的端口

报错端口号和配置对不上时（例如配置 8080 却报别的端口占用），先怀疑有更高优先级的配置源覆盖。Spring Boot 配置优先级：命令行参数 > SPRING_APPLICATION_JSON > 系统属性 > 环境变量 > 配置文件。用 --server.port=8090 显式传一次即可确认。

2. 控制台中文乱码

JDK 17 在 Windows 下默认字符集仍是 GBK（默认 UTF-8 是 JDK 18 才落地）。源码和日志文件是 UTF-8，控制台按 GBK 解码就成乱码。解法：启动参数加 -Dfile.encoding=UTF-8；IDEA File Encoding 全部设 UTF-8；或升级 JDK 18+。

3. 消费者启动后半天收不到消息

新 Topic 第一次写入时由 Broker 自动创建，消费者此时还没拿到路由。客户端路由信息默认 30 秒刷新一次，刚启动就发消息可能要等半分钟才被消费。生产环境应提前建好 Topic，别依赖自动创建。

4. 事务消息回查一直 UNKNOWN

回查取不到 KEYS，多半是发送时没设置 header，MessageBuilder.setHeader(RocketMQHeaders.KEYS, orderId) 别漏。回查方法里也不要用 ThreadLocal 或内存变量判断——回查线程和发送线程不是同一个。

5. 顺序消息把队列堵死

顺序消费失败会阻塞整个队列。若业务里有「偶发失败靠重试恢复」的逻辑，在顺序队列里就是灾难：一条毒消息能让队列停摆。要么保证顺序队列逻辑不会失败，要么用挂起当前队列的机制控制阻塞时长。

十一、上线前检查项

  • 用 dependency:tree 确认 rocketmq-client 只有一个版本，且与 Broker 匹配；
  • 生产环境关掉 autoCreateTopicEnable，Topic 和消费组提前创建；
  • 关键链路用同步发送或可靠异步，失败要有落库补偿，不能只打日志；
  • 消费端幂等用数据库唯一键，不用 Redis 短 TTL 锁；
  • 死信队列、消费堆积、发送失败率都要有监控告警；
  • 消息体不要放敏感信息，日志脱敏；
  • 顺序消费的队列数要评估，队列数决定并行度上限。

十二、小结

  • 4.x 整合的第一步是版本匹配：starter 2.2.2 对应 client 4.9.3，2.2.3 起底层换 5.x 客户端，不要乱上高版本；
  • 生产者收敛到统一出口，按同步/异步/单向/顺序/延迟五种语义选型；KEYS 只用于检索，幂等靠业务 eventId；
  • 事务消息走半消息 → 本地事务 → 提交/回滚 → 回查，本地事务放独立 Bean，回查只读数据库；
  • 消费端用不同 Group 做 Tag 过滤，顺序消费是队列内有序；幂等记录与业务数据在同一本地事务，事务注解加在 Service 上；
  • 延迟消息只有固定等级，关单靠条件更新 + 状态回查；重点避开版本错配、配置覆盖、字符集、路由延迟、回查状态、队列阻塞这几类坑。
