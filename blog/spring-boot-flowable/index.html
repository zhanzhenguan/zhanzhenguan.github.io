一、版本基线

组件 本文版本 用途
JDK 17 运行环境
Spring Boot 3.5.4 应用框架
Flowable 7.2.0 BPMN 流程引擎 + Spring Boot Starter
MySQL 8.0.45 持久化业务表与 ACT_* 引擎表
Maven 3.9.3 构建

这个组合不是随手选的，两条关键事实：

  • Flowable 7.2.0（2025-08-21）Release Notes 明确 Upgrade to Spring Boot 3.5.4；
  • Flowable 8.0.0 Breaking Changes 写明：Flowable 8 is now based on Spring Framework 7 and Spring Boot 4. There is no support for Spring Boot 3 anymore.

也就是说，Spring Boot 3 项目应该用 7.2.0，把 8.x 拽进来会直接踩到 Spring 7 / Jackson 3 的不兼容。7.2.0 的元数据基线就是 3.5.4，不擅自升到其它 3.5.x 补丁版本——要升必须重新跑完整回归。

1.1 依赖树两个注意点

  1. Boot 3.5.4 的 BOM 把 MySQL 驱动管到 Connector/J 9.3.0，不是 8.x。实测连 MySQL 8.0.45 服务端完全正常，不需要手动降版本，也不要在 pom 里自己写死版本。
  2. 只引 process starter：常规 BPMN 审批只需要 flowable-spring-boot-starter-process，它会传递引入 flowable-engine 和所需自动配置。不要一上来就引聚合的 flowable-spring-boot-starter，那会把 CMMN、DMN、Event Registry 等用不到的引擎一起拖进来。

7.2.0 的 process starter 自带 IDM / Event Registry 配置器，启动日志会出现 IdmEngineConfigurator、SpringEventRegistryConfigurator 并额外建一批 flw_* / act_id_* 表，不影响 BPMN 功能，不用手动排除。

二、五个核心概念与六大服务

工作流教程最容易劝退人的地方，是几个名词长得太像。先钉死：

概念 含义 本文例子
Process Definition 流程定义，可反复启动的模板 leaveApproval:1:xxx
Deployment 一次部署记录，保存资源与版本 启动时自动部署的 BPMN 文件
Process Instance 按定义启动的一次具体运行 张三的一次请假申请
Task 需要人工办理的任务实例 部门经理待审批的那条
Process Variable 流程运行期间的数据 approverId、days、approved

一句话串起来：部署把 BPMN 变成流程定义，按定义启动得到流程实例，实例走到 User Task 生成待办任务，办理时写入流程变量决定网关往哪走。

对应的 Flowable 服务，由 starter 自动装配，构造器注入即可，不需要自己 buildProcessEngine()：

服务 职责
RepositoryService 部署流程定义、查询定义与部署资源
RuntimeService 启动、查询运行实例，管理运行变量
TaskService 查询、认领、完成任务
HistoryService 查询历史实例、任务轨迹、历史变量
IdentityService 设置认证用户（决定历史里的发起人）
ManagementService 作业、异步执行器、表管理等

三、流程设计：一条请假审批主线

示例流程固定四步：

步骤 节点 说明
1 开始事件 员工提交申请，传入申请人、审批人、天数、事由
2 部门经理审批 引擎创建分配给 approverId 的用户任务
3 排他网关 按 approved 布尔变量选分支
4A / 4B 通过 / 驳回 各走一个结束事件，流程结束

架构上是「业务系统调用嵌入式引擎」：Spring MVC 收请求 → 业务 Service 校验并调 Flowable API → MySQL 同时存业务表与 ACT_* 表。

3.1 业务数据与流程数据必须分表

这是很多新手项目后期最难改的决定：

  • leave_request 业务表存请假单详情、申请人、天数、业务状态；
  • ACT_* 引擎表由 Flowable 全权管理，不要手工改、不要加字段、不要直接删运行记录；
  • 两者通过 businessKey（业务单号）和 processInstanceId 关联。

业务单号直接作为 businessKey 传给引擎，后面查状态、查历史、做幂等都靠它。

五、准备 MySQL 数据库

先手工建库（这一步需要 DBA 权限，应用启动时做不了）。生产环境建议同时建一个最小权限账号，别让应用用 root 跑。

两类表由应用自动创建：

表 谁创建 怎么触发
leave_request 业务表 应用 spring.sql.init.mode=always 执行 resources/schema.sql
ACT_* 引擎表 Flowable flowable.database-schema-update=true

实测首次启动后库里出现 47 张表，包括 ACT_RE_PROCDEF、ACT_RU_TASK、ACT_RU_EXECUTION、ACT_HI_PROCINST、ACT_HI_TASKINST、ACT_HI_VARINST，以及 IDM / Event Registry 相关的 act_id_*、flw_*。

database-schema-update=true 只适合本地开发和首次验证。生产必须改成 false，按对应版本的升级脚本做受控变更，应用账号只保留 DML 权限。

逐项说明：

配置 作用

history-level: audit 保存流程实例、活动、任务、变量历史
async-executor-activate: false 示例无定时器和异步节点，先关掉；用了异步 Service Task 再打开

6.1 坑：YAML 单引号必须闭合

配置行开头有单引号、结尾没有时，YAML 解析到行尾发现引号标量没闭合，会直接报扫描错误，或被解析成非预期值，表现是「BPMN 扫不到 / 启动失败」。这类错误发生在配置绑定阶段，日志里不会有「文件不存在」之类的友好提示，排查时优先看 application.yml 本身。

七、设计 BPMN 2.0 流程文件

放在 src/main/resources/processes/leave-approval.bpmn20.xml：

<?xml version="1.0" encoding="UTF-8"?>
<definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL"
             xmlns:flowable="http://flowable.org/flowable"
             targetNamespace="http://flowable.org/demo">

  <process id="leaveApproval" isExecutable="true">

    <startEvent id="start" />

    <userTask id="managerTask" flowable:assignee="${approverId}" name="部门经理审批" />

    <exclusiveGateway id="approvalGateway" />

    <sequenceFlow id="toApprove" sourceRef="approvalGateway" targetRef="approvedEnd">
      <conditionExpression xsi:type="tFormalExpression">
        <![CDATA[${approved == true}]]>
      </conditionExpression>
    </sequenceFlow>
    <sequenceFlow id="toReject" sourceRef="approvalGateway" targetRef="rejectedEnd">
      <conditionExpression xsi:type="tFormalExpression">
        <![CDATA[${approved == false}]]>
      </conditionExpression>
    </sequenceFlow>

    <endEvent id="approvedEnd" />
    <endEvent id="rejectedEnd" />

    <sequenceFlow sourceRef="start" targetRef="managerTask" />
    <sequenceFlow sourceRef="managerTask" targetRef="approvalGateway" />
  </process>
</definitions>

关键字段：

字段 含义
process id="leaveApproval" 流程定义 Key，启动时 startProcessInstanceByKey("leaveApproval", ...) 用的就是它，写错会报 No process definition
isExecutable="true" 标识可执行流程，漏了部署后无法启动
flowable:assignee="${approverId}" 从流程变量动态取审批人，所以启动流程时必须传 approverId
exclusiveGateway 排他网关，按出线条件选且只选一条
${approved == true} / ${approved == false} 两条出线的条件，变量必须是 Boolean

网关最容易踩两个坑：一是 approved 变量没传或类型不对，引擎报「无出线可走」，办理任务时要显式写入布尔变量；二是两条出线都写了条件、没有默认流，变量齐全就没问题，以后加分支记得给一条留默认出线兜底。条件表达式用 CDATA 包一层是必要的，避免 XML 把 <、&& 之类字符当标签解析。

八、启动验证：自动建表与自动部署

启动后日志三处关键信息，重点是 SpringBootAutoDeployment 扫到 jar 包里的 BPMN 并完成部署。注意路径是 jar 内部的 BOOT-INF/classes/processes/，所以文件必须放在 src/main/resources/processes/，放错目录不会被扫到。

同一个 Key 多次部署会累加 version，启动实例默认用最新版本；已经跑起来的实例仍绑定它启动时的那一版。

九、业务表与幂等：解决并发重复提交

「先查有没有运行中的实例，再启动」挡不住并发——两个请求同时通过预检查，就会生成两个流程实例。正确做法是数据库唯一约束兜底。业务表 DDL：

CREATE TABLE IF NOT EXISTS leave_request (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    business_key VARCHAR(64) NOT NULL,
    applicant_id VARCHAR(64) NOT NULL,
    approver_id VARCHAR(64) NOT NULL,
    days INT NOT NULL,
    reason VARCHAR(255),
    status VARCHAR(32) NOT NULL DEFAULT 'RUNNING',
    process_instance_id VARCHAR(64),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_business_key UNIQUE (business_key)
);

发起流程时三步放在同一个事务里：先写业务表、再设认证用户、最后启动流程实例。

三个细节：

  1. 业务表写入与引擎调用共用同一个 DataSource 和事务管理器，任何一步失败一起回滚，不会出现「有业务单但没流程」或反过来。
  2. identityService.setAuthenticatedUserId(applicantId) 决定 ACT_HI_PROCINST.START_USER_ID_ 有没有值。不设置的话，历史查询里 startUserId 是 null。它是 ThreadLocal，用完必须在 finally 里清空，否则线程复用会串号。
  3. DuplicateKeyException 交给全局异常处理映射成 HTTP 409，前端能明确知道是重复提交，而不是看到一个 500。

十、Service 层：待办、审批与历史查询

10.1 请求 DTO 用 record + 校验注解

public record StartLeaveRequest(

10.2 查询待办

BPMN 用 assignee 直接分配，用 taskAssignee 查：

List<Task> todoTasks(String userId) {
    return taskService.createTaskQuery()
            .taskAssignee(userId)
            .orderByTaskCreateTime().desc()
            .list();
}

如果改成 flowable:candidateGroups="MANAGER" 候选组，查询要换成 taskCandidateGroup("MANAGER")，办理前还要先 taskService.claim(taskId, userId)，两者不能混用。

10.3 办理审批

void complete(String taskId, String operatorId, boolean approved, String comment) {
    Task task = taskService.createTaskQuery().taskId(taskId).singleResult();
    if (task == null || !operatorId.equals(task.getAssignee())) {
        throw new IllegalArgumentException("任务不存在、已办理或当前用户无权办理");
    }
    Map<String, Object> vars = new HashMap<>();
    vars.put("approved", approved);
    taskService.complete(taskId, vars);
}

taskService.complete() 一执行，引擎立刻计算排他网关条件，走对应结束事件，运行实例从 ACT_RU_* 移除，历史留在 ACT_HI_*。

权限提醒：operatorId 由前端传入只适合教程演示。生产项目必须从 Principal / JWT 里取当前用户 ID，否则攻击者可以伪造审批人。用 taskAssignee 做基本限定不等于完整的认证授权。

10.4 运行状态与历史查询

running != null 表示流程还在跑；一旦到达结束事件，运行实例被删除，只能从 HistoryService 查。历史任务轨迹和历史变量同理。历史级别会限制可查范围：audit 足够覆盖常规审批轨迹；要更完整的活动级记录再评估 full，但要注意数据量。

十一、统一响应与异常处理：把 500 变成 4xx

Controller 直接返回 Map/List，一旦 Service 抛 IllegalArgumentException，Spring 默认给一个 HTTP 500 + 一堆堆栈，调用方分不清「参数填错了」和「服务挂了」。补统一响应体和全局异常处理器：

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> validation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldError() != null
                ? e.getBindingResult().getFieldError().getDefaultMessage() : "参数校验失败";
        return ResponseEntity.badRequest().body(Map.of("success", false, "message", msg));
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, Object>> badRequest(IllegalArgumentException e) {
        return ResponseEntity.badRequest().body(Map.of("success", false, "message", e.getMessage()));
    }

    @ExceptionHandler(DuplicateKeyException.class)
    public ResponseEntity<Map<String, Object>> conflict(DuplicateKeyException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(Map.of("success", false, "message", "该业务单号已存在，请勿重复提交"));
    }

    @ExceptionHandler(FlowableObjectNotFoundException.class)
    public ResponseEntity<Map<String, Object>> notFound(FlowableObjectNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Map.of("success", false, "message", "流程对象不存在"));
    }

    @ExceptionHandler(FlowableException.class)
    public ResponseEntity<Map<String, Object>> flowable(FlowableException e) {
        return ResponseEntity.badRequest().body(Map.of("success", false, "message", e.getMessage()));
    }
}

映射结果：

异常 HTTP 典型场景
MethodArgumentNotValidException 400 days=0、缺 businessKey
IllegalArgumentException 400 越权办理、查不存在的实例、空 userId
DuplicateKeyException 409 重复提交同一业务单号
FlowableObjectNotFoundException 404 流程对象不存在
FlowableException 400 流程定义未部署、网关表达式错误
其它 500 真正的服务端错误，记日志

十三、端到端实测

按「先部署确认 → 发起 → 查待办 → 查状态 → 审批 → 查历史」的顺序跑，再补驳回分支和异常场景。

13.1 通过分支

发起申请后待办任务自动生成；运行中状态 startUserId 有值，说明 setAuthenticatedUserId 生效；审批通过后再查，实例已从运行时移除；历史任务轨迹与变量可查，中文审批意见在入库、查询、返回三段链路都正常。

13.2 驳回分支

同一套流程换 approved=false，实测 running=false、approved=false 已持久化，业务单状态变成 REJECTED。这证明排他网关两条出线都被真实走到，不是只测了顺的那条。

13.3 异常与边界

场景 实测结果
重复提交同一业务单号 HTTP 409，该业务单号已存在，请勿重复提交
days=0 HTTP 400，请假天数至少为 1
缺 businessKey HTTP 400，businessKey 不能为空
越权办理他人任务 HTTP 400，任务不存在、已办理或当前用户无权办理
空 userId HTTP 400，userId 不能为空
查不存在的流程实例 HTTP 400（非 500），流程实例不存在

十四、踩坑汇总与生产化建议

14.1 踩坑速查

现象 原因 处理
启动失败或 BPMN 扫不到 YAML 后缀配置单引号未闭合 补上结尾引号
No process definition ... for key BPMN process id 与启动参数不一致，或文件不在 resources/processes/ 核对 id、目录、部署日志
审批后网关报无出线 approved 变量缺失/类型不对 完成任务时显式写 Boolean
历史 startUserId 为 null 未设置认证用户 setAuthenticatedUserId，用完清空
参数/权限错误返回 500 没有全局异常处理 @RestControllerAdvice 映射 4xx
重复提交生成多实例 只做「先查再启动」预检查 业务表唯一键 + 事务
Windows 控制台中文乱码 Logback 跟随系统 GBK logging.charset.console: UTF-8
ACT_* 表结构版本异常 引擎版本与库表版本不一致 核对版本与升级脚本，生产走受控升级
静态资源 404 被刷成 ERROR 堆栈 兜底 @ExceptionHandler(Exception.class) 把静态资源 404 当服务端故障 显式处理 NoResourceFoundException 返回 404

14.2 生产化清单

  1. 关闭 database-schema-update，应用账号收回 DDL 权限；
  2. userId / operatorId 一律从登录态取，待办、认领、办理、查历史都做数据权限校验；
  3. 流程发布改成受控操作，记录 BPMN 文件、版本、发布人、审批与回滚预案；流程 Key 保持稳定，已运行实例继续绑定旧版本；
  4. 用了定时器或异步 Service Task 才启用 async-executor-activate，Delegate 必须幂等；外部通知走 Outbox / 异步作业，不要指望数据库事务能回滚外部系统；
  5. 待办查询分页，历史级别按审计与数据量评估；流程变量不放超大 JSON、附件二进制、口令和令牌；
  6. 多实例部署共享同一数据库，配置异步作业锁与时钟同步，监控 ACT_RU_*、ACT_HI_*、作业积压和连接池。

十五、前端可视化页面：把请求流程画出来

后端闭环后，只看接口文档或 curl 命令，很难建立「一次审批到底发了几个请求、上一步的哪个返回值喂给了下一步」的直觉。工程可补一个零依赖的静态页面，放在 src/main/resources/static/，Spring Boot 默认托管 classpath:/static/，java -jar 启动后同源访问，不需要 Node、不需要打包，也不需要配 CORS。

页面所有请求走同一个 execute 函数，关键在 step.after 负责把上一步返回值写进上下文：发起申请时存 processInstanceId，查待办时按它匹配出 taskId，办理审批和查历史就从上下文取——7 步顺序不是写死的脚本，而是由依赖关系串起来的。

页面操作 请求 依赖
① 查看流程定义 GET /api/process/definitions 无
② 发起请假申请 POST /api/leave/start 无
③ 查询审批人待办 GET /api/leave/tasks?userId= ② 的流程实例
④ 办理审批任务 POST /api/leave/tasks/{taskId}/complete ③ 的 taskId
⑤ 查询运行状态 GET /api/process/instances/{id}/status ② 的 processInstanceId
⑥ 查询审批轨迹 GET /api/process/instances/{id}/history/tasks 同上
⑦ 查询历史变量 GET /api/process/instances/{id}/history/variables 同上

页面价值不在「好看」，而在把不可见的调用链变成可见证据：哪个参数来自上一步、哪一步返回 4xx、耗时花在哪、错误信息长什么样，都能直接指着屏幕讲，对联调和排查「为什么流程没走完」都好用。

十六、小结

把 Flowable 接进 Spring Boot 3，真正花时间的不是写 startProcessInstanceByKey 那几行，而是四件事：版本组合选对、BPMN 放对位置并确认部署成功、业务表与引擎表用事务和唯一键对齐、异常与权限边界收干净。三个最容易复盘的点：

  1. Boot 3 配 Flowable 7.2.0，8.x 已转向 Spring 7 / Boot 4，别混进依赖树；
  2. 业务表与 ACT_* 分表，靠 businessKey 关联，引擎表不手工改；
  3. 并发幂等靠唯一约束 + 事务，「先查再启动」挡不住并发。
