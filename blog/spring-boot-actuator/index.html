这篇是 Spring Boot 系列第二十三部分，应用监控篇。Actuator 不写业务逻辑，它把应用的健康状态、运行指标、容器信息和环境配置暴露成一组 HTTP 端点，供开发排查或监控系统采集。技术栈：Spring Boot 3.5.16、JDK 17、Micrometer 1.15.12（由 Actuator 传递引入）、Prometheus Java Client 1.3.10。代码为通用示例，敏感信息按实际环境脱敏。

一、版本基线

组件 版本
JDK 17
Spring Boot 3.5.16
Maven 3.9.3
Micrometer 1.15.12（由 Actuator 传递引入）
Prometheus Java Client 1.3.10
应用端口 8080

Micrometer 与 Prometheus client 的版本全部交给 Boot BOM 托管，pom 里不写第三方版本号，这是保证「依赖能下载」和「版本真兼容」同时成立的最省事做法。

1.1 动手前先核实的三个官方事实

Actuator 的配置语义在 Boot 2 到 Boot 3 之间变过好几次，按官方参考文档核对三条：

  1. 默认只暴露 health：By default, only the health endpoint is exposed over HTTP and JMX，management.endpoints.web.exposure.include 默认值就是 health。不显式配置 include，/actuator/info、/actuator/metrics 都会返回 404。
  2. health.show-details 默认 never：默认 /actuator/health 只返回 {"status":"UP"}，看不到任何组件明细，需要显式设置 always 或 when-authorized。
  3. 3.5 引入了 access 访问级别：management.endpoint.<id>.access 可取 unrestricted、read-only、none；除 shutdown 与 heapdump 外，其余端点默认 unrestricted。另外 exclude 优先级高于 include，YAML 里用 * 表示全部端点时必须加引号。

二、创建工程与依赖

2.1 pom.xml

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <!-- 核心依赖：端点框架、健康体系与 Micrometer 门面 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-validation</artifactId>
    </dependency>
    <!-- /actuator/prometheus 端点自动装配的前提，少了它端点不会注册 -->
    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-registry-prometheus</artifactId>
    </dependency>
</dependencies>

四个依赖各自解决什么问题：

  • spring-boot-starter-web：提供 Spring MVC，Actuator 的 Web 端点需要 Web 容器才能挂载；业务接口也才能产生 HTTP 指标。
  • spring-boot-starter-actuator：核心依赖，提供端点框架、健康体系与 Micrometer 门面。
  • spring-boot-starter-validation：让请求 DTO 的 @NotBlank / @Min 生效，演示参数校验失败映射成 400 而不是 500。
  • micrometer-registry-prometheus：/actuator/prometheus 端点能否自动装配的前提，依赖树会带入 prometheus-metrics-core 与 prometheus-metrics-exposition-formats。

三、写 application.yml

3.1 完整配置（本地学习）

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus,env,beans,mappings,conditions,configprops,loggers,threaddump,heapdump,httpexchanges,caches,scheduledtasks,appstatus
  endpoint:
    health:
      show-details: always
      group:
        custom:
          include: storage,diskSpace
    heapdump:
      access: unrestricted
  info:
    env:
      enabled: true
    java:
      enabled: true
    os:
      enabled: true

info:
  app:
    name: actuator-demo
    version: 1.0.0

3.2 端点暴露清单

include 里显式列端点 ID，本地学习需要逐个验证才列全；生产环境绝不这么写，见第十三章。启动日志会打印实际生效的端点数量，这是配置是否落地最直接的证据。如果数量少于预期，优先查三件事：对应端点的条件依赖是否存在（比如 prometheus 需要 registry、httpexchanges 需要 Repository Bean）、端点 ID 是否拼错、access 是否被限制。

3.3 健康详情与自定义分组

show-details: always 让 /actuator/health 返回各组件明细。在此基础上定义 custom 健康分组，除 /actuator/health 外还能访问 /actuator/health/custom，它只包含 storage 与 diskSpace 两个组件。分组适合给不同消费方用：负载均衡只看存活探针，运维平台看全量，避免一个端点把所有内部状态都摊开。

3.4 info 贡献者与 heapdump 放开

info.app.* 写在配置文件里，同时显式启用 env、java、os 三个 info 贡献者，/actuator/info 输出才稳定，不会因环境默认值差异变成空对象。

3.5 里 heapdump 默认不是 unrestricted。不写 management.endpoint.heapdump.access: unrestricted，即使把它放进 include，端点也不会注册到 Web 上；加上后 /actuator/heapdump 返回 200 与 JAVA PROFILE 1.0.2 开头的 HPROF 二进制流。

四、启动类、统一响应与异常处理

4.1 全局异常处理器为什么要限定包范围

这是本次搭建最值得单独讲的坑。@ExceptionHandler(Exception.class) 兜底如果不限制 basePackages，会接管 Actuator 端点抛出的所有异常：用 Accept: application/json 请求 /actuator/prometheus 和 /actuator/heapdump，框架抛出 HttpMediaTypeNotAcceptableException，被兜底包装成业务错误体，同时打一整段 ERROR 堆栈；浏览器请求 /favicon.ico 触发的 NoResourceFoundException 也会被兜底变成 500。这两类都不是业务异常，不该由业务响应体接管。

把异常处理器限定到业务 Controller 包后，业务接口仍享受统一的 400/404/500 治理，而静态资源与端点异常交回 Spring MVC 默认解析器：

@RestControllerAdvice(basePackages = "com.example.actuator.controller")
public class GlobalExceptionHandler {

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<Map<String, Object>> unreadable(HttpMessageNotReadableException e) {
        return ResponseEntity.badRequest().body(Map.of("success", false, "message", "请求体不是合法 JSON"));
    }

    // ... 400 / 404 / 500 分支
}

另外补上 HttpMessageNotReadableException → 400，保证非法 JSON 不会落到兜底的 500。

五、写一个能产生真实数据的业务接口

监控教程如果只有 /hello，http.server.requests 和业务指标都是空的。加一组自洽的订单接口：内存仓储、创建后可查、删除后查不到。

异常映射实测结果：

场景 请求 状态码

请求体非法 {bad json 400

六、自定义健康检查

内置的 diskSpace、ping 等指示器只能反映 JVM 和磁盘；业务依赖是否可用，要靠自己实现 HealthIndicator 补上。

@Component
public class StorageHealthIndicator implements HealthIndicator {

    private final Path dataDir = Path.of("data");
    private volatile boolean faultInjected;

    public StorageHealthIndicator() throws IOException {
        Files.createDirectories(dataDir);
    }

    @Override
    public Health health() {
        if (faultInjected) {
            return Health.down().withDetail("storage", "fault injected").build();
        }
        return Health.up().withDetail("storage", "reachable").build();
    }

    public void setFaultInjected(boolean faultInjected) {
        this.faultInjected = faultInjected;
    }
}

两个设计细节：构造函数里 Files.createDirectories 保证默认启动就是 UP，不会因为忘了建 data 目录导致应用一启动健康就 DOWN；额外留一个 faultInjected 开关，真实项目可换成远程服务探测，教程用可控开关演示「健康状态真的会变」。

6.1 Bean 名到健康项 ID 的规则

Spring Boot 把 XxxHealthIndicator 的 Bean 名去掉 HealthIndicator 后缀、首字母小写，作为健康项 ID。所以 StorageHealthIndicator 在响应里的键是 storage，健康分组里写的也是 storage。

七、业务指标

7.1 三种指标一次注册

三种类型分工明确：Counter 只增不减，记录累计次数；Timer 记录耗时分布；Gauge 反映当前瞬时值，靠持有 AtomicInteger 引用实现，创建订单时加一、删除时减一。

7.2 在业务链路里埋点

埋点集中在创建订单的业务方法里，用 Timer.record(Supplier) 包住仓储写入，一次拿到真实耗时：

private final MeterRegistry meterRegistry;

public OrderResponse create(OrderCreateRequest req) {
    Counter.builder("business.orders.created").register(meterRegistry).increment();
    Gauge.builder("business.orders.active", activeCount, AtomicInteger::get)
            .register(meterRegistry);
    return Timer.builder("business.orders.create.latency")
            .register(meterRegistry)
            .record(() -> orderRepository.save(req));
}

先访问 /actuator/metrics 拿指标名列表，再访问 /actuator/metrics/{name} 拿具体数值。

7.3 Prometheus 名称转换：不要凭拼接猜

按直觉，Counter business.orders.created 在 scrape 文本里应该叫 business_orders_created_total，但实测 .created 后缀被收敛成了 _total，实际输出是 business_orders_total。Gauge 与 Timer 的输出则符合直觉。

结论：验证脚本按实际输出名断言，不要用点转下划线再拼 _total 的规则去猜。这个差异在 Micrometer 1.15.12 + Prometheus Java Client 1.3.10 组合下实测成立，换版本时以 /actuator/prometheus 实际输出为准。

八、自定义端点

Actuator 允许用 @Endpoint 定义自己的端点，一个端点上可以同时有读、写、删除三种操作：

操作 方法 HTTP 返回值 状态码
读 @ReadOperation GET /actuator/appstatus Map 200
写 @WriteOperation + @Selector POST /actuator/appstatus/inject Map 200
删除 @DeleteOperation DELETE /actuator/appstatus void 204 
@Endpoint(id = "appstatus")
@Component
public class AppStatusEndpoint {

    private final StorageHealthIndicator storageHealthIndicator;

    @ReadOperation
    public Map<String, Object> status() {
        return Map.of("running", true);
    }

    @WriteOperation
    public Map<String, Object> inject(@Selector String action) {
        boolean on = "inject".equals(action);
        storageHealthIndicator.setFaultInjected(on);
        return Map.of("faultInjected", on);
    }

    @DeleteOperation
    public void clear() {
        storageHealthIndicator.setFaultInjected(false);
    }
}

@Selector 把路径最后一段绑定成方法参数，所以 inject / clear 走同一个写方法。自定义端点 ID 是 appstatus，必须出现在 exposure.include 里才会暴露。

有了这个端点，健康状态联动可以在不重启应用的情况下完整验证：注入 → DOWN → 回读开关为 true → 清除 → UP，五步全部做成断言。这证明自定义指示器真的接进了 Actuator 的健康聚合链路。

九、应用信息 info

9.1 静态配置

info.app.* 由 env 贡献者读取，/actuator/info 返回 app.name = actuator-demo。info 适合放应用名、版本、构建号这类识别信息，不要放密码、Token、手机号等敏感值。

9.2 自定义 InfoContributor

静态配置之外，还可以追加运行时信息。实现 InfoContributor 并注册成 Bean，contribute 里用 builder.withDetail 追加任意结构：

@Component
public class RuntimeInfoContributor implements InfoContributor {
    @Override
    public void contribute(Info.Builder builder) {
        builder.withDetail("runtime", Map.of("jvm", System.getProperty("java.version")));
    }
}

十、HTTP 交换记录

httpexchanges 端点需要一个 HttpExchangeRepository Bean 才会自动装配。只把它写进 include 不够，必须显式注册。加上这个 Bean 后，/actuator/httpexchanges 返回 200 且 exchanges 数组里有实际调用记录。内存实现只保留最近 100 条，重启即清空；生产环境应考虑持久化或换成专用链路追踪方案。

十一、内置端点逐项验证

11.1 端点发现页

GET /actuator 返回 _links，把当前暴露的端点全列出来，带模板参数的链接（如 metrics-requiredMetricName、appstatus-action）也会一并给出。这是排查「某个端点为什么 404」的第一站：链接里有，说明端点注册成功；链接里没有，说明条件依赖或 access 没满足。

11.2 内置端点实测清单

端点 路径 实测状态
health /actuator/health 200，status=UP，含 storage 组件
health 分组 /actuator/health/custom 200，含 storage + diskSpace
info /actuator/info 200，含 app / runtime
metrics /actuator/metrics 200，指标名列表非空
metrics 详情 /actuator/metrics/{name} 200，含 measurements
prometheus /actuator/prometheus 200，text/plain;version=0.0.4
env / beans / mappings / conditions / configprops 同名路径 200
loggers / threaddump 同名路径 200
heapdump /actuator/heapdump 200，HPROF 二进制流
httpexchanges /actuator/httpexchanges 200，含 exchanges
caches / scheduledtasks 同名路径 200，空结构（项目无缓存/定时任务）

caches 与 scheduledtasks 返回空结构是正常的——端点本身注册成功。

11.3 两个需要特殊 Accept 的端点

prometheus 产出 text/plain;version=0.0.4;charset=utf-8，heapdump 产出 application/octet-stream。用 Accept: application/json 去请求，媒体类型协商会失败返回 406：

Accept /actuator/prometheus /actuator/heapdump
text/plain / application/octet-stream 200 200
*/* 200 200
application/json 406 406

11.4 暴露边界

shutdown 默认禁用且没有写进 include，POST /actuator/shutdown 返回 404。这个端点能直接关掉应用，任何环境都不该随手开放。

十二、构建与集成测试

12.1 测试环境默认关闭可观测性

首轮构建有一个测试失败：/actuator/prometheus 返回 404，测试上下文的端点发现页 _links 里没有 prometheus，启动日志只暴露 15 个端点。

根因不在项目代码，而在 Spring Boot Test 的默认行为：测试上下文里的 ObservabilityContextCustomizerFactory 会关闭可观测性（含指标导出），导致 PrometheusMeterRegistry 不创建、prometheus 端点因条件不满足而不注册。这是测试框架为避免集成测试产生外部指标导出而做的收敛，但会让测试与真实运行行为不一致。

12.2 用 @AutoConfigureObservability 恢复

在测试类上加官方注解即可恢复：

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureObservability
class ActuatorIntegrationTest {
    // ...
}

加上之后测试环境也变成暴露 16 个端点，集成测试全部通过。测试类覆盖：业务连通性、健康状态、info 内容、metrics 与 Prometheus、自定义端点与健康联动、订单 CRUD 与校验、shutdown 未暴露。

十三、生产形态：端口隔离与最小暴露

13.1 为什么要分端口

本地学习把 16 个端点全打开没问题，生产环境这么做等于把环境变量、Bean 结构、配置属性、线程栈和堆内存全摊在公网。prod 配置做三件事：

  1. management.server.port: 9090 + address: 127.0.0.1，把管理端点挪到独立的本机端口；
  2. exposure.include 只留 health,info,prometheus；
  3. show-details: when-authorized，未认证时健康响应不含组件明细。

13.2 实测结论

业务接口在业务端口可访问；业务端口访问 /actuator/health 返回 404；管理端口 9090 的 health 返回 200 且不含 components，info / prometheus 返回 200；env / beans / heapdump / mappings / loggers / shutdown 全部 404。

端口分离本身不等于认证，但它把攻击面从「任意业务请求可达」压缩到「只有能连上管理网段才看得到」。

13.3 与 Spring Security 集成

本项目没有引入 Spring Security，目的是让端点行为可以无认证地直接验证。生产环境应当补上认证授权；如果项目已有 SecurityFilterChain，把规则合并进去，不要覆盖业务系统原有策略，配合 EndpointRequest.toAnyEndpoint() 精确匹配管理端点。同时启用 HTTPS、配置具备 ACTUATOR 角色的管理账号，不要把账号密码写进代码仓库。

13.4 敏感端点清单

端点 主要风险 生产建议
env 环境变量、配置属性、可能关联密钥 不暴露
configprops 配置绑定结果 不暴露或严格授权
beans / mappings 暴露内部结构与接口清单 不暴露
heapdump 可能包含内存中的业务数据，文件体积大 不暴露，按需离线导出
threaddump 线程栈与调用链 限制访问范围
loggers 可动态改级别，写操作需防护 不暴露
shutdown 可直接关闭应用 保持禁用

十四、踩坑汇总

现象 根因 修复
Accept: application/json 请求 prometheus/heapdump 得到 500 + ERROR 堆栈 全局 @RestControllerAdvice 的 Exception 兜底接管了框架级 406 用 basePackages 把异常处理器限定到业务 Controller 包
非法 JSON 请求落到 500 兜底先于校验异常被命中 显式处理 HttpMessageNotReadableException → 400
/favicon.ico 产生 ERROR 日志 全局兜底把 NoResourceFoundException 变成 500 同上；首页用 <link rel="icon" href="data:,"> 避免浏览器发起该请求
集成测试里 prometheus 返回 404，只暴露 15 个端点 Spring Boot Test 默认关闭可观测性，PrometheusMeterRegistry 不创建 测试类加 @AutoConfigureObservability
Prometheus 文本里找不到 business_orders_created_total Micrometer 1.15 把 .created 收敛为 _total，实际名是 business_orders_total 按实际输出名断言，不凭规则拼接
heapdump 写进 include 仍不注册 3.5 里 heapdump 默认不是 unrestricted management.endpoint.heapdump.access: unrestricted

十五、小结

这个项目从空目录到可运行，核心就是三层：

  1. 依赖与配置层：spring-boot-starter-actuator + 显式 exposure.include + show-details + Prometheus registry，决定「有哪些端点、谁能看到多少」。
  2. 扩展层：HealthIndicator、InfoContributor、@Endpoint、MeterRegistry，把业务自己的状态和指标接进 Actuator 体系。
  3. 治理层：包范围受限的异常处理、prod 下的端口隔离与最小暴露、敏感端点清单、认证与网络 ACL，决定「上线后会不会变成风险」。

三个容易被忽略但实测很有价值的结论：

  1. 3.5 默认只暴露 health，别按老经验假设 info 也在；
  2. 全局异常处理器会干扰 Actuator 端点，必须限定作用域；
  3. 测试环境默认关闭可观测性，验证端点行为要以真实 jar 为准。

备注：本篇为个人学习整理，内容基于公开学习资料归纳，代码片段为通用示例；内存仓储仅用于演示，真实项目应替换为持久层并补充权限校验。
